# Сценарии вариантов использования

## UC1. Получить прогноз загрузки объекта/района

**Краткое описание:** Отельер или представитель региональной администрации получает прогноз загрузки конкретного средства размещения или района Иркутской области на горизонт до 30 дней.

**Действующие лица:** Отельер, Администратор региона

**Цель:** Получить количественную оценку ожидаемой загрузки и доверительный интервал прогноза для принятия решений по тарифам, маркетингу и операционному планированию.

**Предусловия:**
- Система доступна, ML-сервис прошёл прогрев `_warmup_forecast_cache`.
- В PostgreSQL присутствует история `hotel_statistics` за последние 90 дней.
- Ensemble обучён (Prophet + NeuralProphet + XGBoost), feature engineering пайплайн доступен.

**Постусловия:**
- Прогноз отображён пользователю в виде графика с CI-bands (нижняя/верхняя границы).
- Прогноз закэширован в Redis на 30 минут (TTL по умолчанию).
- Запрос пользователя зафиксирован в журнале.

**Основной поток:**
1. Пользователь открывает страницу «Прогноз спроса».
2. Система отображает форму с полями: район, объект (опционально), горизонт прогноза (3, 7, 14, 30 дней).
3. Пользователь задаёт параметры и нажимает «Построить прогноз» (include: Ввести параметры запроса).
4. Система обращается к `/api/forecast/ensemble` (include: Запросить Ensemble прогноз).
5. Сервис ensemble через `executor.run_sync` параллельно строит прогнозы трёх моделей и считает weighted average.
6. Система отображает прогноз на графике с доверительными интервалами (include: Визуализировать результат).
7. Система сохраняет запрос в журнал.

**Альтернативные потоки:**

*4a. Прогноз есть в кэше Redis:*
- 4a.1. Сервис возвращает закэшированный результат без перезапуска ML.
- 4a.2. Переход к шагу 6.

*5a. Запрошен горизонт > 14 дней (extend: Показать CI-bands):*
- 5a.1. Система явно выделяет «зону низкой уверенности» начиная с 15-го дня.
- 5a.2. Доверительный интервал расширяется по правилу `±1.96·σ`.
- 5a.3. Переход к шагу 6.

*6a. Пользователь запросил сравнение моделей (extend: Показать метрики моделей):*
- 6a.1. Система обращается к `/api/forecast/compare-all`.
- 6a.2. Под графиком показывается таблица RMSE / MAE / R² по моделям.
- 6a.3. Переход к шагу 7.

*5b. Ошибка при обращении к ML-сервису:*
- 5b.1. Сервис возвращает 503 / fallback к одиночной модели Prophet.
- 5b.2. Система помечает ответ как «деградированный».
- 5b.3. Переход к шагу 6.

**Ассоциации:**
- UC1 связан с UC2 (прогноз показывается внутри карточки объекта) и UC10 (RMS-метрики используют тот же прогноз для пересчёта Pace).


## UC2. Просмотреть карточку своего объекта размещения

**Краткое описание:** Отельер открывает карточку своего объекта и получает консолидированную картину: профиль, динамику бронирований, актуальные RMS-метрики, прогноз загрузки.

**Действующие лица:** Отельер

**Цель:** Получить единую панель управления объектом с ключевыми показателями для Revenue Management.

**Предусловия:**
- Объект существует в реестре `hotels` PostgreSQL.
- За последние 30 дней есть записи `hotel_statistics`.
- ID объекта известен пользователю (или передан из списка объектов).

**Постусловия:**
- Карточка объекта отображена с актуальными данными.
- Метрики RMS показаны рядом с прогнозом и динамикой цен.

**Основной поток:**
1. Отельер переходит в раздел «Объекты размещения» или открывает прямую ссылку `/hotels/:id`.
2. Система загружает профиль объекта (include: Загрузить профиль объекта).
3. Система загружает историю загрузки за последние 30 дней (include: Загрузить статистику загрузки).
4. Система загружает историю минимальной цены и доступных номеров (include: Загрузить динамику цен).
5. Система отображает карточку: название, район, тип, рейтинг, номерной фонд, графики динамики.
6. Отельер просматривает карточку.

**Альтернативные потоки:**

*5a. Просмотреть RMS-метрики объекта (extend: UC10):*
- 5a.1. Отельер нажимает «RMS-метрики» в карточке.
- 5a.2. Система запрашивает `/api/analytics/revenue-summary?hotel_id=...`.
- 5a.3. Под профилем отображаются блоки RevPAR / ADR / Occupancy / Pickup / Pace.
- 5a.4. Переход к шагу 6.

*5b. Просмотреть прогноз загрузки (extend: UC1):*
- 5b.1. Отельер нажимает «Прогноз».
- 5b.2. Система обращается к `/api/forecast/ensemble?hotel_id=...`.
- 5b.3. Под профилем отображается прогноз с CI-bands.
- 5b.4. Переход к шагу 6.

*5c. Посмотреть на карте (extend: Посмотреть на карте):*
- 5c.1. Отельер нажимает «На карте».
- 5c.2. Система открывает страницу `/map` с маркером, центрированным на объект.

*2a. Объект не найден:*
- 2a.1. Система возвращает 404 и сообщение «Объект не найден или ему не присвоены данные».
- 2a.2. Сценарий завершается.

**Ассоциации:**
- UC2 является входной точкой для UC1 и UC10 в контексте конкретного объекта.


## UC3. Анализ событий и их влияния на спрос

**Краткое описание:** Пользователь анализирует календарь событий региона и оценивает влияние каждого события на загрузку средств размещения.

**Действующие лица:** Отельер, Администратор региона, Исследователь

**Цель:** Понять, какие события исторически дают всплеск спроса и где ожидаются пики в ближайшем будущем.

**Предусловия:**
- В таблице `events` PostgreSQL есть записи минимум за 6 месяцев.
- Эндпоинт `/api/analytics/events-impact` доступен.

**Постусловия:**
- Список событий с расчётными impact-значениями отображён.

**Основной поток:**
1. Пользователь переходит в раздел «События и спрос».
2. Система загружает календарь событий из PostgreSQL (include: Получить календарь событий).
3. Для каждого события сервис рассчитывает impact = `Δ Occupancy = Occupancy(день события) − среднее Occupancy(±7 дней)` (include: Рассчитать impact события).
4. Система отображает таблицу: дата, название, тип, источник, impact (число и спарклайн).
5. Пользователь сортирует/фильтрует список.

**Альтернативные потоки:**

*4a. Фильтр по типу события (extend: Фильтровать по типу/источнику):*
- 4a.1. Пользователь выбирает тип (фестиваль, концерт, конференция, спорт).
- 4a.2. Система применяет фильтр и обновляет таблицу.

*4b. Сортировка по impact (extend: Сортировать по impact):*
- 4b.1. Пользователь нажимает на заголовок «Impact».
- 4b.2. Система сортирует по убыванию.
- 4b.3. Видны верхние события-драйверы спроса.

*4c. Просмотреть детали события (extend: Просмотреть детали события):*
- 4c.1. Пользователь кликает на строку.
- 4c.2. Система открывает карточку: описание, площадка, источник, ссылка, исторические impact-значения для аналогичных событий.

**Ассоциации:**
- UC3 поставляет регрессоры для UC1 (Ensemble использует event-features при прогнозе).


## UC4. Сравнить модели прогнозирования и выгрузить методологию

**Краткое описание:** Исследователь запускает сравнение Prophet, NeuralProphet, XGBoost и Ensemble на одном горизонте, получает метрики качества и методологическое описание.

**Действующие лица:** Исследователь

**Цель:** Получить воспроизводимый артефакт для академической публикации или внутреннего обзора методологии.

**Предусловия:**
- Все три модели обучены и доступны.
- Эндпоинт `/api/forecast/compare-all` отвечает.

**Постусловия:**
- Исследователь скачал CSV с метриками.
- Методологическое описание (раздел «Feature engineering, гиперпараметры, weights») доступно.

**Основной поток:**
1. Исследователь переходит в раздел «Сравнение моделей».
2. Исследователь выбирает район и горизонт прогноза.
3. Система обращается к `/api/forecast/compare-all` (include: Запустить compare-all).
4. Backend параллельно через `executor.run_sync` запускает 3 модели и собирает метрики (include: Получить метрики).
5. Система отображает таблицу: модель, RMSE, MAE, R², время выполнения.
6. Под таблицей — feature importance XGBoost (топ-15).

**Альтернативные потоки:**

*6a. Скачать методологию (extend: Скачать методологию):*
- 6a.1. Исследователь нажимает «Экспорт методологии».
- 6a.2. Система формирует CSV с метриками + текстовое описание моделей и весов Ensemble.
- 6a.3. Браузер инициирует загрузку файла.

*6b. Просмотреть feature importance (extend: Просмотреть feature importance):*
- 6b.1. Исследователь раскрывает блок feature importance.
- 6b.2. Система отображает столбчатую диаграмму с весами признаков.

*4a. Один из горизонтов недоступен:*
- 4a.1. Сервис помечает строку модели как «n/a» с пояснением (например, «недостаточно данных для XGBoost на горизонте 30 дней»).
- 4a.2. Переход к шагу 5.

**Ассоциации:**
- UC4 связан с UC9 — оба возвращают артефакты для исследовательских задач.


## UC5. Региональная аналитика рынка

**Краткое описание:** Администратор региона получает агрегированный срез по районам Иркутской области: heatmap загрузки, рейтинг RevPAR, динамика средств размещения.

**Действующие лица:** Администратор региона

**Цель:** Сформировать отчёт о состоянии рынка средств размещения для принятия решений на уровне Министерства туризма.

**Предусловия:**
- Эндпоинты `/api/analytics/heatmap`, `/api/analytics/revenue-summary`, `/api/analytics/districts` доступны.

**Постусловия:**
- Администратор имеет визуализированную картину рынка по 15 районам.

**Основной поток:**
1. Администратор переходит в раздел «Аналитика рынка».
2. Система загружает heatmap занятости по районам и месяцам (include: Загрузить heatmap по районам).
3. Система загружает рейтинг районов по RevPAR (include: Загрузить рейтинг RevPAR).
4. Система отображает: heatmap (ECharts), бар-чарт RevPAR-рейтинга, treemap количества объектов.
5. Администратор взаимодействует с визуализациями.

**Альтернативные потоки:**

*4a. Сравнение районов (extend: Сравнение районов):*
- 4a.1. Администратор выбирает 2–4 района.
- 4a.2. Система отображает совмещённый график динамики Occupancy.

*4b. Скачать сводный отчёт (extend: Скачать сводный отчёт):*
- 4b.1. Администратор нажимает «Экспорт сводки».
- 4b.2. Система формирует CSV с агрегатами по районам (см. UC9).

**Ассоциации:**
- UC5 потребляет те же данные, что UC10, но в агрегированном по району виде.


## UC6. Управление источниками данных

**Краткое описание:** Технический администратор управляет настройками парсеров и источников данных.

**Действующие лица:** Технический администратор

**Предусловия:**
- Пользователь авторизован как технический администратор (`X-API-Key`).
- Эндпоинты `/api/parser/...` доступны.

**Постусловия:**
- Настройки источников данных обновлены, парсер при необходимости перезапущен вручную.

**Основной поток:**
1. Технический администратор переходит в раздел «Источники данных».
2. Система загружает список источников и состояние health-monitor (include: Загрузить список источников).
3. Система отображает таблицу: источник, URL, статус, последний сбор, количество ошибок.
4. Технический администратор просматривает информацию.

**Альтернативные потоки:**

*4a. Редактировать настройки (extend: Редактировать настройки):*
- 4a.1. Администратор кликает на источник.
- 4a.2. Система открывает форму с параметрами (URL, частота, активность).
- 4a.3. Администратор сохраняет.
- 4a.4. Система валидирует и обновляет конфигурацию.

*4b. Проверить доступность (extend: Проверить доступность):*
- 4b.1. Администратор нажимает «Проверить» рядом с источником.
- 4b.2. Система выполняет тестовый запрос.
- 4b.3. Система отображает результат (доступен / недоступен / частичный ответ).

*4c. Перезапустить парсер (extend: Перезапустить парсер):*
- 4c.1. Администратор нажимает «Запустить сейчас» (требует API-ключ).
- 4c.2. Система обращается к `/api/parser/{source}/run`.
- 4c.3. Парсер запускается асинхронно, результат отражается в логах (UC7).


## UC7. Мониторинг работы системы

**Действующие лица:** Технический администратор

**Предусловия:**
- Пользователь авторизован.
- Сервисы `db_service`, `cache_service`, `chroma_service` отвечают на health-checks.

**Постусловия:**
- Администратор получил картину состояния системы.

**Основной поток:**
1. Технический администратор переходит в раздел «Мониторинг».
2. Система загружает последние записи журнала и метрики health (include: Загрузить логи и метрики).
3. Система отображает таблицу логов и виджеты статуса (PostgreSQL, Redis, ChromaDB, ML, LLM).
4. Технический администратор просматривает информацию.

**Альтернативные потоки:**

*3a. Фильтровать по уровню (extend: Фильтровать по уровню):*
- 3a.1. Администратор выбирает уровень (ERROR / WARNING / INFO).
- 3a.2. Система применяет фильтр.

*3b. Статистика парсеров (extend: Статистика парсеров):*
- 3b.1. Администратор открывает вкладку «Парсеры».
- 3b.2. Система отображает количество собранных записей и ошибок по каждому из 8 парсеров событий + 3 парсеров отелей/погоды.

*3c. Health-checks сервисов (extend: Health-checks сервисов):*
- 3c.1. Система отображает результат `/health` каждые 30 секунд.


## UC8. Автоматический сбор данных

**Краткое описание:** Планировщик APScheduler запускает автоматический сбор данных из внешних источников по расписанию.

**Действующие лица:** Планировщик (APScheduler / AsyncIOScheduler)

**Предусловия:**
- Backend запущен (lifespan-инициализация прошла успешно).
- Источники данных настроены и активны.
- В `.env` заданы корректные ключи API (если требуется).

**Постусловия:**
- Данные в PostgreSQL обновлены.
- Векторный индекс ChromaDB переиндексирован.
- Результат записан в журнал.

**Основной поток:**
1. APScheduler срабатывает по расписанию (события — 6ч, отели — 2ч, погода — 3ч, Telegram — 1ч).
2. Система инициализирует подключение к PostgreSQL.
3. Система выполняет сбор событий из 8 источников (include: Собрать события).
4. Система выполняет сбор средств размещения через 101Hotels API + Xotelo (include: Собрать средства размещения).
5. Система выполняет сбор погоды через Open-Meteo (include: Собрать погоду).
6. Система сохраняет данные в PostgreSQL.
7. Система обновляет векторный индекс ChromaDB (include: Обновить индекс ChromaDB).
8. Система записывает результат в журнал (количество записей, время выполнения).

**Альтернативные потоки:**

*3a–5a. Ошибка при сборе из источника:*
- Xa.1. Система фиксирует ошибку в журнале (WARNING).
- Xa.2. HealthMonitor увеличивает счётчик ошибок источника.
- Xa.3. Система продолжает сбор из следующего источника.

*6a. Ошибка записи в PostgreSQL:*
- 6a.1. Система выполняет повторную попытку (до 3 раз).
- 6a.2. При неудаче — фиксирует ошибку (ERROR) и переходит к шагу 8.

*8a. Критическая ошибка (extend: Уведомить Технического администратора):*
- 8a.1. Все источники недоступны или ошибка БД.
- 8a.2. Система отправляет уведомление техническому администратору.


## UC9. Экспорт данных для исследовательских задач

**Краткое описание:** Исследователь выгружает структурированный набор данных (загрузка средств размещения / события / реестр гостиниц) в формате CSV для собственных аналитических задач.

**Действующие лица:** Исследователь

**Цель:** Получить воспроизводимую выгрузку данных в открытом формате с указанием диапазона дат и фильтра по району.

**Предусловия:**
- Эндпоинт `/api/analytics/export?type=occupancy|events|hotels` доступен.
- В PostgreSQL есть данные за запрошенный период.
- Размер выгрузки не превышает лимит (по умолчанию 100 000 строк).

**Постусловия:**
- CSV-файл сформирован и отдан клиенту.
- Запрос на выгрузку зафиксирован в журнале.

**Основной поток:**
1. Исследователь переходит в раздел «Аналитика рынка» или «Сравнение моделей».
2. Исследователь нажимает «Экспорт CSV».
3. Система открывает форму: тип данных (occupancy / events / hotels), диапазон дат, район (опционально).
4. Исследователь задаёт параметры и подтверждает.
5. Система обращается к `/api/analytics/export?type=...&date_from=...&date_to=...&district=...` (include: Запросить выгрузку).
6. Сервис формирует CSV из PostgreSQL (include: Сформировать CSV).
7. Браузер инициирует загрузку файла (include: Скачать файл).
8. Система фиксирует запрос в журнале.

**Альтернативные потоки:**

*4a. Выбран type=occupancy (extend: Выбрать тип данных):*
- 4a.1. CSV содержит колонки: date, hotel_id, district, available_rooms_percent, min_price.

*4b. Выбран type=events:*
- 4b.1. CSV содержит колонки: date, name, type, source, district, impact.

*4c. Выбран type=hotels:*
- 4c.1. CSV содержит колонки: id, name, district, type, rating, rooms_total.

*4d. Задать диапазон дат (extend: Задать диапазон дат):*
- 4d.1. Если диапазон не задан — по умолчанию последние 90 дней.

*4e. Указать фильтр по району (extend: Указать фильтр по району):*
- 4e.1. Если параметр пуст — выгрузка по всем 15 районам.

*6a. Превышение лимита строк:*
- 6a.1. Сервис возвращает 413 Payload Too Large с указанием максимального допустимого диапазона.
- 6a.2. Система предлагает сузить период.
- 6a.3. Возврат к шагу 4.

*6b. Данные за период отсутствуют:*
- 6b.1. Сервис возвращает CSV только с заголовками.
- 6b.2. UI отображает предупреждение «Данные за период не найдены».

**Ассоциации:**
- UC9 запускается из UC4 (выгрузка методологии) и UC5 (выгрузка сводки по районам).


## UC10. Расчёт RMS-метрик: RevPAR, ADR, Pickup, Pace

**Краткое описание:** Отельер получает расчёт ключевых метрик Revenue Management для своего объекта или района: RevPAR, ADR, Occupancy %, Pickup, Pace, а также тепловую карту загрузки по дням недели.

**Действующие лица:** Отельер

**Цель:** Получить численную оценку доходности и динамики бронирований объекта для принятия решений по тарифам.

**Предусловия:**
- Эндпоинты `/api/analytics/revenue-summary`, `/api/analytics/pickup-pace`, `/api/analytics/weekday-heatmap` доступны.
- В PostgreSQL есть `hotel_statistics` за период.
- Если в данных отсутствует `revenue` — сервис возвращает прокси-оценку через `min_price * occupancy_share` (явно помечает в ответе).

**Постусловия:**
- Метрики рассчитаны и отображены пользователю.
- Дополнительный запрос на скачивание метрик (CSV) — опционален.

**Основной поток:**
1. Отельер переходит в раздел «RMS-метрики» или открывает блок метрик из карточки объекта (UC2).
2. Отельер задаёт параметры: объект (или район), диапазон дат.
3. Система обращается к `/api/analytics/revenue-summary?hotel_id=...&date_from=...&date_to=...` (include: Получить агрегаты).
4. Сервис рассчитывает:
   - **RevPAR** = revenue / available room nights.
   - **ADR** = revenue / sold room nights.
   - **Occupancy %** = sold / available.
5. Система обращается к `/api/analytics/pickup-pace?hotel_id=...&target_date=...` (include: Получить Pickup/Pace).
6. Сервис рассчитывает:
   - **Pickup** — изменение бронирований за фиксированное окно (например, +7 дней).
   - **Pace** — кумулятивный темп набора бронирований за 30 дней до даты заезда.
7. Система обращается к `/api/analytics/weekday-heatmap?hotel_id=...` (include: Получить heatmap).
8. Сервис формирует матрицу 7×12 (дни недели × месяцы) средней загрузки.
9. Система отображает блоки RevPAR / ADR / Occupancy %, графики Pickup / Pace и тепловую карту.

**Альтернативные потоки:**

*4a. Сравнить с прошлым периодом (extend: Сравнить с прошлым периодом):*
- 4a.1. Отельер включает переключатель «vs прошлый период».
- 4a.2. Сервис дополнительно считает метрики за равный по длине предыдущий период.
- 4a.3. UI отображает дельты в процентах рядом с каждой метрикой.

*9a. Скачать метрики (extend: Скачать метрики):*
- 9a.1. Отельер нажимает «Скачать CSV».
- 9a.2. Система запускает UC9 с предзаполненными параметрами (type=occupancy + RMS-агрегаты).

*9b. Просмотреть тренд (extend: Просмотреть тренд):*
- 9b.1. Система рисует линию RevPAR по неделям за последние 12 недель.

*4b. Нет revenue в данных:*
- 4b.1. Сервис рассчитывает прокси-оценку через `min_price * occupancy_share`.
- 4b.2. UI отображает значения с пометкой «прокси-оценка».
- 4b.3. Переход к шагу 5.

*3a. Нет данных за период:*
- 3a.1. Сервис возвращает пустой ответ с пояснением.
- 3a.2. UI отображает «Недостаточно данных для расчёта метрик».

**Ассоциации:**
- UC10 является развитием UC2 — отельер видит метрики в контексте конкретного объекта.
- Результаты UC10 могут быть выгружены через UC9.
