**Спасает:** старый парсер (внешний к проекту) **продолжает работать** и пишет данные о 101hotels в **рабочую YDB-таблицу**. Эта таблица — единственный актуальный источник данных по средствам размещения за период простоя.

**Что делаем:**

1. `MUST` — Зафиксировать period gap: написать SQL по `hotel_statistics` в PostgreSQL, найти `MAX(date)` и сравнить с `date.today()`. Если gap > 3 дней — нужен импорт.
2. `MUST` — Создать одноразовый скрипт `backend/scripts/import_from_ydb_101hotels.py`:
   - Подключение к YDB через `ydb` Python SDK + JSON-credentials.
   - SELECT по hotel_statistics WHERE date BETWEEN gap_start AND today.
   - Маппинг колонок YDB → PostgreSQL `hotel_statistics` (поля: id, date, rooms_num, free_rooms_amount, available_rooms_percent, min_price).
   - Batch upsert (`ON CONFLICT (id, date) DO UPDATE`) — идемпотентно.
   - Логирование: сколько строк прочитано из YDB, сколько upsert, сколько skip.
3. `SHOULD` — После импорта: переиндексировать ChromaDB по свежим данным (`/api/parser/reindex` или вызовом `chroma_service.reindex_*`).
4. `SHOULD` — Запустить агента в фоне на dev (через `uvicorn`) и убедиться, что warmup-кэш ensemble-прогноза переподтянул свежие данные.

**Что про события:** события за период простоя восстанавливать сложнее — внешние источники (irk.ru, kassir.ru, Telegram) не имеют истории «как у YDB». Стратегия: после старта агента дать APScheduler один полный проход парсеров событий — догнать всё, что доступно через текущие парсеры.
