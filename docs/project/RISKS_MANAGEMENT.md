# Управление рисками проекта ВКР

## Тема: ИАС мониторинга и прогнозирования туристической активности Иркутской области

---

## Методология

- **Вероятность**: 0.1, 0.3, 0.5, 0.7, 0.9
- **Влияние**: 0.05, 0.1, 0.2, 0.4, 0.8
- **Величина** = Вероятность × Влияние
- **Категории**: Критические (≥0.18), Умеренные (0.04-0.18), Незначительные (<0.04)

## Стратегии реагирования

### 1. Уклонение от риска
Полное устранение риска путём изменения плана проекта.
- Не применяется в данном проекте (все риски управляемы)

### 2. Передача риска
Перенос последствий риска на другого участника.
- R10: Docker Compose обеспечивает воспроизводимое развёртывание (PostgreSQL 16 + Redis 7)

### 3. Снижение риска
Уменьшение вероятности и/или влияния до приемлемого уровня.
- **R1-R9**: Основная стратегия для всех выявленных рисков

### 4. Принятие риска
Осознанное принятие последствий без активных действий.
- R8: Частичное принятие (низкая вероятность при наличии резервного копирования)

## План реагирования на критические риски

### R1: Срыв сроков ВКР (0.40)

**Триггеры:**
- Отставание от плана более 5 дней
- Незавершённые работы критического пути

**Действия:**
1. Еженедельный контроль выполнения по диаграмме Ганта
2. Резерв 10% времени на каждую критическую работу
3. MVP-подход: сначала ядро системы, затем улучшения
4. Параллельное написание ВКР с разработкой

---

### R2: Низкое качество данных (0.28)

**Триггеры:**
- Пропуски >20% записей
- Несогласованность данных из разных источников

**Действия:**
1. Валидация данных на этапе парсинга (Pydantic)
2. Автоматическое заполнение пропусков (интерполяция)
3. Логирование и алерты при аномалиях
4. Ручная проверка выборки данных

---

### R3: Изменение требований (0.28)

**Триггеры:**
- Новые требования от научного руководителя
- Изменение scope проекта

**Действия:**
1. Фиксация требований в UC-диаграммах (UC1-UC7)
2. Документирование всех изменений
3. Оценка влияния изменений на сроки
4. Согласование изменений до реализации

---

### R4: Недоступность API (0.20)

**Триггеры:**
- HTTP ошибки при запросах к API
- Изменение структуры ответов

**Действия:**
1. Локальное кэширование данных (SQLite/JSON)
2. Retry-логика с exponential backoff
3. Мониторинг доступности (healthcheck)
4. Документирование альтернативных источников

---

### R5: Точность моделей (0.20)

**Триггеры:**
- MAPE > 15%
- Систематические ошибки прогноза

**Действия:**
1. Ensemble из Prophet + NeuralProphet + XGBoost
2. Кросс-валидация на временных рядах
3. Feature engineering (праздники, события)
4. A/B тестирование моделей
