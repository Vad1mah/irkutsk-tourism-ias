## 1. Зачем переделываем

После 7.04 — рефокус на B2B (отельеры, региональная администрация, исследователи). Субагент в сессии 2026-05-03 формально закрыл 9 этапов REFOCUS_PLAN (`tsc --noEmit` зелёный, pytest 104/2/1, скриншоты сделаны), но при ревью пользователем 04.05.2026 вскрылось, что фронт остаётся «солянкой»: блоки без обоснования, английская терминология, методологически неверные метрики, потеря функционала старого DataLens-дашборда, AI-чат пропал из навигации, парсеры собирают часть доступных полей, в backend 22% мёртвых эндпоинтов.

**Принцип масштаба правок:** **C — тотальная переработка, но без ломки того, что обосновано**. Защита далеко (минимум 7 дней), время есть, рискуем качеством за счёт скорости.

## 2. Принципы дизайна

### 2.1 Единый интерфейс

Все три B2B-сегмента (отельер, администрация, исследователь) пользуются **одними и теми же страницами**. Никаких персональных лендингов. Сегментация — через семантику и семантически обоснованные секции на одной странице, а не через роутинг и скрытие функций.

Откуда: явное требование пользователя 04.05.2026 («систему мониторинга разрабатывали как единую для всех»).

### 2.2 Каждый блок — обоснован тремя осями

Перед сохранением любого виджета должен быть однозначный ответ:
1. **Для кого полезно** — отельер / администрация / исследователь (или все три).
2. **Какую B2B-задачу решает** — конкретное действие, которое пользователь может предпринять.
3. **Почему именно в этом месте страницы** — логическая позиция в потоке внимания.

Если на любой из осей ответ «не знаю» — блок не нужен.

### 2.3 Сохранять, если обосновано; удалять, если нет

Правило по [фидбэку 04.05.2026](#): «если обосновывается хорошо — зачем переделывать». Большинство блоков на текущем фронте обосновываются после правок терминологии и методологии. Удаляем только то, что после честного ревью не находит ответа на три оси.

### 2.4 Прокси-метрики — честно

Везде, где `min_price` подменяет реальный ADR — пишем «прокси-ADR». В легенде, в tooltip, в методологии. Это не дефект, а часть research story. Проверено на эталонах STR/CoStar и Lighthouse — там тоже различают «реальный» и «оценочный» ADR.

### 2.5 Gap данных июль-сентябрь 2025 — highlight + annotate

Обработка по Song & Szafir VIS 2018: разрыв линии без интерполяции, серая зона на чарте с подписью «данные не собирались», отдельный цвет N/A в heatmap, методология на странице. Никакого тихого «дорисовывания».

### 2.6 Методология — на странице, не в коде

Каждая страница имеет видимый блок «Источники, методология, ограничения». Это требование исследовательского сегмента (по эталону Visit California Research Dashboard). Помогает защите — комиссия видит, что мы знаем границы своих данных.

## 5. Аналитика (`/analytics`)

### 5.1 Назначение

Глубокая аналитика рынка. Tabs внутри одной страницы, чтобы переключение между темами не тратило время на загрузку и сохраняло контекст района.

### 5.2 Структура — четыре tab'а

```
[ Регионы ] [ Сезонность ] [ События ] [ Сегменты ]
```

#### Tab 1: Регионы

- **RMS-сводка по 15 районам** (таблица). Сохраняем — это базовая ценность для администрации. Доработки:
  - Чекбокс «показывать только достоверные» (high + medium confidence). По умолчанию — включён, low-confidence строки скрыты.
  - При выключении — low-confidence строки рендерятся серым с tooltip «выборка слишком мала для уверенного среднего».
  - Колонка «Δ к региону» оставляем, но рядом — иконка info с пояснением «отклонение от средневзвешенного RevPAR региона».
  - Сортировка по умолчанию — по RevPAR убыв.
- **Mini-bar chart по 5 топовым районам** (сверху таблицы) — для быстрого сравнения, как у TravelLine.

#### Tab 2: Сезонность

- **Calendar heatmap** day-of-week × month — сохраняем с правильной обработкой gap (см. §2.5):
  - Для месяцев без данных — диагональная штриховка + подпись «нет данных», вместо тишины.
  - В легенде — отдельный квадрат «N/A» с пояснением.
- **Quartile bands** (новое) — пометка «high / mid / low season» по статистическим квартилям occupancy.
- **YoY-сравнение** (новое) — линейный график «текущий год vs предыдущий», с чётким разрывом в gap-периоде.

#### Tab 3: События

- **Топ-N событий с corrected impact** (новая методология, §6.3). Колонки: Дата, Событие, Тип, Район, occupancy_baseline, occupancy_observed, **Δ corrected** (с CI), Достоверность.
- Фильтр «только impact ≥ 5%» (по умолчанию выключен).
- **Demand calendar** (новое) — календарь-heatmap с pre-aggregated impact по датам (события, которые однозначно повышают спрос — выделены).

#### Tab 4: Сегменты

- **Распределение объектов по типам/звёздности** — bar chart по сегментам (хостел / гостиница / гостевой дом / санаторий, если есть в данных).
- **ADR-распределение по перцентилям** (p10/p25/p50/p75/p90) — box-plot или multi-line. Это исследовательский сегмент.
- **Сегментный benchmark** (паттерн TravelLine) — для каждого района: средняя цена в сегменте «5-15 номеров» / «15-50» / «50+» — отельеру даёт понимание «где я по тарифу относительно похожих по размеру».

## 6. Корректные методологии

### 6.1 RMS-сводка с фильтром достоверности

Текущая логика: показывать всё. Проблема — у Кабанского с 1 объектом дельта +265% выглядит как факт.

**Решение:**
- На уровне backend `revenue-summary` поле `confidence` уже возвращается (`high` ≥ 5 объектов, `medium` 2-4, `low` ≤ 1).
- На фронте — чекбокс «показывать только достоверные». По умолчанию `confidence != 'low'`.
- При сортировке по RevPAR — low-confidence строки идут в отдельную секцию «недостаточная выборка», не смешиваются с надёжными.

### 6.2 Прокси-ADR / прокси-RevPAR — методология

Везде называем «прокси-…». info-icon рядом с метрикой раскрывает:

> Прокси-ADR рассчитан как медианная минимальная цена номера на снимке, не как средневзвешенная цена реализованных номеров. Реальный ADR обычно на 15-30% выше. Прокси-RevPAR = прокси-ADR × occupancy. Метрика пригодна для сравнения районов и трендов, не для абсолютных ROI-расчётов.

Это снимает претензии комиссии «откуда RevPAR взяли» — мы честно говорим, как считаем.

### 6.3 Corrected events impact — переработка

**Текущая метрика (`/api/analytics/events-impact`)**: `impact = occupancy_on_day - avg_occupancy_period`. Проблема — при сезонном спаде (зима) `avg_occupancy` высокий за счёт лета (хотя у нас и лета нет — gap), и любое зимнее событие даёт огромный отрицательный impact, не отражающий реальное влияние.

**Новая методика** (по PredictHQ / Lighthouse Destination Insight):

```
baseline = mean(occupancy на похожих днях недели в окне ±3 недели до события,
                исключая дни других событий и gap-периоды)
observed = occupancy в день события
delta_pct = (observed - baseline) / baseline * 100%

confidence = функция(размер выборки baseline, std baseline, дистанция в днях)
```

Логика:
- Baseline считается из похожих дней недели (event в субботу — baseline по субботам), а не из всего периода.
- Окно ±3 недели — захватывает локальный сезонный фон.
- Исключаем другие события и gap — чтобы baseline не загрязнялся.
- Возвращаем CI (доверительный интервал) на основе bootstrap.

**Endpoint:** добавляем `GET /api/analytics/events-impact?method=seasonal_corrected&window_weeks=3`. Старая метрика остаётся как `method=naive` для обратной совместимости и для отчёта-сравнения.

### 6.4 Pickup proxy — методология

```
для каждой будущей даты D в окне (today + 1 .. today + 14):
  pickup_D = occupancy(D, snapshot_today) - occupancy(D, snapshot_today - N дней)
```

Где N = 7 (неделя назад). Это grow rate — насколько процентов загрузки набралось за неделю. Не реальный pickup (нет каналов прихода), но эквивалентен по смыслу для планирования.

### 6.5 Forecast vs Actual — самовалидация

Новый endpoint `GET /api/forecast/{district}/validation?days_back=30`:
- Берёт прогноз 14-дневной давности
- Сравнивает с фактическими наблюдениями
- Возвращает `{forecast, actual, rmse, mae, rmse_per_day}`

На странице `/forecast` (Expert mode) — мини-блок «как модель отрабатывает на свежих данных». Это важно для исследовательского сегмента и для защиты («модели регулярно валидируются»).

### 10.4 Quick prompts на Home — «вечнозелёные» формулировки

Принцип: ни один prompt не должен ссылаться на конкретную дату или конкретное событие — иначе через неделю он становится бессмысленным («майские» в июне). Формулировки общие, чтобы пользователь мог нажать в любой день и получить осмысленный ответ.

```
1. «Какой район показал лучший RevPAR за последние 30 дней?»
   → get_revenue_metrics + ранжирование внутри ответа
2. «Топ-5 событий с наибольшим положительным влиянием на спрос»
   → get_top_events_by_impact(min_impact=0, n=5)
3. «Сравни два самых загруженных района по RMS-метрикам»
   → compare_districts (агент сам определяет два по occupancy)
4. «Темп бронирований за последние 14 дней — ускоряется или замедляется?»
   → get_booking_pace + summary trend
```

Эти промпты остаются актуальны постоянно — не привязаны к майским / ноябрьским / летним.

## 19. Решения по open questions (закрыты 2026-05-04)

1. **Yandex Maps API ключ** — получен от пользователя, добавлен в `frontend/.env` (gitignored, проверено `git check-ignore`). В коде используется через `import.meta.env.VITE_YANDEX_MAPS_API_KEY`. Placeholder-вариант лежит в `frontend/.env.example`. Fallback на Leaflet+ESRI не потребуется.

2. **Аудит #5 моделей UML** — выполнен «before-rebuild» (см. §16.1). После Фазы 4 повторим тем же агентом для сравнения «before/after» — это даст защите дополнительный аргумент об эволюции модели системы.

3. **Alembic vs `create_all`** — выбрано `create_all` + одноразовый `ALTER`-скрипт `backend/scripts/migrate_event_schema_v2.py`. Идемпотентный. Alembic фиксируется в отчёте ВКР как «направление развития» (соответствует NORTH_STAR §6).

4. **Quick-prompts на Home** — переформулированы как «вечнозелёные» (см. §10.4). Не привязаны ни к датам, ни к конкретным событиям — актуальны в любой день года.

5. **Сегментный benchmark** — закреплён вариант **«район × размерная категория»** (mini ≤15 / mid 16-50 / large 51+). Звёздность не используется (в схеме Hotel её нет — проверено в `backend/app/db/models.py`). Опционально — вторичный фильтр по `accommodation_type` (после проверки распределения значений в данных). Подробности в §13.2.1.
