# Обоснование выбора технологий

## Выбор библиотеки прогнозирования временных рядов

При разработке подсистемы прогнозирования загруженности гостиниц рассматривались три основных решения: Prophet (Meta), StatsForecast (Nixtla) и Chronos (Amazon).

**Prophet** представляет собой библиотеку для прогнозирования временных рядов, разработанную компанией Meta. Ключевым преимуществом является встроенная поддержка учёта праздников и событий через параметр `holidays`. Это критически важно для задачи прогнозирования туристической активности, поскольку загруженность отелей напрямую зависит от проведения мероприятий и праздничных дней.

**StatsForecast** — библиотека от Nixtla, реализующая классические статистические модели (AutoARIMA, ETS, Theta). Её преимущество — высокая скорость обучения, в 10-100 раз превышающая Prophet. Однако встроенной поддержки событий не предусмотрено, что требует дополнительной инженерной работы.

**Chronos-2** — foundation-модель от Amazon для прогнозирования временных рядов методом zero-shot. Требует GPU для эффективной работы, что выходит за рамки бюджета проекта.

Для объективного сравнения использованы результаты бенчмарков на стандартных датасетах:

| Библиотека | Benchmark Score | Требования к GPU |
|------------|-----------------|------------------|
| Prophet | 85.9 | Не требуется |
| StatsForecast | 82.6 | Не требуется |
| Chronos-2 | 69.9 | Требуется |

На основании проведённого анализа выбран **Prophet** по следующим причинам:
- наивысший показатель точности среди рассмотренных решений (85.9);
- встроенная поддержка праздников и событий, что соответствует специфике задачи;
- активная поддержка сообществом и обширная документация;
- отсутствие требований к специализированному оборудованию.

## Выбор модели эмбеддингов для RAG-системы

Для реализации системы Retrieval-Augmented Generation (RAG) необходима модель преобразования текста в векторные представления. Специфика проекта — работа с русскоязычными текстами (описания событий, запросы пользователей, аналитические отчёты).

Рассмотрены следующие модели:

**GigaChatEmbeddings** — модель эмбеддингов от Сбера, специально оптимизированная для русского языка. Доступна через API GigaChat. Стоимость использования невысока.

**multilingual-e5-large** — мультиязычная модель от Microsoft, поддерживающая 100+ языков. Показывает хорошие результаты на русском языке, однако уступает специализированным моделям.

**bge-m3** — модель от Beijing Academy of AI, также мультиязычная. Сопоставима по качеству с multilingual-e5.

Выбор сделан в пользу **GigaChatEmbeddings** по следующим основаниям:
- модель изначально обучена на русскоязычных текстах, что обеспечивает лучшее качество эмбеддингов для данной задачи;
- интеграция через единый API Сбера упрощает архитектуру системы;
- стоимость использования приемлема для прототипа.

## Выбор языковой модели для интеллектуального агента

Для генерации ответов на запросы пользователей необходима большая языковая модель (LLM), способная работать с русским языком и доступная через API.

Рассматривались варианты:

**Mistral Large (Mistral AI)** — основной LLM в системе: до 1 млрд токенов/мес на бесплатном тарифе, работа из РФ без VPN, нативный tool calling для LangGraph.

**GigaChat (Сбер)** — сильное качество на русском; для проекта используется прежде всего как провайдер эмбеддингов (RAG); как основной чат-LLM ограничен стоимостью тарифов.

**OpenRouter и MiMo-V2-Flash** — рассматривались на ранних этапах как универсальный шлюз и быстрые модели; не выбраны основными из‑за лимитов и приоритета Mistral Large.

**Локальные модели** — развёртывание open-source моделей на собственном оборудовании отклонено из‑за требований к ресурсам.

В ходе разработки проверены провайдеры: Mistral AI (mistral-large-latest), Groq, GigaChat (Pro/Max), OpenRouter. **Mistral Large** закреплён как основной LLM по причинам:
- лучший баланс качества и доступного объёма (1B токенов/мес);
- нативная поддержка tool calling для LangGraph агента;
- устойчивое понимание русского языка.

GigaChat и Groq остаются в мультипровайдерной схеме как резервные варианты в `.env`.

## Выбор фреймворка для AI-агента: LangGraph

При проектировании интеллектуального агента рассматривалось два подхода:
1. Прямые вызовы API (простой RAG pipeline)
2. LangGraph — фреймворк для построения stateful multi-step агентов

Выбран **LangGraph** (из экосистемы LangChain), поскольку система требует:
- **Многошаговую обработку**: сбор данных → запуск моделей → анализ факторов → генерация объяснения
- **Conditional routing**: прогноз vs аналитика (Command pattern)
- **Структурированный вывод**: PydanticOutputParser для ForecastExplanation
- **Tool calling**: 5 инструментов в `main_agent.py` (search_hotels, search_events, get_weather, forecast_occupancy, get_statistics)

В системе реализовано два LangGraph-агента:
- **MainAgent** — общий аналитический агент с StateGraph и Command[Literal[...]] для маршрутизации
- **ForecastAgent** — специализированный агент прогнозирования с линейным пайплайном (4 узла)

При этом для простого RAG-поиска по-прежнему используются прямые вызовы ChromaDB без абстракций LangChain — избыточная обёртка не добавляет ценности для этого слоя.

# Расчёт сроков проекта

## Применение метода PERT

Для оценки сроков реализации проекта применён метод PERT (Program Evaluation and Review Technique). Метод предполагает использование трёх оценок длительности каждого этапа работ:
- O (optimistic) — оптимистичная оценка при благоприятных условиях;
- M (most likely) — наиболее вероятная оценка;
- P (pessimistic) — пессимистичная оценка при возникновении затруднений.

Ожидаемое время выполнения рассчитывается по формуле:

**T = (O + 4M + P) / 6**

Стандартное отклонение:

**σ = (P − O) / 6**

Результаты PERT-анализа представлены в таблице (значения в рабочих днях):

| Этап | O | M | P | T | σ |
|------|---|---|---|---|---|
| Проектирование | 3 | 5 | 10 | 5,5 | 1,2 |
| Подсистема сбора данных | 5 | 8 | 14 | 8,5 | 1,5 |
| Модуль аналитики | 4 | 6 | 12 | 6,7 | 1,3 |
| Подсистема событий | 4 | 6 | 12 | 6,7 | 1,3 |
| Модуль прогнозирования | 5 | 8 | 14 | 8,5 | 1,5 |
| Интеллектуальный агент | 7 | 10 | 18 | 10,8 | 1,8 |
| REST API | 3 | 5 | 10 | 5,5 | 1,2 |
| Веб-интерфейс | 7 | 10 | 16 | 10,5 | 1,5 |
| Тестирование | 5 | 8 | 14 | 8,5 | 1,5 |
| Документирование | 3 | 4 | 8 | 4,5 | 0,8 |
| **Итого** | 46 | 70 | 128 | **75,7** | — |

Суммарное стандартное отклонение проекта:

σ_общ = √(Σσᵢ²) = √19,14 ≈ 4,4 дня

Таким образом, ожидаемая длительность проекта составляет **76 рабочих дней** (приблизительно 3,8 месяца) с доверительным интервалом 95%: от 67 до 85 рабочих дней.

## Проверка по формуле Боэма

Для верификации полученной оценки применена эмпирическая формула Барри Боэма:

**T = 2,5 × N^(1/3)**

где N — трудоёмкость в человеко-месяцах.

При общей трудоёмкости 550 человеко-часов и норме 160 часов в месяц:

N = 550 / 160 = 3,44 чел.-мес.

T = 2,5 × (3,44)^(1/3) = 2,5 × 1,51 = 3,78 месяца

Результаты двух методов согласуются, что подтверждает корректность оценки. Принятый срок реализации проекта — **4 месяца**.

## Оценка трудозатрат методом PERT

Для оценки трудозатрат применён метод PERT (Program Evaluation and Review Technique), предложенный в 1958 году при разработке проекта «Поларис».

Метод использует три оценки длительности каждого пакета работ:
- O (optimistic) — оптимистичная оценка, при которой риски не реализуются;
- M (most likely) — наиболее вероятная оценка;
- P (pessimistic) — пессимистичная оценка при реализации рисков.

Ожидаемое время рассчитывается по формуле:

**E = (O + 4M + P) / 6**

Стандартное отклонение:

**σ = (P − O) / 6**

Суммарное стандартное отклонение проекта:

**σ_общ = √(Σσᵢ²)**

Оценка с вероятностью 95%:

**E₉₅% = E + 2σ**

Результаты PERT-анализа для проекта:
- Ожидаемая длительность: 76 рабочих дней.
- Стандартное отклонение: ±4,4 дня.
- Диапазон с вероятностью 95%: от 67 до 85 рабочих дней.

Полученные оценки согласуются с результатами расчёта по формуле Боэма, что подтверждает корректность оценок.

# Модель предметной области (IDEF1X)

## Обоснование выбора методологии

Для моделирования структуры данных информационной системы выбрана методология IDEF1X (Integration Definition for Information Modeling). Методология является федеральным стандартом США и широко применяется для проектирования реляционных баз данных.

IDEF1X позволяет наглядно отобразить:
- сущности предметной области и их атрибуты;
- связи между сущностями;
- зависимости данных (идентифицирующие и неидентифицирующие отношения).

## Перечень сущностей системы

Модель включает 9 сущностей, разделённых на три категории:

**Существующие сущности** (из курсовой работы):
1. Средство размещения (af_all_2024) - справочник гостиниц, отелей, хостелов
2. Номер (rooms_data) - информация о номерах
3. Статистика загруженности (hotels_statistics) - ежедневные данные о занятости

**Справочники**:
4. Район (districts) - справочник районов Иркутской области
5. Источник данных (data_sources) - справочник источников (101Hotels, irk.ru, culture38.ru)

**Новые сущности** (для дипломной работы):
6. Событие (events) - туристические мероприятия региона
7. Прогноз (forecasts) - результаты прогнозирования загруженности
8. Запрос пользователя (user_queries) - запросы к ИИ-агенту
9. Ответ агента (agent_responses) - сгенерированные ответы

## Типы связей в модели

В IDEF1X различают два типа связей:

**Идентифицирующая связь** - внешний ключ дочерней сущности входит в состав её первичного ключа. Дочерняя сущность не может существовать без родительской. На диаграмме изображается сплошной линией, дочерняя сущность имеет скруглённые углы.

**Неидентифицирующая связь** - внешний ключ является обычным атрибутом дочерней сущности, не входящим в первичный ключ. На диаграмме изображается пунктирной линией.

В разработанной модели присутствуют оба типа связей:

| Родитель | Потомок | Тип связи | Обоснование |
|----------|---------|-----------|-------------|
| Средство размещения | Номер | Идентифицирующая | hotel_id входит в составной PK (id, hotel_id, date) |
| Средство размещения | Статистика | Идентифицирующая | id входит в составной PK (id, date) |
| Средство размещения | Прогноз | Идентифицирующая | id входит в составной PK (id, forecast_date) |
| Запрос пользователя | Ответ агента | Идентифицирующая | query_id является PK ответа |
| Район | Средство размещения | Неидентифицирующая | district_id - атрибут, не часть PK |
| Источник данных | Средство размещения | Неидентифицирующая | source_id - атрибут, не часть PK |
| Источник данных | Событие | Неидентифицирующая | source_id - атрибут, не часть PK |

Такой смешанный подход точно отражает реальные зависимости данных: временные ряды статистики и прогнозов неразрывно связаны с конкретным средством размещения, тогда как привязка к району или источнику носит справочный характер.

## Мощность связей

Для обозначения мощности связей используются стандартные символы IDEF1X:
- точка (●) у дочерней сущности означает «много» (1:N);
- символ Z означает «ноль или один» (0..1).

Все связи в модели имеют мощность 1:N, за исключением связи Запрос-Ответ (1:1).

# Модель алгоритма (IDEF3)

## Назначение методологии

Методология IDEF3 предназначена для описания динамических аспектов системы - последовательности выполнения процессов и логики их взаимодействия. В отличие от IDEF0, которая отображает функциональную структуру, IDEF3 позволяет моделировать поведение системы во времени.

## Основные элементы модели

**Единица работ (UOW)** - центральный элемент диаграммы, представляющий отдельный процесс или действие. Изображается прямоугольником с уникальным номером и именем в виде отглагольного существительного.

**Связи** определяют последовательность выполнения работ:
- сплошная стрелка обозначает временное предшествование - работа-источник должна завершиться до начала работы-цели;
- пунктирная линия связывает работы с объектами ссылок.

**Перекрёстки** управляют разветвлением и слиянием потоков:
- символ & обозначает логику «И» - все входящие процессы должны завершиться, все исходящие запускаются;
- символ X обозначает исключающее «ИЛИ» - выполняется только один из альтернативных путей.

**Объекты ссылок** служат для документирования дополнительной информации: объектов данных (OBJECT), уточнений (ELAB), примечаний (NOTE).

## Структура модели: два сценария

Разработанная модель состоит из двух сценариев, отражающих реальную архитектуру системы.

### Сценарий 1: Фоновый сбор данных (работы 1.1.2–1.1.10)

Выполняется автоматически по расписанию (APScheduler: события — каждые 6 часов, отели — 2 часа, погода — 3 часа, Telegram — 1 час). Обеспечивает актуальность данных в хранилище.

| Номер | Имя работы | Описание |
|-------|------------|----------|
| 1.1.2 | Запуск сбора данных | Инициализация через APScheduler |
| 1.1.3 | Сбор данных о событиях | asyncio.gather: 8 парсеров событий (irk, culture38, zeroevent, kassir, telegram, yandex, culture_rf, major) |
| 1.1.4 | Сбор данных о размещении | 101Hotels API (региональный) + Xotelo API (cross-reference) |
| 1.1.5 | Сбор данных о погоде | Open-Meteo API (прогноз + исторические) |
| 1.1.6 | Нормализация и валидация | Очистка, проверка, дедупликация по ID |
| 1.1.7 | Логирование ошибки | HealthMonitor, статистика парсеров |
| 1.1.8 | Сохранение в PostgreSQL | Batch insert в таблицы events, hotels, hotel_statistics |
| 1.1.9 | Индексация в Chroma | GigaChatEmbeddings → ChromaDB |
| 1.1.10 | Завершение сбора | Финальная работа, статистика |

### Сценарий 2: Обработка запроса пользователя (работы 1.2.10–1.2.18)

Выполняется интерактивно при обращении пользователя через веб-интерфейс.

| Номер | Имя работы | Описание |
|-------|------------|----------|
| 1.2.10 | Получение запроса | Пользователь вводит вопрос |
| 1.2.11 | Поиск контекста в Chroma | RAG: поиск релевантных документов |
| 1.2.12 | Определение типа запроса | Агент классифицирует: прогноз или аналитика |
| 1.2.13 | Ensemble прогнозирование | Prophet + NeuralProphet + XGBoost + LightGBM → weighted average |
| 1.2.14 | Аналитика исторических данных | Выборка данных для запросов о прошлом |
| 1.2.15 | Генерация ответа (LLM) | Формирование текстового ответа |
| 1.2.16 | Визуализация результатов | Отображение графиков в React |
| 1.2.17 | Сохранение в историю | Запись в user_queries, agent_responses |
| 1.2.18 | Завершение обработки | Финальная работа, завершающая процесс |

**Примечание:** Нумерация сквозная по всей модели — все номера работ уникальны.

## Логика перекрёстков

### Сценарий 1

**J1 (разветвление &)** — после запуска параллельно инициируются сбор событий и сбор данных о размещении.

**J2 (слияние &)** — ожидание завершения обоих процессов сбора.

**J3 (разветвление X)** — исключающее ИЛИ: данные валидны → Нормализация; ошибка источника → Логирование.

**J4 (слияние X)** — после нормализации или логирования ошибки продолжается сохранение.

### Сценарий 2

**J5 (разветвление X)** — исключающее ИЛИ: запрос о будущем → Прогнозирование; о прошлом → Аналитика.

**J6 (слияние X)** — результат прогноза или аналитики передаётся на генерацию ответа.

**J7 (разветвление &)** — параллельно выполняются визуализация и сохранение в историю.

**J8 (слияние &)** — ожидание завершения визуализации и сохранения перед завершением обработки.

## Взаимосвязь сценариев

Сценарий 1 подготавливает данные, которые использует Сценарий 2. При прогнозировании Ensemble (в т.ч. Prophet и NeuralProphet) берёт исторические данные загруженности из PostgreSQL и учитывает события и регрессоры, что позволяет прогнозировать влияние мероприятий на туристический поток.

# Диаграмма бизнес-процессов (Erikson-Penker)

## Назначение диаграммы

Для наглядного представления бизнес-процессов системы используется нотация Erikson-Penker - расширение UML для моделирования бизнес-логики. Данная нотация применяется в инструментах Enterprise Architect и позволяет отразить не только последовательность действий, но и ресурсы, цели и результаты каждого процесса.

## Элементы нотации

Диаграмма использует пять типов элементов, каждый со своей семантикой:

**«event»** - событие, инициирующее процесс. Отображается параллелограммом, направленным к процессу. Примеры: запрос пользователя, срабатывание планировщика.

**«information»** - входная информация, необходимая для выполнения процесса. Отображается прямоугольником снизу. Примеры: данные о средствах размещения, запрос пользователя.

**«resource»** - ресурсы, используемые процессом: программное обеспечение, оборудование, базы данных. Отображается прямоугольником сверху. Примеры: PostgreSQL, AI-агент, Ensemble.

**«goal»** - цель процесса. Отображается прямоугольником справа сверху. Примеры: обеспечение актуальности данных, качественный анализ.

**«output»** - результат выполнения процесса. Отображается прямоугольником справа. Примеры: аналитический ответ, прогноз загрузки.

## Контекстная диаграмма

Контекстная диаграмма представляет систему как единый процесс, взаимодействующий с внешней средой.

**Центральный процесс:** Информационно-аналитическая поддержка туризма Прибайкалья

| Категория | Элементы |
|-----------|----------|
| «event» | Запрос пользователя на анализ туризма |
| «information» | Данные о средствах размещения, события региона, исторические данные загрузки |
| «resource» | PostgreSQL, AI-агент (Mistral Large + RAG), Ensemble, веб-интерфейс (React + Recharts + ECharts) |
| «goal» | Обеспечение качественного анализа и прогнозирования туристической сферы региона |
| «output» | Аналитический ответ AI-агента, прогноз загрузки средств размещения |

## Декомпозиция на три процесса

При декомпозиции центральный процесс разбивается на три взаимосвязанных процесса.

### Процесс 1: Сбор и обновление данных о туризме

Выполняется автоматически по расписанию, обеспечивает актуальность информационной базы системы.

| Категория | Элементы |
|-----------|----------|
| «event» | Срабатывание планировщика |
| «information» | Метаданные, внешние API |
| «resource» | PostgreSQL |
| «goal» | Актуальные данные о средствах размещения и событиях |
| «output» | Обновлённые данные в PostgreSQL |

### Процесс 2: Взаимодействие с пользователем

Обеспечивает приём запросов и отображение результатов через веб-интерфейс.

| Категория | Элементы |
|-----------|----------|
| «event» | Пользователь вводит запрос |
| «information» | Запрос пользователя |
| «resource» | Веб-интерфейс, FastAPI |
| «goal» | Удобный ввод и получение ответа |
| «output» | Структурированный запрос |

### Процесс 3: Анализ данных и формирование ответа

Ядро интеллектуальной обработки: поиск релевантной информации, прогнозирование, генерация ответа.

| Категория | Элементы |
|-----------|----------|
| «event» | Поступление запроса |
| «information» | Данные PostgreSQL, аналитические данные |
| «resource» | AI-агент (Mistral Large), Chroma (RAG), Ensemble |
| «goal» | Качественный анализ и точный прогноз |
| «output» | Ответ AI-агента, прогноз загрузки |

## Связи между процессами

- Выход Процесса 1 (обновлённые данные в PostgreSQL) используется Процессом 3 как источник информации
- Выход Процесса 2 (структурированный запрос) инициирует выполнение Процесса 3
- Выход Процесса 3 возвращается пользователю через интерфейс

# Диаграмма функциональных требований

## Классификация требований

Для систематизации требований к системе использована классификация Карла Вигерса, выделяющая несколько уровней абстракции:

**Бизнес-требования** определяют высокоуровневые цели организации. Для данного проекта бизнес-требование формулируется как обеспечение информационно-аналитической поддержки туристической отрасли Иркутской области.

Требования к подсистеме сбора и представления информации о мероприятиях.

- FR2.4. Просмотр календаря событий

Требования к пользовательскому интерфейсу и формам взаимодействия.

Требования к связующим компонентам архитектуры.

## Связь требований с другими моделями

Требования групп FR1 и FR2 реализуются в первом сценарии IDEF3 (фоновый сбор данных). Требования групп FR3 и FR4 соответствуют второму сценарию IDEF3 (обработка запроса пользователя). Группа FR5 обеспечивает интеграцию всех компонентов системы.

# Диаграмма вариантов использования (Use Case)

## Назначение диаграммы

Диаграмма вариантов использования описывает функциональное назначение системы с точки зрения внешних пользователей. Каждый вариант использования определяет последовательность действий, выполняемых системой при взаимодействии с соответствующим актёром.

## Актёры системы

**Пользователь** - основной актёр, представляющий туриста, аналитика туристической отрасли или представителя средства размещения. Взаимодействует с системой через единый веб-интерфейс чата с AI-агентом.

**Администратор** - технический специалист. Наследует все возможности Пользователя (отношение обобщения) и дополнительно имеет доступ к управлению источниками данных и логам.

**Планировщик** - автоматический актёр, реализованный через APScheduler (AsyncIOScheduler). Запускает процесс сбора данных по расписанию (события — 6ч, отели — 2ч, погода — 3ч, Telegram — 1ч) без участия человека. Интегрирован в lifespan FastAPI.

## Варианты использования

Модель содержит 7 основных вариантов использования.

Для Пользователя:
- UC1 "Построить прогноз загруженности" - центральный вариант использования системы
- UC2 "Просмотреть справочник размещения" - справочная информация
- UC3 "Просмотреть календарь событий" - информация о мероприятиях
- UC4 "Просмотреть историю запросов" - история диалогов

Для Администратора:
- UC5 "Настроить источники данных"
- UC6 "Просмотреть логи системы"

Для Планировщика:
- UC7 "Выполнить сбор данных" - автоматический процесс

## Отношения между вариантами

**Включение (include)** применяется для обязательных подпроцессов. UC1 обязательно включает поиск контекста в RAG и генерацию ответа LLM. UC7 включает сохранение в PostgreSQL и обновление индекса Chroma.

**Расширение (extend)** применяется для условного поведения. Построение прогноза Ensemble расширяет UC1 при условии, что запрос связан с будущим периодом. Фильтрация расширяет просмотр справочников.

**Обобщение** связывает актёров: Администратор наследует возможности Пользователя.

## Структура диаграммы

Диаграмма выполнена в файле `use_case_model.drawio` и содержит 7 страниц:

## Структура описания сценария

Каждый вариант использования описан по шаблону:
- **Краткое описание** - суть варианта использования
- **Актёры** - кто инициирует
- **Предусловия** - что должно быть выполнено до начала
- **Постусловия** - результат выполнения
- **Главная последовательность** - пошаговое описание действий актёра и ответов системы
- **Альтернативные последовательности** - обработка исключений и особых случаев

Пример главной последовательности UC1 "Построить прогноз загруженности":

1. Пользователь открывает веб-интерфейс системы
2. Пользователь вводит вопрос в текстовое поле
3. Пользователь нажимает кнопку отправки
4. Система выполняет поиск релевантного контекста в Chroma (include: RAG)
5. Система формирует промпт с контекстом и отправляет в LLM (include: Генерация ответа)
6. Система отображает ответ в окне чата
7. Система сохраняет запрос и ответ в базу данных (include: Сохранить в историю)

Альтернативная последовательность 4a: если запрос содержит вопрос о будущем периоде, выполняется extend "Построить прогноз" - система вызывает Ensemble и включает данные прогноза в контекст

Полные сценарии всех 7 UC приведены в UC_SCENARIOS.md

# Диаграмма предметной области (Domain Model)

## Назначение диаграммы

Диаграмма предметной области описывает основные понятия реального мира, связанные с разрабатываемой системой. Построение модели начинается с выявления абстракций, существующих в реальном мире.

Объекты предметной области выявлены на основе анализа сценариев вариантов использования. Существительные и именные группы из сценариев становятся объектами, глаголы и глагольные группы становятся ассоциациями.

## Объекты предметной области

В модели выявлено 17 объектов, сгруппированных по функциональным областям:

**Взаимодействие с пользователем:**
- Пользователь - турист, аналитик, представитель туриндустрии
- Администратор - технический специалист (наследует Пользователя)
- Запрос - текстовый вопрос к системе
- Ответ - текстовый ответ системы
- История запросов - хранилище предыдущих диалогов

**Интеллектуальная обработка:**
- AI-агент - компонент обработки запросов
- Прогноз - предсказание загруженности

**Данные о размещении:**
- Средство размещения - гостиница, отель, хостел
- Тип размещения - классификация объектов
- Район - территориальная принадлежность
- Номерной фонд - комнаты и номера

**Данные о событиях:**
- Событие - мероприятие региона
- Тип события - классификация мероприятий
- Календарь - отображение событий по датам

**Системные объекты:**
- Источник данных - внешний ресурс
- Лог системы - журнал работы
- Планировщик - автоматический запуск задач

## Отношения между объектами

Основные типы отношений в модели:

**Ассоциация** - связь между объектами. Пример: Пользователь создаёт Запрос, AI-агент формирует Ответ.

**Агрегация** - отношение часть-целое. Пример: Средство размещения содержит Номерной фонд, История запросов содержит Запрос.

**Обобщение** - наследование. Администратор является специализацией Пользователя и наследует его возможности.

# Диаграмма деятельности (Activity Diagram)

## Назначение диаграммы

Диаграмма деятельности представляет собой частный случай диаграммы состояний и предназначена для описания последовательности действий, реализующих бизнес-процесс или алгоритм. Переходы на диаграмме инициируются завершением предыдущего действия, а не внешними событиями.

Для каждого бизнес-процесса, выявленного на диаграмме Erikson-Penker, построена отдельная диаграмма деятельности с использованием дорожек (swimlanes).

## Основные элементы

**Initial** - начальное состояние, изображается закрашенным кругом. Каждая диаграмма имеет единственное начальное состояние.

**Activity** - деятельность, изображается прямоугольником с закруглёнными углами. Именуется глаголом с пояснительными словами: "Запустить сбор", "Сформировать эмбеддинг".

**Decision** - точка ветвления, изображается ромбом. Условие указывается над ромбом или рядом с ним, выходящие переходы маркируются сторожевыми условиями в квадратных скобках: [да], [нет].

**Fork/Join** - линия синхронизации, изображается толстой горизонтальной линией. Fork разделяет поток на параллельные ветви, Join объединяет их. После Join выполнение продолжается только после завершения всех входящих ветвей.

**Partition (дорожка)** - вертикальная полоса, группирующая действия по ответственным элементам. Название элемента указывается в верхней части дорожки. Пересекать линию дорожки могут только переходы.

**Final** - конечное состояние, изображается кругом с точкой внутри. Каждая диаграмма имеет единственное конечное состояние.

## БП1: Сбор и обновление данных о туризме

Диаграмма описывает фоновый процесс сбора данных, запускаемый планировщиком.

**Дорожки:** Планировщик (APScheduler), Парсер, PostgreSQL, Chroma

**Последовательность действий:**
1. Запустить сбор по расписанию (Планировщик)
2. Fork: параллельный парсинг данных
   - Парсить данные о средствах размещения (Парсер)
   - Парсить данные о событиях (Парсер)
3. Join: объединение потоков после завершения парсинга
4. Decision: Данные валидны?
   - [нет] Логировать ошибку → к завершению
   - [да] Сохранить данные в таблицы (PostgreSQL)
5. Сформировать эмбеддинги (Chroma)
6. Обновить индекс (Chroma)
7. Записать лог успешного сбора (Планировщик)

Диаграмма отражает архитектурное решение о параллельном сборе данных из разных источников с последующим объединением и валидацией.

## БП2: Взаимодействие с пользователем

Диаграмма описывает интерактивный процесс приёма запроса от пользователя.

**Дорожки:** Пользователь, Веб-интерфейс, FastAPI

**Последовательность действий:**
1. Открыть главную страницу (Пользователь)
2. Отобразить форму чата (Веб-интерфейс)
3. Ввести вопрос на естественном языке (Пользователь)
4. Нажать кнопку Отправить (Пользователь)
5. Отправить запрос на API (Веб-интерфейс)
6. Принять запрос и валидировать (FastAPI)
7. Decision: Запрос валиден?
   - [нет] Вернуть ошибку 400 → Отобразить ошибку → к завершению
   - [да] Передать запрос AI-агенту
8. Прочитать ответ (Пользователь)

Данная диаграмма чётко разграничивает ответственность: Пользователь инициирует взаимодействие, Веб-интерфейс отвечает за отображение, FastAPI - за валидацию и маршрутизацию.

## БП3: Анализ данных и формирование ответа

Диаграмма описывает интеллектуальную обработку запроса.

**Дорожки:** FastAPI, AI-агент, RAG (Chroma), Ensemble, PostgreSQL

**Последовательность действий:**
1. Принять запрос от пользователя (FastAPI)
2. Анализировать текст запроса (AI-агент)
3. Decision: Запрос о будущем?
   - [нет] Сформировать эмбеддинг запроса (RAG) → Найти релевантные документы (RAG)
   - [да] Загрузить исторические данные (PostgreSQL) → Построить прогноз загруженности (Ensemble) → Учесть календарь событий и регрессоры
4. Join: объединение контекста (RAG) и прогноза (Ensemble)
5. Сформировать промпт с контекстом (AI-агент)
6. Сгенерировать ответ LLM (AI-агент)
7. Сохранить запрос и ответ (PostgreSQL)
8. Вернуть ответ пользователю (FastAPI)

Диаграмма демонстрирует ключевое архитектурное решение: тип запроса определяет путь обработки. Вопросы о будущем направляются к Ensemble, вопросы о текущем состоянии — к RAG. Результаты объединяются для формирования итогового ответа.

## Связь с другими моделями

Диаграммы деятельности детализируют бизнес-процессы, выявленные на диаграмме Erikson-Penker:
- БП1 соответствует сценарию IDEF3 "Фоновый сбор данных" (1.1.X)
- БП2 и БП3 соответствуют сценарию IDEF3 "Обработка запроса пользователя" (1.2.X)

Control-объекты диаграмм анализа пригодности реализованы как Activities в соответствующих дорожках.

# Диаграмма последовательности

## Назначение

Диаграмма последовательности (Sequence Diagram) представляет графическую модель, отображающую взаимодействие объектов системы во времени. Для каждого сценария варианта использования диаграмма показывает участников, порядок передачи сообщений и временную последовательность событий.

Отличительная особенность данного типа диаграмм - наличие времени как самостоятельного измерения. Вертикальная ось отображает ход времени сверху вниз, горизонтальная - расположение взаимодействующих объектов.

## Элементы диаграммы

Каждая диаграмма включает следующие элементы:

**Объект (Lifeline)** - участник взаимодействия, изображается прямоугольником с подчёркнутым именем в формате ":ИмяКласса". От прямоугольника вниз идёт пунктирная линия жизни.

**Сообщение (Message)** - передача информации между объектами. Вызов операции обозначается сплошной стрелкой с закрашенным наконечником, возврат результата - пунктирной стрелкой.

**Условие (Guard)** - сторожевое условие в квадратных скобках [условие], определяющее выполнение альтернативных ветвей.

**Рамка (Frame)** - граница диаграммы с именем в формате "sd [Название сценария]".

## Диаграммы по Use Case

Для системы разработано 7 диаграмм последовательности, соответствующих выявленным вариантам использования.

### UC1. Построить прогноз загруженности

Наиболее комплексная диаграмма системы. Участники: Пользователь, ГлавнаяСтраница, ФормаВвода, FastAPI, AIАгент, Chroma, Ensemble, LLM (Mistral Large), PostgreSQL, ОбластьОтвета, График.

Последовательность включает открытие страницы, ввод вопроса, передачу запроса через API к AI-агенту. Агент выполняет поиск контекста в Chroma. При обнаружении вопроса о будущем [запросОБудущем] вызывается Ensemble для построения прогноза. Контекст и прогноз передаются LLM для генерации ответа. Результат сохраняется в PostgreSQL и отображается пользователю.

### UC2-UC4. Информационные сценарии

Диаграммы просмотра справочников (UC2 - размещение, UC3 - события, UC4 - история) имеют схожую структуру: открытие страницы, загрузка данных из PostgreSQL, применение фильтров, отображение деталей выбранного элемента.

### UC5-UC6. Административные сценарии

Диаграммы настройки источников (UC5) и просмотра логов (UC6) предназначены для актёра Администратор. Включают загрузку данных, редактирование параметров, проверку доступности источников, экспорт логов.

### UC7. Фоновый сбор данных

Диаграмма описывает взаимодействие системных компонентов без участия пользователя. APScheduler инициирует Парсер, который запрашивает данные из внешних источников (101Hotels, irk.ru), сохраняет их в PostgreSQL и формирует эмбеддинги для индексации в Chroma.

## Связь с другими моделями

Диаграммы последовательности являются детализацией диаграмм анализа пригодности. Boundary-объекты становятся участниками (Lifeline), Control-объекты трансформируются в сообщения-операции, Entity-объекты представлены как участники с данными.

# Диаграмма анализа пригодности (Robustness Diagram)

## Назначение диаграммы

Диаграмма анализа пригодности представляет собой промежуточный этап между диаграммой вариантов использования и диаграммой последовательности. Методология предполагает анализ каждого сценария Use Case с целью выявления трёх типов объектов: граничных (boundary), управляющих (control) и сущностных (entity).

## Типы объектов

**Boundary (граничный объект)** — элемент интерфейса, через который актёр взаимодействует с системой. Изображается кругом с вертикальной линией слева. Примеры: форма ввода, кнопка, страница, API-эндпоинт.

**Control (управляющий объект)** — логика обработки, координирующая взаимодействие между boundary и entity. Изображается кругом со стрелкой. Примеры: обработчик запроса, валидатор, менеджер сессий.

**Entity (сущностный объект)** — данные предметной области, хранимые в системе. Изображается кругом с горизонтальной линией снизу. Примеры: запись в базе данных, документ, бизнес-объект.

## Правила связей

Методология устанавливает ограничения на допустимые связи между объектами:

| Источник | Может связываться с |
|----------|---------------------|
| Актёр | Только Boundary |
| Boundary | Только Control |
| Control | Boundary, Entity, другие Control |
| Entity | Только Control |

Прямая связь Boundary → Entity запрещена. Это обеспечивает разделение представления и данных через слой логики.

## Структура модели

Для системы разработано 7 диаграмм анализа пригодности, соответствующих вариантам использования:

### UC1. Построить прогноз загруженности

| Тип | Объекты |
|-----|---------|
| Boundary | ГлавнаяСтраница, ФормаВвода, ОбластьОтвета, График |
| Control | Обработать запрос, Найти контекст, Построить прогноз, Сформировать ответ, Сохранить |
| Entity | Запрос, Ответ, Контекст, Прогноз |

### UC2-UC4. Информационные сценарии

Диаграммы просмотра справочников имеют схожую структуру: страница со списком (Boundary), контроллер загрузки (Control), данные из PostgreSQL (Entity).

### UC5-UC6. Административные сценарии

Включают формы настроек (Boundary), валидаторы и обработчики (Control), конфигурации и логи (Entity).

### UC7. Сбор данных

| Тип | Объекты |
|-----|---------|
| Boundary | Планировщик, 101HotelsAPI, irk.ru, culture38.ru |
| Control | ПарсерОтелей, ПарсерСобытий, Нормализатор, Индексатор |
| Entity | СредствоРазмещения, Событие, Эмбеддинг |

## Связь с другими моделями

Объекты диаграмм анализа пригодности трансформируются в элементы последующих диаграмм:
- Boundary → Lifeline на диаграмме последовательности
- Control → Операции и методы в диаграмме классов
- Entity → Классы со стереотипом «entity»

# Диаграмма пользовательского интерфейса

## Назначение диаграммы

Диаграмма пользовательского интерфейса описывает структуру экранов системы и элементов управления. Применяется нотация UML с использованием стереотипов «web page» и «control».

## Элементы диаграммы

**«web page»** — веб-страница как контейнер элементов. Изображается прямоугольником со стереотипом.

**«control»** — элемент управления: кнопка, поле ввода, таблица, список. Изображается прямоугольником внутри страницы.

**Вложенность (⊕)** — символ агрегации, показывающий принадлежность элемента странице.

Система включает **8 основных экранов**: Home, Chat, Analytics, Events, Map, Forecast, HotelDetail, About. Визуализация: **Recharts** и **ECharts** (встроенные в React; GeoMap на Map), без отдельного BI (DataLens).

# Диаграмма классов

## Назначение диаграммы

Диаграмма классов описывает статическую структуру системы: классы, их атрибуты, операции и отношения. Для каждого бизнес-процесса построена отдельная диаграмма с использованием стереотипов, отражающих роль класса в архитектуре.

## Стереотипы классов

**«boundary»** — классы пользовательского интерфейса и внешних интерфейсов. Отвечают за взаимодействие с внешним миром.

**«control»** — классы бизнес-логики. Координируют обработку данных и управляют потоком выполнения.

**«entity»** — классы данных предметной области. Соответствуют таблицам базы данных или бизнес-объектам.

**«enumeration»** — перечисления констант. Используются для типизации (типы событий, статусы).

## Отношения между классами

**Ассоциация** — связь между классами. Пример: Запрос → Ответ (1:1).

**Агрегация** — часть-целое без владения. Пример: История содержит Запросы.

**Композиция** — часть-целое с владением. Пример: Планировщик владеет Парсерами.

**Зависимость** — использование. Пример: AIАгент использует МодульEnsemble.

Множественности указаны на всех связях: 1, 0..1, *, 1..*.

## Нотация

# Экспериментальные результаты прогнозирования

## Модели прогнозирования

В системе реализован ансамбль из четырёх моделей:

1. **Prophet** (Meta) — аддитивная модель с сезонностью, праздниками и регрессорами (температура).
2. **NeuralProphet** — нейросетевое расширение Prophet: AR-Net, lagged regressors (температура), events, quantiles=[0.1, 0.9].
3. **XGBoost + LightGBM** — градиентный бустинг с 32 фичами (calendar, holidays, lags, rolling, weather, events, trend). Confidence intervals через quantile regression (reg:quantileerror).
4. **Ensemble** — взвешенное объединение моделей (в т.ч. Prophet, NeuralProphet, XGBoost, LightGBM). Веса калибруются автоматически по inverse-RMSE.

## Feature Engineering (32 фичи)

| Группа | Кол-во | Примеры |
|--------|--------|---------|
| Календарные | 8 | day_of_week, month, is_weekend, quarter |
| Праздничные | 5 | is_holiday, days_to_holiday, days_from_holiday, season |
| Лаговые | 7 | lag_1, lag_7, lag_14, lag_30, lag_90, diff_1, diff_7 |
| Скользящие | 5 | rolling_mean_7, rolling_mean_30, rolling_std_7, rolling_min_7, rolling_max_7 |
| Погодные | 4 | temperature, precipitation, temp_deviation, is_good_weather |
| Событийные | 3 | events_count, events_week, has_major_event |

## Выводы по прогнозированию

1. Ансамблевый метод показывает лучший результат в 2 из 3 районов (Иркутский, Слюдянский).
2. Prophet остаётся лучшей индивидуальной моделью для районов с высокой волатильностью (Ольхонский).
3. Скользящие статистики (rolling_min/max) и lag_1 — наиболее информативные фичи.
4. Температура входит в топ-8 фичей, подтверждая значимость погодного фактора.
5. Negative R2 для отдельных моделей на малом тестовом окне (7 дней) ожидаемо — ансамбль компенсирует.

# LangGraph агент: объяснимые прогнозы

## Архитектура агента

Агент прогнозирования построен на LangGraph StateGraph с Command-routing и PydanticOutputParser для структурированного вывода LLM (по паттерну из executory_formula).

### Состояние агента (ForecastState)

```
ForecastState(TypedDict)
├── Входные: district, days_ahead, target_date
├── Данные: history, weather_data, events_data, holidays_info
├── Модели: forecasts, best_model, metrics, feature_importance
├── Результат: explanation, factors, recommendation
└── Мета: error, processing_time
```

### Пайплайн (4 узла)

1. **collect_data** — сбор исторических данных, погоды, событий, праздников из PostgreSQL и API
2. **run_models** — запуск Ensemble (Prophet + NeuralProphet + XGBoost + LightGBM) через ensemble_service, сравнение метрик, определение best_model
3. **analyze_factors** — анализ факторов влияния (праздники, сезон, погода, события, ML-фичи)
4. **generate_explanation** — формирование структурированного объяснения через LLM с PydanticOutputParser

### Структурированный вывод LLM

```python
class ForecastExplanation(BaseModel):
    summary: str          # Краткое резюме прогноза
    main_factors: list[str]  # Главные факторы (2-4 пункта)
    recommendation: str   # Практическая рекомендация
    confidence_note: str  # Оценка уверенности
```

LLM получает ChatPromptTemplate с данными прогноза, метриками моделей и факторами, возвращает JSON-ответ, который парсится PydanticOutputParser. При ошибке парсинга используется fallback с rule-based генерацией.
