## 1. АНАЛИЗ ПРЕДМЕТНОЙ ОБЛАСТИ

### 1.1 Туристический рынок Иркутской области

Иркутская область — один из ключевых туристических регионов Сибири, привлекающий посетителей озером Байкал, историческим наследием и природными достопримечательностями.

**Ключевые показатели (по данным Ростуризма):**
- Ежегодный турпоток: более 1.5 млн человек
- Количество средств размещения: 500+
- Сезонность: пиковая загрузка июль-август (до 95%)

### 1.2 Проблемы отрасли

| Проблема | Описание | Последствия |
|----------|----------|-------------|
| Фрагментация данных | Информация о событиях на разных порталах | Туристы не находят мероприятия |
| Отсутствие аналитики | Нет единой системы мониторинга загруженности | Неэффективное ценообразование |
| Ручной сбор данных | Отельеры вручную анализируют конкурентов | Затраты времени, неточности |

### 1.3 Требования к системе

**Функциональные требования:**
1. Агрегация данных из множества источников
2. Визуализация загруженности отелей
3. Прогнозирование спроса
4. Интеллектуальный поиск по базе знаний
5. Мониторинг культурных событий

**Нефункциональные требования:**
1. Масштабируемость (контейнеризация, Docker Compose)
2. Отказоустойчивость (retry logic, graceful degradation)
3. Производительность (ответ < 500ms для API, кэширование Redis)
4. Безопасность (конфигурация через env, rate limiting, API key auth)

## 2. ОБЗОР ТЕХНОЛОГИЙ

### 2.1 Серверные технологии

#### FastAPI

FastAPI — современный асинхронный web-фреймворк для Python, основанный на стандарте OpenAPI.

**Преимущества:**
- Автоматическая генерация документации (Swagger)
- Нативная поддержка async/await
- Валидация данных через Pydantic
- Высокая производительность (на уровне Node.js и Go)

**Альтернативы и обоснование выбора:**

| Фреймворк | Производительность | Документация | Выбор |
|-----------|-------------------|--------------|-------|
| FastAPI | Высокая | Автоматическая | ✅ |
| Flask | Средняя | Ручная | ❌ |
| Django | Средняя | Ручная | ❌ |
| Express.js | Высокая | Ручная | ❌ |

#### PostgreSQL

PostgreSQL — объектно-реляционная СУБД с открытым исходным кодом, стандарт в индустрии для production-систем.

**Характеристики:**
- Полная поддержка ACID-транзакций
- Расширяемость (типы данных, индексы, расширения)
- Асинхронный доступ через asyncpg
- ORM через SQLAlchemy 2.0

**Обоснование выбора:**

| Критерий | PostgreSQL 16 | MySQL |
|----------|---------------|-------|
| Производительность | Высокая | Средняя |
| Экосистема Python | SQLAlchemy 2.0, Alembic, asyncpg | SQLAlchemy |
| Контейнеризация | Docker-ready | Docker-ready |
| Миграции схемы | Alembic | Alembic |
| Стоимость | Бесплатно (self-hosted) | Бесплатно |

Ранее на этапе MVP использовалась Yandex YDB Serverless; в ходе разработки выполнена миграция на PostgreSQL 16 (Docker, SQLAlchemy 2.0 + asyncpg) для обеспечения:
- независимости от облачного провайдера,
- полноценного ORM через SQLAlchemy 2.0,
- контейнеризации через Docker Compose,
- поддержки миграций схемы.

#### Redis

Redis — in-memory хранилище данных, используемое для кэширования API-ответов и rate limiting.

**Применение в проекте:**
- Кэширование результатов ML-прогнозов (TTL 30 мин)
- Sliding window rate limiting для API endpoints
- Кэширование данных отелей и событий

### 2.4 Прогнозирование временных рядов

#### Ансамблевое прогнозирование

В системе реализовано ансамблевое прогнозирование, объединяющее четыре базовые модели и итоговый Ensemble:

**Prophet** — классическая аддитивная модель Facebook для временных рядов с поддержкой праздников, сезонности и внешних регрессоров (погода).

**NeuralProphet** — нейросетевое расширение Prophet с авторегрессией, лаговыми регрессорами и обработкой событий.

**XGBoost** — gradient boosting с 25+ инженерными признаками и quantile regression для доверительных интервалов.

**LightGBM** — gradient boosting в составе ансамбля для дополнительного разнообразия прогнозов.

**Ensemble** — взвешенное объединение прогнозов всех моделей с адаптивной калибровкой весов на основе метрик (RMSE, MAE, R2).

| Модель | RMSE (Иркутский) | MAE (Иркутский) | Особенность |
|--------|-------------------|------------------|-------------|
| Prophet | 5.58 | 5.17 | Регрессоры погоды |
| NeuralProphet | 5.92 | 4.77 | Авторегрессия, события |
| XGBoost | 6.11 | 5.44 | 25+ фичей, quantile CI |
| **Ensemble** | **2.67** | **2.39** | Weighted average |

#### Feature Engineering

Модуль инженерии признаков генерирует 25+ фичей:
- Календарные: день недели, месяц, квартал, выходные, праздники
- Лаговые: lag_1, lag_7, lag_14, lag_30, lag_90
- Скользящие статистики: rolling_mean, rolling_std, rolling_min, rolling_max (окна 7, 14, 30)
- Дифференциальные: diff_1, diff_7
- Погодные: температура, осадки, скорость ветра
- Событийные: количество событий, тип событий
- Расстояние до ближайшего праздника

### 2.5 AI-агенты (LangGraph)

#### LangGraph

LangGraph — фреймворк для построения мультиагентных графов на основе LangChain, позволяющий создавать сложные цепочки рассуждений с tool calling.

**Реализация в проекте:**

В системе используются два агента:

1. **main_agent** — аналитический агент; инструменты объявлены в `main_agent.py`:
   - `search_hotels` — поиск отелей в БД
   - `search_events` — поиск событий
   - `get_weather` — прогноз погоды
   - `forecast_occupancy` — прогноз загруженности (Ensemble)
   - `get_statistics` — KPI и статистика

2. **forecast_agent** — агент объяснимого прогнозирования с PydanticOutputParser для структурированного вывода (summary, main_factors, recommendation, confidence_note)

**Архитектурный паттерн:** Command pattern для маршрутизации между узлами графа (`Command[Literal["tools", "respond"]]`)

## 3. МЕТОДОЛОГИЯ RAG

### 3.1 Retrieval-Augmented Generation

RAG (Retrieval-Augmented Generation) — архитектурный паттерн, комбинирующий:
1. **Retrieval** — поиск релевантных документов
2. **Augmentation** — обогащение промпта контекстом
3. **Generation** — генерация ответа LLM

```
┌─────────────────────────────────────────────────────────────┐
│                      RAG Pipeline                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Запрос  ──▶  Embedding  ──▶  Vector Search  ──▶  Top-K    │
│    │            │                  │               │        │
│    │      [GigaChat]          [ChromaDB]           │        │
│    │                                               ▼        │
│    └──────────────────────────────────────▶  Контекст      │
│                                                   │        │
│                                                   ▼        │
│                                            ┌──────────┐    │
│                                            │   LLM    │    │
│                                            │(Mistral) │    │
│                                            └──────────┘    │
│                                                   │        │
│                                                   ▼        │
│                                              Ответ         │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 Преимущества RAG перед Fine-tuning

| Критерий | RAG | Fine-tuning |
|----------|-----|-------------|
| Актуальность данных | Мгновенная | Требует переобучения |
| Стоимость | Низкая | Высокая (GPU) |
| Прозрачность | Источники видны | "Чёрный ящик" |
| Масштабирование | Добавление документов | Переобучение |

### 3.3 Embeddings

Embeddings — представление текста в виде вектора чисел, сохраняющего семантический смысл.

**Свойства:**
- Семантически похожие тексты имеют близкие векторы
- Cosine similarity используется для измерения сходства
- Размерность вектора: 512-1536 (в зависимости от модели)

**Формула косинусного сходства:**

```
cos(θ) = (A · B) / (||A|| × ||B||)
```

Где:
- A, B — векторы эмбеддингов
- A · B — скалярное произведение
- ||A||, ||B|| — нормы векторов

### 3.4 Индексация HNSW

HNSW (Hierarchical Navigable Small World) — алгоритм приближённого поиска ближайших соседей.

**Характеристики:**
- Время поиска: O(log N)
- Память: O(N × M × d)
- Точность: 95-99% recall

## 4. АРХИТЕКТУРНЫЕ ПАТТЕРНЫ

### 4.1 Микросервисная архитектура

Система разделена на независимые компоненты:

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│   Frontend  │  │   Backend   │  │  External   │
│   Service   │  │   Service   │  │  Services   │
├─────────────┤  ├─────────────┤  ├─────────────┤
│ React App   │  │ FastAPI App │  │ PostgreSQL  │
│ Vite Build  │  │ Uvicorn     │  │ ChromaDB    │
│ Recharts    │  │ LangGraph   │  │ Mistral API │
│ ECharts     │  │             │  │             │
└─────────────┘  └─────────────┘  └─────────────┘
```

### 4.2 Repository Pattern (Data Service Factory)

Абстракция доступа к данным через `data_service` и `DBService` (PostgreSQL):

```python
# Доступ к данным: data_service / db_service (PostgreSQL 16, SQLAlchemy 2.0 + asyncpg)

class DBService:
    async def get_hotels(self, city: str = None) -> list[Hotel]:
        ...
    async def get_events(self, date_from: date = None) -> list[Event]:
        ...

class ChromaService:
    def search(self, query: str, n_results: int = 5) -> list[dict]:
        ...
```

**Преимущества:**
- Изоляция бизнес-логики от хранилища
- Единая точка доступа через `data_service` / `db_service` (PostgreSQL)
- Упрощение тестирования (мокирование)
- Миграции схемы (Alembic) без разрушения контрактов API

### 4.3 Dependency Injection

FastAPI нативно поддерживает DI через `Depends` и `Annotated`:

```python
DataServiceDep = Annotated[DataServiceBase, Depends(get_data_service_dep)]
CacheServiceDep = Annotated[CacheService, Depends(get_cache_service_dep)]

@router.get("/hotels")
async def get_hotels(data: DataServiceDep, cache: CacheServiceDep):
    cached = await cache.get("hotels")
    if cached:
        return cached
    result = await data.get_hotels()
    await cache.set("hotels", result, ttl=300)
    return result
```

### 4.4 Circuit Breaker (Retry Logic)

Паттерн для обработки временных сбоев внешних сервисов:

```python
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=2, min=4, max=30),
)
async def call_external_api():
    ...
```

**Стратегия:**
1. Первая попытка — немедленно
2. Вторая попытка — через 4 сек
3. Третья попытка — через 8 сек
4. После 3 неудач — возврат fallback
