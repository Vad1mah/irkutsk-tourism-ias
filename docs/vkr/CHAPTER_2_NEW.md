# 2 РАЗРАБОТКА ИНТЕЛЛЕКТУАЛЬНОЙ СИСТЕМЫ ПРОГНОЗИРОВАНИЯ ЗАПОЛНЯЕМОСТИ СРЕДСТВ РАЗМЕЩЕНИЯ

## 2.1 Архитектура системы и подсистема сбора данных

Проектируемая информационно-аналитическая система (ИАС) мониторинга туристической активности Иркутской области построена по клиент-серверной архитектуре с модульным серверным ядром. Выбор монолитной модульной архитектуры, а не микросервисной, обусловлен масштабом проекта: система обслуживает один регион с прогнозируемой нагрузкой до нескольких тысяч запросов в сутки, и накладные расходы на оркестрацию контейнеров, сервисную шину и распределённые транзакции не оправданы [8]. Модульность достигается разделением бэкенда на изолированные слои: маршрутизация (routers), бизнес-логика (services), доступ к данным (db), модели данных (models), парсеры (parsers), промежуточное ПО (middleware) и зависимости (dependencies). Три основных слоя архитектуры – клиентское SPA-приложение, модульное серверное ядро и инфраструктурные сервисы (PostgreSQL, Redis, ChromaDB) – показаны на рисунке 1.

Исторически на этапе курсовой работы использовалась Yandex YDB Serverless – облачная документо-ориентированная СУБД. После закрытия бесплатного тарифа в конце 2025 года принято решение о миграции на PostgreSQL 16. Миграция выполнена в феврале 2026 года: переписаны ORM-модели на SQLAlchemy 2.0, заменён драйвер с YDB SDK на asyncpg, схема данных приведена к реляционной модели с внешними ключами и CHECK-ограничениями. Время отклика на типовых запросах сократилось втрое по сравнению с облачной YDB, а локальное развёртывание через Docker Compose устранило зависимость от внешнего облачного провайдера.

Серверная часть реализована на FastAPI – асинхронном Python-фреймворке, автоматически генерирующем документацию OpenAPI на основе аннотаций типов [8]. Фреймворк нативно поддерживает async/await, что критично для системы с интенсивным вводом-выводом: одновременные HTTP-запросы к внешним API, обращения к базе данных и вызовы LLM-провайдеров. Бэкенд содержит 7 роутеров, объединяющих 59 API-эндпоинтов: hotels (3), events (6), query (5), forecast (9), documents (5), parser (12), analytics (17) и 2 корневых (health, root). Роутер analytics предоставляет endpoint для дашборда ключевых показателей эффективности (KPI, Key Performance Indicators), тепловой карты загруженности, корреляционного анализа, агрегированных данных по отелям и районам (в том числе для картографической визуализации на странице Map) и сравнения районов.

Клиентская часть – одностраничное приложение (SPA) на React 18 с TypeScript, взаимодействующее с сервером через REST API и Server-Sent Events (SSE) для потоковых ответов интеллектуального агента [22]. Обратный прокси-сервер nginx выполняет маршрутизацию запросов к бэкенду и фронтенду, gzip-сжатие статических ресурсов и поддержку SSE-соединений с настроенными таймаутами (proxy_read_timeout 300s). Политика общего происхождения ресурсов (CORS, Cross-Origin Resource Sharing) ограничивает источники запросов доменом фронтенда, разрешая только методы GET, POST, PUT, OPTIONS и заголовки Content-Type, Authorization, X-API-Key.

Инфраструктурный слой включает три компонента: PostgreSQL 16 как основную СУБД, Redis 7 для кэширования и rate limiting, ChromaDB для хранения векторных представлений документов. Все инфраструктурные компоненты развёрнуты в Docker-контейнерах через Docker Compose [23]. Конфигурация предусматривает два режима: по умолчанию запускаются только PostgreSQL и Redis (для локальной разработки бэкенда и фронтенда); профиль full добавляет контейнеры бэкенда и фронтенда для развёртывания в production. Контейнеры PostgreSQL и Redis используют healthcheck-проверки (pg_isready и redis-cli ping), секреты передаются через переменные окружения, а контейнеры работают от непривилегированного пользователя (non-root) для снижения поверхности атаки.

Схема базы данных спроектирована на основе реляционной модели и реализована средствами SQLAlchemy 2.0 ORM с асинхронным драйвером asyncpg [24, 25]. Асинхронный драйвер обрабатывает несколько запросов к БД параллельно, не блокируя event loop FastAPI. База содержит пять таблиц с чётко определёнными связями и ограничениями целостности. Таблица Hotel – справочник средств размещения. На март 2026 года содержит 1 366 записей по 15 районам области. Первичный ключ id – строковый идентификатор длиной до 64 символов, формируемый на основе slug-имени отеля из 101Hotels. Обязательные поля: name (название, тип Text), city (город, String(100)). Необязательные: district (район, String(100)), lat и lon (координаты, Float с ограничениями ge=-90, le=90 и ge=-180, le=180 соответственно), rating (рейтинг 0–10), min_price (минимальная цена, Integer, ge=0), accommodation_type (тип размещения, String(100)). Поля TripAdvisor (tripadvisor_rating, tripadvisor_reviews, tripadvisor_url) заполняются перекрёстным парсером Xotelo. Типы размещения принимают одно из 25 значений: «гостиница», «хостел», «база отдыха», «апартаменты», «гостевой дом», «санаторий» и др.

Временные ряды загруженности номерного фонда сосредоточены в HotelStatistic. Составной первичный ключ (id, date) гарантирует уникальность записи для каждого отеля на каждую дату. Внешний ключ id ссылается на Hotel.id с каскадным удалением (ondelete=CASCADE): при удалении отеля вся его статистика автоматически очищается. Поля: rooms_num (общее количество номеров), free_rooms_amount (свободных номеров), available_rooms_percent (процент доступности), min_price (минимальная цена на дату), max_capacity (максимальная вместимость). Поле updated_at с серверным значением по умолчанию (server_default=func.now()) и автоматическим обновлением (onupdate=func.now()) фиксирует момент последней актуализации. На март 2026 года накоплено 37 663 записи статистики.

Культурные и туристические мероприятия региона агрегированы в Event. На март 2026 года – 318 записей. Первичный ключ event_id (String(128)) формируется хешированием заголовка, даты начала и идентификатора источника, что гарантирует идемпотентность при повторном парсинге: один и тот же фестиваль, полученный из irk.ru и culture38, не создаст дубликат. Обязательные поля: title, date_start, source_id. Поля date_end, event_type (String(50), допускает значения «концерт», «выставка», «фестиваль», «экскурсия», «спектакль» и др.), location и url допускают NULL, поскольку не все источники предоставляют полную информацию. Временные метки created_at и updated_at отслеживают жизненный цикл записи.

Обращения к интеллектуальному агенту фиксируются в QueryHistory. Автоинкрементный первичный ключ id, обязательное поле query_text (текст вопроса пользователя), необязательные response (ответ агента), provider (имя LLM-провайдера: mistral, gigachat, groq). Серверные значения по умолчанию для created_at и updated_at минимизируют нагрузку на приложение – бэкенд не формирует временные метки в Python, делегируя это PostgreSQL.

Результаты прогнозирования хранятся в Forecast. Поля: district (район), forecast_date (дата прогноза), predicted_occupancy (предсказанная загрузка в процентах), model (имя модели: prophet, neuralprophet, xgboost, ensemble), confidence_lower и confidence_upper (границы доверительного интервала). Хранение прогнозов даёт возможность ретроспективно сравнивать качество моделей и отдавать кэшированные результаты при повторных запросах без полного цикла вычислений.

Подсистема сбора данных решает три задачи: извлечение информации о мероприятиях из восьми источников, получение статистики средств размещения с агрегатора 101Hotels и загрузка метеорологических данных из Open-Meteo. Все парсеры наследуют базовый класс BaseParser, определяющий единый интерфейс и общую логику [26].

BaseParser реализован как абстрактный класс с контекстным менеджером (async with). При входе в контекст создаётся aiohttp.ClientSession с настроенным таймаутом и заголовками, при выходе – сессия корректно закрывается. Метод fetch_with_retry инкапсулирует логику повторных попыток: при HTTP 429 (rate limit) или 5xx (серверная ошибка) запрос повторяется с экспоненциальной задержкой (delay = base_delay × 2^attempt), при HTTP 4xx (кроме 429) – запрос считается неудачным. Таймаут и aiohttp.ClientError обрабатываются аналогично. Конфигурация вынесена в dataclass ParserConfig: name (имя парсера для логов), max_retries (по умолчанию 3), timeout (30 секунд), retry_delay (1.0 с), rate_limit_delay (0.5 с между запросами). Модуль anti_detection предоставляет функцию get_random_user_agent, возвращающую случайную строку из пула актуальных User-Agent для Chrome, Firefox и Safari.

Восемь парсеров событий покрывают основные информационные источники: irk.ru (городской портал Иркутска, HTML-парсинг через BeautifulSoup), culture38 (сайт министерства культуры Иркутской области), zeroevent (афиша мероприятий), yandex (Яндекс.Афиша), kassir (билетный сервис), culture_rf (федеральный портал «Культура.РФ»), telegram (каналы через Telethon API) и major (крупные площадки). Каждый реализует абстрактный метод parse(), возвращающий список объектов ParsedEvent – Pydantic-модели с валидацией: title обязателен и непустой, date_start конвертируется в date, event_type нормализуется к одному из допустимых значений. Telegram-парсер представляет особый случай: сообщения из каналов содержат не только анонсы мероприятий, но и поздравления, рекламу, новости ЖКХ. Реализована LLM-классификация через Pydantic-модель EventCheck (поля is_event: bool, category: Literal[«event», «spam»]) и вызов structured_output, отсеивающий нерелевантный контент на этапе парсинга.

Парсер средств размещения работает с JSON API агрегатора 101Hotels.com [27]. Endpoint ssg.101hotels.com/hotel/available/city/russia/{slug} возвращает JSON с информацией о доступности номеров для конкретного населённого пункта. Источник выбран в результате анализа более 30 агрегаторов (Ostrovok, Яндекс Путешествия, Суточно.ру, Booking и др.) – 101Hotels оказался единственным с открытым JSON API без обязательной OAuth-авторизации (проверено F12-анализом сетевых запросов). Парсер последовательно обходит 15 районов Иркутской области: Иркутский, Ольхонский, Слюдянский, Ангарский, Листвянка (Иркутский район), Байкальск (Слюдянский район) и другие. Для перекрёстной верификации данных реализован дополнительный парсер Xotelo, получающий рейтинги и количество отзывов TripAdvisor путём cross-reference по названию и координатам отеля.

Метеорологические данные поступают из Open-Meteo API [7]. Сервис предоставляет бесплатный доступ без ключа авторизации с лимитом 10 000 запросов в день. Запрашиваются параметры: temperature_2m_max, temperature_2m_min (максимальная и минимальная температура воздуха), precipitation_sum (суточные осадки), wind_speed_10m_max (максимальная скорость ветра), weather_code (код погоды по классификации WMO (World Meteorological Organization), например, 61 – слабый дождь, 71 – слабый снегопад). Координаты запросов соответствуют центрам 15 районов. Горизонт прогноза погоды – 14 дней.

Автоматизация сбора реализована через APScheduler с асинхронным планировщиком AsyncIOScheduler [28]. Четыре периодические задачи запускаются по IntervalTrigger: события каждые 6 часов, отели каждые 2 часа, погода каждые 3 часа, Telegram-каналы каждый час. Периодичность определена экспериментально: интервал в 2 часа для отелей достаточен для фиксации внутридневных колебаний доступности без превышения лимитов API; 6-часовой интервал для событий достаточен, поскольку культурные мероприятия обновляются не чаще раза в сутки. При запуске планировщик выполняет начальный сбор всех типов данных (run_initial=True), затем работает по расписанию.

Нормализация данных выполняется на этапе парсинга. Названия районов приводятся к каноническому виду (например, «Иркутский район» → «Иркутский»). Дедупликация событий осуществляется по первичному ключу event_id, формируемому из хеша заголовка, даты и источника, – повторная вставка приводит к обновлению существующей записи (upsert). Для отелей применяется аналогичная стратегия через ON CONFLICT DO UPDATE в PostgreSQL. Batch insert через SQLAlchemy загружает до нескольких тысяч записей за одну транзакцию с использованием bulk_save_objects и session.execute для INSERT ... ON CONFLICT.

Мониторинг состояния парсеров реализован через модуль health_monitor. Он отслеживает время последнего успешного запуска каждого парсера, количество собранных и отклонённых записей, процент ошибок (error rate). При превышении порогового значения ошибок (50%) парсер помечается как degraded. Статистика доступна через API, что даёт оператору возможность оперативно выявлять проблемы с внешними источниками – изменение структуры HTML-страницы или блокировку IP-адреса.

Доступ к данным централизован через data_service – фабричный класс, абстрагирующий операции CRUD (Create, Read, Update, Delete) для всех таблиц. Методы get_hotels, get_statistics, get_events, save_forecast принимают параметры фильтрации (район, период, тип) и возвращают Pydantic-модели. Прямые SQL-запросы в коде роутеров отсутствуют, что упрощает замену СУБД или добавление кэширующего слоя.

## 2.2 Модуль прогнозирования и интеллектуальный агент

Прогнозирование загруженности средств размещения основано на ансамблевом подходе, объединяющем три модели: Prophet, NeuralProphet и XGBoost (LightGBM включён в XGBoost-сервис). Каждая модель обладает собственными достоинствами в отношении типов зависимостей, которые она способна моделировать. Объединение их прогнозов снижает дисперсию и повышает устойчивость результата. Перед подачей данных в модели выполняется инженерия признаков (feature engineering) – процесс преобразования исходных временных рядов в набор числовых характеристик [29].

Модуль FeatureEngineering генерирует свыше 25 признаков, разделённых на семь групп. Календарные признаки (8 шт.): day_of_week (день недели, 0–6), day_of_month (день месяца, 1–31), month (месяц, 1–12), quarter (квартал, 1–4), week_of_year (номер недели по ISO), is_weekend (бинарный: суббота или воскресенье), is_month_start, is_month_end. Эти признаки кодируют периодические паттерны спроса. Анализ данных показал, что загруженность в пятницу и субботу в среднем на 12–18 процентных пунктов выше, чем в середине рабочей недели.

Праздничные признаки (5 шт.) формируются с использованием библиотеки holidays для российского календаря: бинарный is_holiday, дистанция в днях до ближайшего праздника (days_to_holiday) и от последнего (days_from_holiday), принадлежность к длинным выходным (is_long_weekend), сезон (season). Новогодние каникулы (1–8 января) и майские праздники (1–5 мая) вносят наибольший вклад в колебания спроса.

Лаговые признаки отражают автокорреляцию временного ряда загруженности. Генерируются лаги на 1, 7, 14, 30 и 90 дней, а также разности первого порядка diff_1 и diff_7, фиксирующие краткосрочную и недельную динамику. При недостатке данных (например, для нового отеля с историей менее 14 дней) лаги, превышающие длину ряда, автоматически пропускаются с записью в лог. Скользящие статистики (5 шт.) вычисляются в окнах 7 и 30 дней: rolling_mean_7, rolling_mean_30, rolling_std_7, rolling_min_7, rolling_max_7. Стандартное отклонение в семидневном окне фиксирует внутринедельную волатильность: высокое значение указывает на резкие колебания загрузки.

Погодные признаки (4 шт.) извлекаются из данных Open-Meteo: температура, осадки, скорость ветра, код погоды. При отсутствии данных за конкретную дату применяется fallback на среднемесячные значения, рассчитанные по имеющимся историческим наблюдениям. Корреляция между температурой и загруженностью в Ольхонском районе летом достигает 0.42, что подтверждает значимость метеофактора для прогноза.

Событийные признаки (2 шт.): events_week (количество мероприятий за неделю) и has_major_event (бинарный флаг наличия крупного мероприятия: фестиваль, спортивное событие). Трендовые признаки (2 шт.): линейный time_index и нормализованный trend = time_index / len(data), позволяющие моделям учитывать долгосрочную динамику рынка. Ценовые признаки формируются на основе min_price из HotelStatistic: абсолютное значение и относительное изменение за неделю.

Prophet – библиотека прогнозирования временных рядов, разработанная Facebook Research в 2017 году [14]. Модель декомпозирует временной ряд по аддитивной формуле: y(t) = g(t) + s(t) + h(t) + ε(t), где g(t) – тренд (кусочно-линейный или логистический), s(t) – сезонная компонента (ряды Фурье), h(t) – праздничные эффекты, ε(t) – шум. В системе активированы годовая сезонность (fourier_order = 10) и недельная (fourier_order = 3). Российские праздники задаются явным списком с окном влияния ±2 дня (lower_window = -2, upper_window = 2): система учитывает не только сам праздник, но и дни до и после него, когда спрос начинает расти или спадать. Погодные данные подключены как внешние регрессоры через метод add_regressor: температура, осадки. Prophet работает на CPU и обучается за 2–5 секунд на объёме данных одного района.

NeuralProphet – расширение Prophet с нейросетевыми компонентами, разработанное в 2021 году [15]. Модель сохраняет интерпретируемость Prophet (декомпозиция на тренд, сезонность, праздники), но добавляет авторегрессию через параметр n_lags: внутренняя нейросеть принимает на вход значения загрузки за предыдущие N дней. В системе n_lags = 14, что соответствует двухнедельному окну – оптимальное значение, определённое при grid search по n_lags ∈ {7, 14, 21, 30}. Погода и события подключены как лаговые регрессоры (add_lagged_regressor с n_lags = 7), а не как обычные регрессоры: нейросеть обучает индивидуальные веса для каждого лага, благодаря чему модель улавливает задержку влияния погоды на спрос (например, прогноз хорошей погоды за 3–5 дней увеличивает количество бронирований). Обучение выполняется на CPU; время – 10–15 секунд. Модель поддерживает раннюю остановку (early_stopping) для предотвращения переобучения.

XGBoost (eXtreme Gradient Boosting) – алгоритм градиентного бустинга для табличных данных [16]. В отличие от Prophet и NeuralProphet, XGBoost не оперирует понятием «временной ряд»: модуль feature_engineering преобразует ряд в плоскую таблицу признаков, и XGBoost обучается на ней как на стандартной задаче регрессии. Ключевое преимущество – способность улавливать нелинейные взаимодействия признаков: например, сочетание «праздничные выходные + тёплая погода + крупный фестиваль» может давать мультипликативный эффект на загрузку, который линейные модели не уловят.

Реализована квантильная регрессия (quantile regression) для построения доверительных интервалов: три отдельные модели XGBoost обучаются с функциями потерь для квантилей 0.1, 0.5 и 0.9. Квантиль 0.5 даёт медианный прогноз, квантили 0.1 и 0.9 – нижнюю и верхнюю границы 80-процентного доверительного интервала. LightGBM реализован внутри XGBoost-сервиса как альтернативная реализация градиентного бустинга: стратегия leaf-wise (выбор листа с максимальным снижением ошибки) отличается от level-wise у XGBoost (равномерное углубление), что вносит разнообразие в прогнозы и повышает устойчивость ансамбля.

Ансамблевый сервис (EnsembleService) координирует запуск моделей и объединение результатов. Параллельное выполнение реализовано через asyncio.gather: три корутины (run_prophet, run_neuralprophet, run_xgboost) запускаются одновременно, каждая оборачивает синхронные модели через asyncio.to_thread. Общее время прогноза составляет ~2 секунды вместо 15–20 при последовательном запуске. При ошибке одной модели остальные продолжают работу (graceful degradation): если Prophet вернул пустой результат из-за нехватки данных, ансамбль формируется из оставшихся моделей с перераспределением весов.

Метод по умолчанию – weighted_average. Веса рассчитываются по формуле inverse-RMSE:

w_i = (1 / (RMSE_i + 0.1)) / Σ(1 / (RMSE_j + 0.1))

Модель с меньшей ошибкой на валидационном отрезке получает больший вес. Константа 0.1 предотвращает деление на ноль. Автокалибровка выполняется не чаще раза в час (CALIBRATION_TTL = 3600 с): сервис вызывает метод compare_models на валидационных данных, получает RMSE, MAE (Mean Absolute Error) и R² каждой модели, затем пересчитывает веса. Результаты сравнения моделей представлены в таблице 5. Помимо weighted_average доступны simple_average (равные веса 1/3) и best_model (выбор единственной модели с наименьшей ошибкой). Кэширование в Redis со временем жизни 30 минут исключает повторные вычисления при частых запросах.

Интеллектуальный агент построен на фреймворке LangGraph – библиотеке для создания графов рассуждений [18]. Агент реализован как StateGraph, в котором состояние (AgentState) включает: messages (история сообщений, аннотированная через add_messages), context (строка с контекстом из RAG), tool_calls_count (счётчик для защиты от зацикливания, лимит 5 вызовов за итерацию). Граф содержит два узла – chatbot и tools – связанных условными рёбрами: если LLM-ответ содержит tool_calls, управление передаётся в tools; если нет – ответ возвращается пользователю. Пять инструментов покрывают основные аналитические потребности. search_hotels выполняет семантический поиск по ChromaDB с фильтром type=«hotel» и возвращает до 7 релевантных средств размещения с ценами, рейтингами и координатами. search_events ищет предстоящие мероприятия, фильтруя записи, у которых дата начала позже текущего дня (where filter по epoch days). get_weather обращается к Open-Meteo API за текущей и прогнозной погодой, используя словарь координат для 14 населённых пунктов области. forecast_occupancy делегирует выполнение ForecastAgent – отдельному LangGraph-графу с четырьмя узлами: collect_data (сбор истории, погоды, событий), run_models (запуск ансамбля), analyze_factors (выявление ключевых факторов), generate_explanation (Pydantic-модель ForecastExplanation с полями summary, main_factors, recommendation, confidence_note). get_statistics возвращает агрегированные KPI из PostgreSQL: количество отелей, событий, средний рейтинг, загрузку по районам.

RAG-конвейер (Retrieval-Augmented Generation) расширяет возможности агента контекстом из базы знаний [30]. Документы – описания отелей, события, статистические сводки – индексируются в ChromaDB с эмбеддингами GigaChat Embeddings (модель Embeddings API Сбера). Размер эмбеддинга – 1024 измерения. При поступлении запроса текст преобразуется в вектор, выполняется approximate nearest neighbor search (k = 5), найденные фрагменты конкатенируются и добавляются в системный промпт. Метаданные документов содержат: type (hotel / event / statistic), district (район), date (дата актуальности) – что позволяет применять фильтры where при поиске, сужая контекст до релевантного района и временного периода.

Основной LLM-провайдер – Mistral Large, доступный из РФ без VPN, с квотой 1 млрд токенов в месяц [19]. Для tool calling настроены параметры temperature = 0.1 (минимальная стохастичность) и top_p = 0.9 (рекомендация Mistral для function calling). Мультипровайдерная архитектура LLM поддерживает переключение между провайдерами (GigaChat, Groq, DeepSeek, OpenRouter) через единственную переменную окружения LLM_PROVIDER. Код привязки инструментов (bind_tools) универсален: LangChain абстрагирует различия API провайдеров.

SSE-стриминг реализован через endpoint POST /api/query/stream, возвращающий StreamingResponse с типом text/event-stream. Каждый токен LLM-ответа передаётся клиенту отдельным SSE-событием формата data: {token}\n\n. Пользователь видит начало ответа через 0.5–1 секунду, не дожидаясь полной генерации. Контекст разговора сохраняется в MemorySaver LangGraph по идентификатору потока (thread_id): при следующем сообщении агент «помнит» предыдущие реплики, что позволяет вести связный диалог. При ошибке LLM-провайдера SSE-канал отправляет событие error и закрывает соединение.

## 2.3 Проектирование пользовательского интерфейса и обеспечение качества

Клиентская часть системы реализована на связке React 18 + TypeScript + Vite 7 [22, 31]. Vite выбран вместо Create React App и Webpack по причине скорости: dev-сервер стартует менее чем за 300 мс благодаря нативной поддержке ES-модулей (ESM) в браузере. Hot Module Replacement (HMR) обновляет изменённый компонент без перезагрузки всей страницы. Production-сборка включает tree-shaking (удаление неиспользуемого кода), code splitting (разделение на чанки по маршрутам) и minification. TypeScript работает в строгом режиме (strict: true, noImplicitAny: true), что исключает категорию ошибок, связанных с неявными типами. Маршрутизация реализована через React Router 7 с ленивой загрузкой (React.lazy + Suspense) для страниц, не требующихся при начальной загрузке.

### Информационная архитектура

Структура навигации системы построена по задачному принципу: каждая из восьми страниц соответствует конкретному пользовательскому сценарию. Home – планирование поездки на Байкал (выбор района, периода, быстрые вопросы к AI-ассистенту). Analytics – аналитический обзор района с KPI, историей цен, рекомендациями и прогнозом на 14 дней. Events – каталог мероприятий с фильтрацией по типу, источнику и дате. Map – географическое сопоставление районов (карточки, тепловая карта, radar-сравнение). Forecast – экспертное прогнозирование с переключением между простым и развёрнутым режимами. Chat – полноэкранный диалог с интеллектуальным агентом через SSE-стриминг. HotelDetail – детальная карточка отеля, доступная по прямой ссылке /hotels/:id. About – презентация системы для защиты ВКР.

Боковая панель навигации содержит семь пунктов с иконками (библиотека Lucide), текстовыми метками и краткими описаниями. Пункты «Прогнозы» и «AI-помощник» дополнены бейджами «ML» и «AI» соответственно, сигнализирующими об использовании машинного обучения. Восьмая страница – карточка отеля – не вынесена в меню, поскольку пользователь попадает на неё через клик по отелю из Analytics или Map. Структура навигации показана на рисунке 4.

Типичный сценарий взаимодействия туриста выстроен по принципу «от общего к частному». Принцип progressive disclosure реализован на странице Forecast наиболее явно. По умолчанию пользователь видит простой режим: один график ансамблевого прогноза с доверительным интервалом. Переключатель «Простой / Эксперт / Сезонность» открывает дополнительные слои: кривые отдельных моделей, таблицу метрик (RMSE, MAE, R²), диаграмму значимости признаков XGBoost, AI-объяснение от ForecastAgent и возможность сравнить районы. Такой подход не перегружает неподготовленного посетителя, но предоставляет аналитику полный инструментарий.

### UX-решения

Обработка ошибок стандартизирована через компонент ErrorState. Он содержит иконку (AlertCircle), заголовок, описание и кнопку «Повторить» (Button variant=«outline»). Компонент используется на всех страницах с серверными данными: Analytics, Events, Forecast, Map, HotelDetail. Глобальная обёртка ErrorBoundary перехватывает критические ошибки React-рендеринга и предлагает перезагрузить страницу. Для мутаций (POST-запросы к AI-агенту) ошибки отображаются через всплывающие уведомления react-hot-toast с настроенными стилями: фон hsl(var(--card)), текст hsl(var(--card-foreground)).

Состояния загрузки реализованы через скелетонные экраны, а не через спиннеры. CSS-класс .skeleton в index.css создаёт анимацию shimmer на основе переменной --muted. Скелетоны воспроизводят структуру целевого контента: на Analytics – прямоугольники вместо KPI-карточек и графиков, на Forecast – полоса вместо AreaChart, на Events – ряды карточек, на Map – область карты. Скелетонный подход снижает воспринимаемое время ожидания: пользователь видит каркас интерфейса вместо пустого экрана и спиннера, что уменьшает вероятность преждевременного ухода со страницы.

Страница «AI-помощник» реализует полноэкранный диалоговый интерфейс (рисунок 9). SSE-стриминг передаёт токены по мере их генерации; пользователь видит текст, появляющийся в реальном времени, что создаёт ощущение «живого» разговора. Промежуточные вызовы инструментов агента отображаются бейджами (Badge) – «Ищу отели...», «Строю прогноз...» – и снимаются по завершении. История диалога сохраняется в localStorage под уникальным ключом сессии; при закрытии и повторном открытии вкладки последний диалог восстанавливается. Быстрые подсказки-чипы снижают порог входа для пользователя, не знакомого с системой: «Лучшие отели на Ольхоне», «Прогноз загрузки на майские». Такой подход соответствует модели conversational UI, при которой интерфейс ведёт пользователя через диалог, а не через формы.

Управление серверным состоянием реализовано через TanStack React Query. Библиотека выполняет автоматическое кэширование ответов API, ревалидацию при возврате фокуса окна (refetchOnWindowFocus), retry при сетевых ошибках (retry: 3), дедупликацию параллельных запросов к одному endpoint. Время жизни кэша (staleTime) дифференцировано: 5 минут для справочных данных (отели, события), 1 минута для аналитических (прогнозы, KPI) и 0 для чат-запросов. В нижней части сайдбара индикатор отображает статус подключения к базе данных через вызов api.getHealth – зелёная или красная точка рядом с надписью «ИГУ © 2026».

### Тестирование и безопасность

Тестирование охватывает два уровня. Модульные тесты (60 шт., из них 59 пройдено и 1 пропущен при стандартном прогоне pytest) разделены на пять файлов: инженерия признаков, ансамблевый сервис, парсеры, rate limiting, аутентификация. Фикстуры изолируют тесты: мок-данные истории загрузки (100 точек с синтетической сезонностью), тестовый Redis-клиент (fakeredis), пустая ChromaDB-коллекция. Сквозные (E2E) тесты включают 9 сценариев: health-endpoint, KPI, список отелей, события, прогноз Prophet, ансамблевый прогноз, погода, запрос к AI-агенту, статус планировщика. Тесты выполняются против запущенного сервера и реальной БД, проверяя цепочку от HTTP-запроса до JSON-ответа.

Безопасность реализована четырьмя механизмами. Rate limiting через Redis sorted set (sliding window): 60 запросов/мин для общих endpoint, 10 для /api/query, 5 для /api/parser; при превышении – HTTP 429 с Retry-After; при недоступности Redis – in-memory fallback [10]. API-ключевая аутентификация: заголовок X-API-Key защищает парсерные endpoints. Валидация входных данных через Pydantic: Field(ge=0, le=100) для процентов, Field(min_length=1) для строк, Field(ge=-90, le=90) для широты. В production nginx добавляет заголовки Content-Security-Policy и Strict-Transport-Security.

Собранные данные содержат ограничение: летний период 2025 года (июль–сентябрь) не покрыт наблюдениями, поскольку система находилась на этапе проектирования. Пробел влияет на точность долгосрочных прогнозов – при горизонте 30+ дней R² может принимать отрицательные значения. Для демонстрации рекомендованы краткосрочные горизонты (3–14 дней). Архитектурно система полностью готова к работе с полными данными: при накоплении летних наблюдений в 2026 году модели обучатся на годовом цикле без изменений кода.

## Выводы по главе

В ходе практики разработана информационно-аналитическая система мониторинга туристической активности Иркутской области. Клиент-серверная архитектура с модульным бэкендом на FastAPI (59 эндпоинтов, 7 роутеров) и реляционной базой данных PostgreSQL 16 (5 таблиц, 1 366 отелей, 37 663 записи статистики, 318 событий) реализует полный цикл сбора, хранения и анализа данных из 11 внешних источников. Ансамблевый модуль прогнозирования объединяет Prophet, NeuralProphet и XGBoost с адаптивными весами inverse-RMSE; параллельное выполнение через asyncio.gather сокращает время прогноза до ~2 секунд.

Проектирование пользовательского интерфейса выполнено с позиции информационного дизайна: информационная архитектура из восьми страниц, организованных по пользовательским сценариям; дизайн-система из пяти базовых компонентов с 25 CSS-токенами и поддержкой тёмной/светлой тем; семь типов диаграмм, каждый из которых выбран под конкретный тип данных; единая цветовая семантика загруженности во всех визуализациях. Скелетонные экраны, ErrorState с retry, адаптивная вёрстка для трёх контрольных точек и SSE-стриминг в чате формируют целостный пользовательский опыт. Качество подтверждено 60 модульными и 9 сквозными тестами; безопасность – rate limiting на Redis, API-ключевой аутентификацией, валидацией через Pydantic и CSP-заголовками.
