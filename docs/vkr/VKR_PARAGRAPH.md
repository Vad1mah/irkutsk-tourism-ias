1. **Назначение информационной системы**

Информационная система (ИС) разработана для автоматизации процессов сбора, анализа и прогнозирования данных о туристической активности в Иркутской области. Система предназначена для предоставления актуальной информации и аналитических отчетов представителям туристической отрасли, аналитикам и потенциальным туристам.  
**Цель системы** - повышение эффективности принятия решений в сфере туризма Иркутской области за счет предоставления своевременной и точной аналитической информации, а также прогнозов загруженности средств размещения.  
**Актуальность** проекта обусловлена положительными изменениями, которые будут достигнуты для двух ключевых групп пользователей - аналитиков туристической отрасли и представителей средств размещения. Эти изменения представлены в Таблице 1, содержащей анализ текущей ситуации (AS IS) и целевой модели (TO BE).

| :---- | :---- |
| Для аналитиков туристической отрасли | |
| Данные о загруженности отелей разрознены по разным источникам (Booking, 101Hotels, Ostrovok). Анализ требует ручного сбора и обработки информации. | Система автоматически собирает данные из открытых источников (101Hotels API), нормализует их и предоставляет единый интерфейс для анализа. |

Система интегрирует данные из нескольких внешних источников, сгруппированных по типам: восемь источников событий (irk.ru/afisha, culture38.ru, irk.zeroevent.ru, афиши Яндекса и Kassir.ru, портал «Культура.РФ», Telegram-каналы региона, ручной учёт крупных событий), два источника по средствам размещения (101Hotels API, Xotelo/TripAdvisor) и погода (Open-Meteo). Сбор и нормализация реализованы **17 модулями** в каталоге `backend/app/parsers/` (включая общие утилиты: базовый класс, AI-извлечение, антидетект, мониторинг).

2. **Требования к информационной системе**
   1. **Функциональные требования**

Система разрабатывается с целью обеспечения информационно-аналитической поддержки туристической отрасли региона и должна удовлетворять функциональным требованиям, которые разделяются на следующие группы (Рисунок 1):

* управление данными о средствах размещения;
* управление данными о туристических событиях;
* взаимодействие с пользователем;
* анализ данных и прогнозирование;
* интеграция компонентов системы.

Управление данными о средствах размещения включает получение данных из 101Hotels API, сохранение их в PostgreSQL 16 (Docker, SQLAlchemy 2.0 + asyncpg), обновление статистики загруженности и просмотр списка средств размещения.  
Управление данными о туристических событиях включает парсинг событий из перечисленных внешних источников (восемь парсеров событий плюс общие модули), сохранение событий в PostgreSQL и просмотр календаря событий.  
Взаимодействие с пользователем включает функции:

* ввод запроса на естественном языке;
* отображение ответа AI-агента;
* визуализация прогнозов на графиках;
* просмотр истории запросов.

Анализ данных и прогнозирование включает:
- поиск релевантного контекста (RAG через ChromaDB с эмбеддингами GigaChat);
- прогнозирование загруженности (ансамбль из Prophet, NeuralProphet, XGBoost, LightGBM);
- генерацию ответа языковой моделью (Mistral Large — основной, 1B токенов/мес; GigaChat и др. — резерв);
- учёт событий, погоды, праздников в прогнозе;
- объяснимый прогноз (LangGraph Agent с LLM-объяснением).

Feature engineering включает 38 признаков:
- календарные (day_of_week, month, is_weekend...);
- лаговые (lag_1, lag_7, lag_14, lag_30, lag_90);
- rolling статистики (mean_7, mean_30, std_7, min_7, max_7);
- погода (temperature, precipitation);
- события (events_count, has_major_event);
- праздники (is_holiday, days_to_holiday).  
Интеграция компонентов системы включает REST API для взаимодействия (FastAPI), хранение эмбеддингов в векторной БД (Chroma), логирование запросов и ответов агента, а также автоматический сбор данных по расписанию.

   2. **Нефункциональные требования**

Система должна быть разработана с учетом следующих нефункциональных требований.  
В части совместимости веб-интерфейс должен обеспечивать полную функциональность в актуальных версиях браузеров Google Chrome, Mozilla Firefox и Microsoft Edge. Визуализация реализована библиотеками Recharts и ECharts (встроенные в React). Интерфейс необходимо оптимизировать для корректной работы на устройствах с разрешением экрана от 1280x720 пикселей.  
В категории производительности архитектура системы должна быть рассчитана на одновременное обслуживание до 50 активных пользователей. Время отклика интерфейса на действия пользователя не должно превышать двух секунд.  
Касательно точности работы, средняя абсолютная процентная ошибка (MAPE) прогнозирования загруженности не должна превышать 15%. Достоверность прогнозов подлежит проверке на исторических данных методом кросс-валидации.

3. **Функции информационной системы**

Функции и альтернативные последовательности разработаны и указаны на диаграмме вариантов использования (Приложение Г) (Рисунок 2).  
В системе определены три основные роли - Пользователь, Администратор и Планировщик, каждая со своими функциональными возможностями.  
Пользователь представляет туриста, аналитика туристической отрасли или представителя средства размещения. Пользователь взаимодействует с системой через единый веб-интерфейс: задает вопросы интеллектуальному агенту на естественном языке, просматривает справочник средств размещения, календарь событий и историю своих запросов.  
Администратор выполняет технические функции. Он наследует все возможности Пользователя и дополнительно имеет доступ к управлению источниками данных и логам системы.  
Планировщик представляет собой автоматический актор, реализованный через APScheduler (ежедневный и периодический сбор). Он инициирует процесс сбора данных по расписанию без участия человека.  
Перечень вариантов использования:

* UC1 «Построить прогноз загруженности» - центральный вариант использования системы;
* UC2 «Просмотреть справочник размещения» - справочная информация о средствах размещения;
* UC3 «Просмотреть календарь событий» - информация о мероприятиях региона;
* UC4 «Просмотреть историю запросов» - история диалогов с агентом;
* UC5 «Настроить источники данных» - административная функция;
* UC6 «Просмотреть логи системы» - административная функция;
* UC7 «Выполнить сбор данных» - автоматический процесс.

4. **Основные алгоритмы ИС**

Основные алгоритмы информационной системы формализованы в виде двух ключевых сценариев, отражающих архитектуру и логику работы. Эти сценарии детализированы на диаграммах деятельности (Приложение Б).

Фоновый сбор данных (сценарий 1, работы 1.1.2-1.1.9) выполняется автоматически по расписанию (APScheduler, ежедневный сбор) и обеспечивает актуальность данных в хранилище. Процесс включает следующие этапы: запуск сбора данных (1.1.2), параллельный сбор данных о событиях (1.1.3) и о размещении (1.1.4), нормализация и валидация (1.1.5) или логирование ошибки (1.1.6) при недоступности источника, сохранение в PostgreSQL (1.1.7), индексация в Chroma (1.1.8), завершение сбора (1.1.9).

Обработка запроса пользователя (сценарий 2, работы 1.2.10-1.2.18) выполняется интерактивно при обращении через веб-интерфейс. Процесс представлен на диаграмме активности (Приложение Б) и диаграмме последовательности.  
Механизм обработки запроса состоит из девяти работ. Получение запроса (1.2.10) и поиск контекста в Chroma (1.2.11) выполняются последовательно. Определение типа запроса (1.2.12) приводит к перекрестку исключающего ИЛИ (J5): если запрос касается будущего - вызывается прогнозирование Ensemble (Prophet + NeuralProphet + XGBoost + LightGBM) (1.2.13); если касается прошлого - выполняется аналитика исторических данных (1.2.14). После слияния (J6) языковая модель генерирует ответ (1.2.15). Далее через перекресток И (J7) параллельно выполняются визуализация результатов (1.2.16) и сохранение в историю (1.2.17). После слияния (J8) процесс завершается единой работой «Завершение обработки» (1.2.18).

Для определения структуры проекта была взята за основу предметная область и разработан проект клиент-серверного приложения. Приложение разрабатывается как веб-приложение с интеллектуальным агентом в качестве ядра. Детальную структуру проекта отражает диаграмма классов (Рисунок 4). На ней можно выделить ключевые модули приложения, такие как FastAPIКонтроллер, AIАгент, ПрогнозМодуль, которые детально рассматриваются далее.

Классы со стереотипом «control» отвечают за координацию бизнес-логики:
* FastAPIКонтроллер - обрабатывает HTTP-запросы и координирует их маршрутизацию;
* AIАгент - анализирует текст запроса, выполняет поиск контекста в RAG и определяет тип обработки;
* ПрогнозМодуль - строит прогнозы загруженности с использованием Ensemble (Prophet + NeuralProphet + XGBoost + LightGBM).

Классы со стереотипом «boundary» представляют интерфейсы взаимодействия:
* ГлавнаяСтраница, ФормаВвода, ОбластьОтвета, ГрафикПрогноза - элементы пользовательского интерфейса;
* LLMКлиент - интерфейс к Mistral Large (основной LLM, 1B токенов/мес); GigaChat и другие провайдеры — резерв через мультипровайдерную конфигурацию.

Классы со стереотипом «entity» представляют хранимые данные:
* Запрос - текстовый вопрос пользователя с метаданными;
* Ответ - сгенерированный ответ агента с использованным контекстом;
* Контекст - найденные документы из RAG;
* Прогноз - результат прогнозирования с доверительным интервалом;
* История - записи диалогов пользователя с агентом.

6. **Архитектура ИС**

Высокоуровневая архитектура системы представлена на диаграммах компонентов и развертывания (Приложение В).  
Архитектура системы состоит из пяти основных компонентов. Компонент FastAPI Backend обрабатывает HTTP-запросы от клиента и маршрутизирует их к соответствующим обработчикам. Компонент AI Agent координирует обработку запросов пользователя, определяет тип запроса и формирует ответ. Компонент RAG Retriever обеспечивает поиск релевантного контекста в векторной базе данных Chroma. Компонент Ensemble Module выполняет прогнозирование загруженности с использованием ансамбля из четырёх ML-моделей: Prophet, NeuralProphet, XGBoost и LightGBM. Веса моделей определяются динамически на основе их точности (RMSE) на исторических данных. Лучший результат показывает Ensemble с RMSE=2.24, что значительно превышает точность отдельных моделей (Prophet: 5.39, NeuralProphet: 4.85, XGBoost: 5.73). Компонент LLM Client управляет интеграцией с языковой моделью для генерации ответов. Данные хранятся в PostgreSQL 16 (Docker, SQLAlchemy 2.0 + asyncpg) и Chroma (векторная).  
В целях масштабируемости особое внимание уделено разделению фонового сбора данных и интерактивной обработки запросов. Фоновый процесс выполняется по расписанию через Docker-контейнеры с APScheduler и не влияет на производительность интерактивной части.

Для контейнеризации парсеров создан Dockerfile на базе Python 3.11 с установленным Playwright для браузерных парсеров. Docker Compose конфигурация включает:
- PostgreSQL 16 для хранения данных;
- Redis 7 для кэширования;
- Контейнеры парсеров (hotels, events, weather);
- Планировщик для регулярного запуска по расписанию.

Диаграмма развертывания отражает физическое размещение компонентов:
* Клиент - браузер пользователя с веб-приложением React;
* Сервер приложений - содержит FastAPI Backend, AI Agent, Ensemble Module, RAG Retriever, LLM Client;
* Узел PostgreSQL - база данных PostgreSQL 16 (Docker);
* Сервер Chroma - векторная база данных для хранения эмбеддингов;
* Внешние сервисы - Mistral AI API (Mistral Large — основной LLM) для генерации ответов.

Проект базируется на принципах асинхронного программирования. FastAPI и парсеры данных реализованы с использованием asyncio, что обеспечивает высокую производительность при минимальных ресурсах.  
Взаимодействие между серверной частью и браузерным клиентом осуществляется посредством протокола HTTPS. Обмен данными производится в формате JSON.
