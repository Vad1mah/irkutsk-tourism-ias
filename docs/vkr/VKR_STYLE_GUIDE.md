## A. СТРУКТУРА ПРЕДЛОЖЕНИЙ

### A.1 Длина предложений

Средняя длина: 15–30 слов. Ключевой принцип: **чередование**. Короткое (5–10 слов) после длинного (25–35 слов). Никогда подряд три предложения одной длины.

**Примеры коротких (до 12 слов):**

1. Источник отклонён.
2. Все связи имеют мощность 1:N.
3. Стоимость использования приемлема для прототипа.
4. Иркутск не входит в список поддерживаемых городов.
5. Каждая диаграмма имеет единственное начальное состояние.
6. Результаты двух методов согласуются.
7. Метод предполагает три оценки длительности.
8. Прямая связь Boundary–Entity запрещена.
9. Документ включает девять разделов.
10. Redis обеспечивает кэширование и rate limiting.

**Примеры средних (13–25 слов):**

1. Для объективного сравнения использованы результаты бенчмарков на стандартных датасетах.
2. Модель изначально обучена на русскоязычных текстах, что обеспечивает лучшее качество эмбеддингов.
3. Интеграция через единый API Сбера упрощает архитектуру системы.
4. Методология является федеральным стандартом США и широко применяется для проектирования реляционных баз данных.
5. Альтернативные агрегаторы отклонены, поскольку все требуют авторизацию API или используют защиту от парсинга.
6. Такой смешанный подход точно отражает реальные зависимости данных.
7. Объекты предметной области выявлены на основе анализа сценариев вариантов использования.
8. Переходы на диаграмме инициируются завершением предыдущего действия, а не внешними событиями.
9. Данная диаграмма чётко разграничивает ответственность между компонентами системы.
10. Все парсеры наследуют BaseParser с единым интерфейсом: retry с exponential backoff.

**Примеры длинных (25–40 слов):**

1. FastAPI выбран как фреймворк для REST API по следующим причинам: высокая производительность за счёт асинхронности, автоматическая генерация документации OpenAPI, встроенная валидация данных через Pydantic.
2. Ожидаемая длительность проекта составляет 76 рабочих дней, что соответствует приблизительно 3,8 месяца, с доверительным интервалом 95 процентов: от 67 до 85 рабочих дней.
3. При обнаружении вопроса о будущем вызывается Ensemble для построения прогноза, контекст и прогноз передаются LLM для генерации ответа, результат сохраняется в PostgreSQL и отображается пользователю.
4. В проекте реализована мультипровайдерная архитектура LLM с возможностью переключения между провайдерами через переменную окружения LLM_PROVIDER.
5. Для максимального покрытия событийной активности региона реализовано восемь парсеров, каждый из которых использует адаптированную стратегию извлечения данных.

### A.2 Начала предложений и абзацев

Ни одно начало не повторяется в пределах трёх абзацев подряд. Ниже 15 типовых зачинов из текстов ВКР:

1. **С подлежащего (название технологии/объекта):**
   «Prophet представляет собой библиотеку для прогнозирования временных рядов.»
   «ChromaDB используется для хранения и поиска векторных представлений.»

2. **С обстоятельства места/времени:**
   «В проекте реализована мультипровайдерная архитектура.»
   «В ходе разработки выполнена миграция на PostgreSQL 16.»

3. **С целевого оборота:**
   «Для реализации системы RAG необходима модель преобразования текста.»
   «Для объективного сравнения использованы результаты бенчмарков.»

4. **С основания/причины:**
   «На основании проведённого анализа выбран Prophet.»
   «Выбор обусловлен следующими факторами: ...»

5. **С результативного оборота:**
   «Проверка показала, что Иркутск не входит в список поддерживаемых городов.»
   «Результаты двух методов согласуются, что подтверждает корректность оценки.»

6. **С причастного оборота/определения:**
   «Ранее использованная облачная СУБД заменена PostgreSQL.»
   «Разработанная модель состоит из двух сценариев.»

7. **С вводного слова:**
   «Исторически часть данных формировалась в рамках курсовой работы.»
   «Таким образом, ожидаемая длительность проекта составляет 76 дней.»

### A.3 Залог: активный vs пассивный

Соотношение: примерно 40% пассив, 60% актив. Пассив уместен для описания решений и результатов, актив для действий системы.

**Пассивный залог (описание решений):**
1. Выбран Prophet по следующим причинам.
2. Рассмотрены следующие модели.
3. Выполнена миграция на PostgreSQL 16.
4. Проведён анализ потенциальных источников.
5. Реализовано ансамблевое прогнозирование.
6. Источник отклонён.
7. Разработано семь диаграмм последовательности.
8. Обнаружен endpoint для регионального парсинга.
9. Построена отдельная диаграмма деятельности.
10. Связь Boundary–Entity запрещена.

**Активный залог (действия системы/исследователя):**
1. Система выполняет поиск релевантного контекста в ChromaDB.
2. Агент классифицирует запрос по типу.
3. APScheduler инициирует парсер по расписанию.
4. Пользователь вводит вопрос в текстовое поле.
5. Парсер запрашивает данные из внешних источников.
6. Модуль инженерии признаков генерирует 25+ фичей.
7. ChromaDB обеспечивает persistent storage.
8. FastAPI нативно поддерживает DI через Depends.
9. Ensemble объединяет прогнозы всех базовых моделей.
10. Планировщик запускает сбор данных каждые 6 часов.

### A.4 Введение технических терминов

Термин вводится **один раз**, при первом упоминании, одним из трёх способов:

**Способ 1: Термин + тире + определение**
«HNSW (Hierarchical Navigable Small World) – алгоритм приближённого поиска ближайших соседей.»

**Способ 2: Расшифровка в скобках**
«Для реализации системы RAG (Retrieval-Augmented Generation) необходима модель преобразования текста.»

**Способ 3: Определительное предложение**
«LangGraph представляет собой фреймворк для построения мультиагентных графов на основе LangChain, позволяющий создавать сложные цепочки рассуждений.»

Далее по тексту термин используется без расшифровки.

## B. ЛЕКСИКА И ФРАЗЕОЛОГИЯ

### B.1 Академические обороты (частотные)

Фразы, которые встречаются в реальных текстах ВКР. Чередовать, не повторять в соседних абзацах.

**Обоснование выбора:**
1. На основании проведённого анализа выбран ...
2. Выбор обусловлен следующими факторами: ...
3. Выбор сделан в пользу ... по следующим основаниям: ...
4. ... выбран как основной по причинам: ...
5. ... является оптимальным решением для данной задачи.
6. ... закреплён как основной LLM благодаря ...
7. Обоснование выбора: ...
8. ... отклонён из-за требований к ресурсам.
9. Альтернативы отклонены, поскольку ...
10. ... приемлем для задач прототипирования.

**Сравнение вариантов:**
1. Рассмотрены следующие модели: ...
2. Рассматривались три основных решения: ...
3. При проектировании рассматривалось два подхода: ...
4. Для объективного сравнения использованы результаты бенчмарков.
5. В отличие от IDEF0, методология IDEF3 позволяет моделировать поведение во времени.
6. Сопоставим по качеству с multilingual-e5.
7. ... уступает специализированным моделям.
8. ... в 10–100 раз превышающая Prophet.
9. Однако встроенной поддержки событий не предусмотрено.
10. Требует GPU, что выходит за рамки бюджета проекта.

**Описание процессов:**
1. В проекте реализована мультипровайдерная архитектура.
2. Выполняется автоматически по расписанию.
3. Обеспечивает актуальность данных в хранилище.
4. При обнаружении вопроса о будущем вызывается Ensemble.
5. Результат сохраняется в PostgreSQL и отображается пользователю.
6. Данные нормализуются и проходят валидацию.
7. Контекст и прогноз передаются LLM для генерации ответа.
8. Оркестрация выполняется через asyncio.gather.
9. Доступ к данным централизован через data_service.
10. Docker Compose обеспечивает развёртывание одной командой.

### B.2 Переходы между абзацами и разделами

**Начало нового раздела (от общего к частному):**
1. Для хранения данных системы используется PostgreSQL 16.
2. Диаграмма деятельности представляет собой частный случай диаграммы состояний.
3. При разработке подсистемы прогнозирования рассматривались три решения.
4. Для описания динамических аспектов системы применена методология IDEF3.
5. Техническое задание разработано в соответствии с ГОСТ 34.602-89.

**Связь с предыдущим:**
1. Исторически часть данных формировалась в рамках курсовой работы; для дипломного проекта выполнена миграция.
2. Диаграммы деятельности детализируют бизнес-процессы, выявленные на диаграмме Erikson-Penker.
3. Объекты анализа пригодности трансформируются в элементы последующих диаграмм.
4. Данная диаграмма отражает архитектурное решение о параллельном сборе.
5. Выход Процесса 1 используется Процессом 3 как источник информации.

**Выводы внутри раздела:**
1. Таким образом, ожидаемая длительность проекта составляет 76 рабочих дней.
2. Результаты двух методов согласуются, что подтверждает корректность оценки.
3. Принятый срок реализации проекта составляет 4 месяца.
4. Такой смешанный подход точно отражает реальные зависимости данных.
5. Это обеспечивает разделение представления и данных через слой логики.

## C. СТРУКТУРНЫЕ ПАТТЕРНЫ

### C.1 Начало раздела

Раздел начинается с **одного-двух предложений**, определяющих предмет и контекст. Не с абстрактного вступления, а сразу к делу.

**Шаблон:** [Предмет] + [что это] + [зачем в проекте].

Примеры:
1. «Redis – in-memory хранилище данных, используемое для кэширования API-ответов и rate limiting.»
2. «Для моделирования структуры данных информационной системы выбрана методология IDEF1X.»
3. «При разработке подсистемы прогнозирования загруженности гостиниц рассматривались три основных решения.»
4. «Диаграмма анализа пригодности представляет собой промежуточный этап между диаграммой вариантов использования и диаграммой последовательности.»
5. «Для систематизации требований к системе использована классификация Карла Вигерса.»

### C.2 Завершение раздела

Раздел завершается **конкретным выводом** или **связкой** со следующим разделом.

**Вывод-факт:**
«Принятый срок реализации проекта – 4 месяца.»

**Вывод-обоснование:**
«Выбран Prophet: наивысшая точность (85.9), поддержка событий, отсутствие требований к GPU.»

**Связка со следующим:**
«Объекты анализа пригодности трансформируются в элементы диаграмм последовательности.»
«Сценарий 1 подготавливает данные, которые использует Сценарий 2.»

### C.3 Ссылки на рисунки и таблицы

**Таблица:**
«Результаты PERT-анализа представлены в таблице N (значения в рабочих днях).»
«Для объективного сравнения использованы результаты бенчмарков (таблица N).»
«Сравнительная характеристика моделей приведена в таблице N.»

**Рисунок:**
«Диаграмма выполнена в файле ... и содержит 7 страниц.»
«Структура модели представлена на рисунке N.»
«Общая архитектура системы показана на рисунке N.»

Ссылка ставится **до** таблицы/рисунка, а не после.

### C.4 Ссылки на источники

Нумерованные квадратные скобки: [1], [2, 3], [4, с. 15].

«RAG (Retrieval-Augmented Generation) – архитектурный паттерн, комбинирующий поиск и генерацию [1].»
«Метод PERT предложен в 1958 году при разработке проекта «Поларис» [5].»
«По данным Ростуризма, ежегодный турпоток составляет более 1,5 млн человек [9].»

### C.5 Выводы по главе

Вывод по главе: 4–7 предложений. Не пересказ раздела, а синтез.

**Структура:**
1. Что сделано в главе (1 предложение).
2. Ключевые результаты/решения (2–3 предложения).
3. Значение для проекта в целом (1 предложение).

**Пример:**
«В данной главе проведён сравнительный анализ технологий и обоснован выбор стека разработки. Для серверной части выбран FastAPI с PostgreSQL 16, для прогнозирования – ансамбль из четырёх моделей (Prophet, NeuralProphet, XGBoost, LightGBM), для интеллектуального агента – LangGraph с Mistral Large. Эмбеддинги генерируются через GigaChat API, что обеспечивает высокое качество на русскоязычных текстах. Выбранный стек соответствует требованиям к производительности, масштабируемости и бюджету проекта.»

## D. АНТИ-AI МАРКЕРЫ (что делает текст «человеческим»)

### D.1 Неравномерная длина предложений

AI склонен писать предложения одной длины. Человеческий текст чередует.

**Хорошо (чередование):**
«StatsForecast реализует классические статистические модели. Её преимущество – высокая скорость обучения, в 10–100 раз превышающая Prophet. Однако встроенной поддержки событий не предусмотрено, что требует дополнительной инженерной работы.»

Здесь: 5 слов, потом 12, потом 14. Разброс.

**Плохо (однородно):**
«StatsForecast реализует классические статистические модели с высокой скоростью. Её скорость обучения превышает Prophet в 10–100 раз. Однако поддержки событий не предусмотрено в этой библиотеке.»

### D.2 Конкретные факты и числа

Человеческий текст содержит специфические числа, не округлённые. AI склонен к обобщениям.

**Хорошо:**
1. «В базе – 678 отелей (PostgreSQL).»
2. «Обнаружен endpoint /region/russia/{slug} для парсинга ~200+ отелей в 30 населённых пунктах.»
3. «1262 объекта Иркутской области у Xotelo (vs 200+ у 101Hotels).»
4. «25 типов размещения, 631 объект с рейтингом TripAdvisor.»
5. «Benchmark Score: Prophet 85.9, StatsForecast 82.6, Chronos-2 69.9.»

**Плохо:**
«В базе хранятся сотни отелей.»
«Парсер собирает множество объектов.»

### D.3 Описание реального хода работы

Вплетать повествование о ходе разработки. Это то, что AI не может придумать достоверно.

1. «Проверка показала, что Иркутск не входит в список поддерживаемых городов KudaGo.»
2. «Обнаружен endpoint для регионального парсинга (~200+ отелей).»
3. «В ходе разработки проверены провайдеры: Mistral AI, Groq, GigaChat, OpenRouter.»
4. «Ранее на этапе MVP использовалась Yandex YDB Serverless.»
5. «Исторически часть данных формировалась в рамках курсовой работы.»
6. «Единственный агрегатор с открытым JSON API без авторизации (проверено F12-анализом 30+ агрегаторов).»
7. «OpenRouter и MiMo-V2-Flash рассматривались на ранних этапах как шлюз и быстрые модели.»
8. «Для JS-heavy сайтов используется Crawl4AI; при недоступности применяется fallback через Jina Reader API.»
9. «Альтернативные агрегаторы (Ostrovok, Яндекс Путешествия, Суточно.ру) отклонены.»
10. «При этом для простого RAG-поиска используются прямые вызовы ChromaDB без абстракций LangChain.»

### D.4 Несовершенные переходы

Человеческий текст не всегда идеально гладок. Допустимы:
- Уточнение в скобках: «(проверено F12-анализом 30+ агрегаторов)»
- Ссылка на реальность: «что выходит за рамки бюджета проекта»
- Перечисление через точку с запятой вместо списка
- Неожиданное короткое предложение после длинного: «Источник отклонён.»

### D.5 Доменная терминология

Естественное использование профессионального жаргона и предметной терминологии без пояснений (после первого ввода):

1. «cross-reference данных» (а не «перекрёстная ссылка»)
2. «fallback через Jina Reader API»
3. «JS-heavy сайты»
4. «batch insert в таблицы»
5. «дедупликация по event ID»
6. «exponential backoff»
7. «sliding window rate limiting»
8. «tool calling для LangGraph»
9. «формула Хаверсина» (для сопоставления по координатам)
10. «zero-shot прогнозирование»

После первого определения термин используется свободно, как в речи разработчика, а не робота.

### D.6 Авторские оценки (осторожные)

Вместо AI-стиля «это лучшее решение» используются взвешенные формулировки:

1. «Стоимость использования приемлема для прототипа.»
2. «Избыточная обёртка не добавляет ценности для этого слоя.»
3. «Что выходит за рамки бюджета проекта.»
4. «Показывает хорошие результаты, однако уступает специализированным моделям.»
5. «Лучший баланс качества и доступного объёма.»

## E. ЧЕГО ИЗБЕГАТЬ (AI-tells)

### E.1 Одинаковые начала абзацев

**Плохо:**
> Для реализации RAG необходима модель эмбеддингов.
> Для хранения данных используется PostgreSQL.
> Для прогнозирования выбран Prophet.
> Для генерации ответов применяется Mistral.

Четыре абзаца подряд начинаются с «Для...». Системы антиплагиата фиксируют повторяющиеся паттерны.

**Хорошо:**
> Система RAG требует модель эмбеддингов для преобразования текста в векторное представление.
> Основным хранилищем данных выбран PostgreSQL 16.
> При разработке подсистемы прогнозирования рассматривались три решения.
> Mistral Large закреплён как основной LLM благодаря квоте в 1 млрд токенов.

### E.2 Идеально отполированная проза

AI пишет слишком гладко. Человеческий текст содержит:
- Вставки в скобках
- Уточнения через тире
- Ссылки на предыдущий опыт
- Упоминание конкретных инструментов проверки

### E.3 Списки одинаковой структуры

**Плохо:**
> - Prophet обеспечивает высокую точность прогнозов.
> - NeuralProphet обеспечивает нейросетевое расширение.
> - XGBoost обеспечивает gradient boosting.
> - LightGBM обеспечивает дополнительное разнообразие.

Четыре пункта, каждый начинается с «[Модель] обеспечивает...».

**Хорошо:**
> Prophet – классическая аддитивная модель с поддержкой праздников и внешних регрессоров. NeuralProphet расширяет его за счёт авторегрессии и лаговых регрессоров. XGBoost работает с 25+ инженерными признаками и поддерживает quantile regression для доверительных интервалов. LightGBM включён в ансамбль для дополнительного разнообразия прогнозов.

### E.4 Повторяющиеся конструкции

**Плохо (три «это позволяет» подряд):**
> Это позволяет обеспечить высокую производительность.
> Это позволяет упростить разработку.
> Это позволяет сократить время отклика.

**Хорошо:**
> Высокая производительность достигается за счёт асинхронности.
> Компонентный подход React упрощает разработку дашбордов.
> Время отклика сокращено благодаря кэшированию в Redis.

### E.5 Избыточное хеджирование

**Плохо:**
> Возможно, данный подход может быть потенциально полезен.

**Хорошо:**
> Подход показал свою эффективность на тестовых данных.

### E.6 Типографические маркеры AI

| Символ | Статус | Замена |
|--------|--------|--------|
| — (em dash) | Запрещён | Использовать – (en dash) или - |
| ✅ ❌ 📊 | Запрещены | Только текст |
| \| в тексте (не в таблицах) | Нежелательно | Перечисление через запятую |
| --- (горизонтальная линия) | В тексте нежелательно | Пропуск строки |
| Кавычки "" | Нежелательно | Использовать «» (ёлочки) |
