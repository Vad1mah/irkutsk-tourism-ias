<span id="_Toc225770892" class="anchor"></span>ВВЕДЕНИЕ

Иркутская область занимает особое место в системе внутреннего туризма России. По данным Росстата, регион ежегодно принимает свыше 1,5 миллиона туристов \[1\]. Озеро Байкал, включённое в список Всемирного наследия ЮНЕСКО в 1996 году, остаётся главным магнитом турпотока; стратегия развития туризма области до 2030 года предусматривает рост до 3 миллионов человек в год \[2\]. Гостиничная инфраструктура насчитывает свыше тысячи объектов размещения в 42 муниципальных районах и городских округах. Сезонность выражена резко: Ольхонский район — главный драйвер летнего потока с заполняемостью до 95 % в июле, зимой показатель падает ниже 20 %. Слюдянский район привлекает туристов круглогодично благодаря Кругобайкальской железной дороге, горнолыжному курорту «Гора Соболиная» и зимнему фестивалю «Ледовый Байкал». Подобные перепады создают для средств размещения серьёзную проблему ценообразования и кадрового планирования.

Данные о заполняемости рассредоточены по десяткам агрегаторов бронирования. Каждый из них охватывает лишь часть рынка и отдаёт информацию в собственном формате без открытых программных интерфейсов (API, Application Programming Interface). Нами проведён анализ более 30 российских платформ — Ostrovok, Sutochno, Яндекс.Путешествия, TVIL, Bronevik и других — который выявил единственный сервис с открытым API: 101Hotels возвращает данные в формате JSON (JavaScript Object Notation) без авторизации \[3\]. Остальные агрегаторы защищены антибот-системами либо требуют партнёрского договора. Классические методы прогнозирования — ARIMA (AutoRegressive Integrated Moving Average), метод Хольта–Уинтерса — не располагают штатными механизмами учёта событийной активности и погодных факторов, что ограничивает их применимость к специфике Байкальского региона.

Проблему усиливает отсутствие визуально-аналитических инструментов. Управляющие компании принимают решения на основе субъективных оценок, а региональные органы туризма не располагают оперативной картиной заполняемости номерного фонда в масштабе области. Готовые решения, ориентированные именно на Иркутскую область, в ходе проведённого анализа не обнаружены.

**Актуальность** работы определяется потребностью в интеллектуальной аналитической системе (ИАС), способной автоматически собирать данные из доступных источников, обогащать их событийной и метеорологической информацией, строить ансамблевые прогнозы заполняемости и предоставлять результаты через веб-интерфейс с продуманной информационной архитектурой и диалоговым агентом на основе большой языковой модели (LLM, Large Language Model).

**Объект исследования** — рынок средств размещения Иркутской области.

**Предмет исследования** — методы автоматизированного сбора, визуального анализа и прогнозирования заполняемости средств размещения с применением ансамблей моделей машинного обучения, интеллектуальных агентов и средств информационного дизайна.

**Цель работы** — проектирование и разработка интеллектуальной аналитической системы прогнозирования заполняемости средств размещения с интерфейсом визуальной аналитики на основе данных туристических агрегаторов и событийной активности в регионе.

Для достижения поставленной цели определены следующие **задачи**.

1.  Исследовать предметную область мониторинга туристической активности и провести анализ существующих аналитических решений.

2.  Обосновать выбор технологий, дизайн-инструментов и средств визуализации данных для разработки системы.

3.  Спроектировать и реализовать подсистему автоматизированного сбора данных из туристических агрегаторов и порталов событий.

4.  Разработать ансамблевый метод прогнозирования заполняемости средств размещения и модуль его реализующий с визуальной аналитикой результатов.

5.  Спроектировать архитектуру интеллектуальной аналитической системы (ИАС) и реализовать систему, ее взаимодействие с интеллектуальным агентом и веб-интерфейс.

**Методы исследования**: системный анализ предметной области, сравнительный анализ технологий и средств визуализации, объектно-ориентированное проектирование, проектирование информационной архитектуры, итеративное прототипирование пользовательского интерфейса (UI, User Interface), методы машинного обучения (градиентный бустинг, нейросетевые модели временных рядов, ансамблирование), экспериментальная оценка качества прогнозов на реальных данных.

**Научная новизна** работы состоит в разработке ансамблевого подхода к прогнозированию заполняемости средств размещения, объединяющего три модели различной природы (Prophet, NeuralProphet, XGBoost) с адаптивными весами на основе обратной среднеквадратичной ошибки (inverse-RMSE, Root Mean Square Error). Для Иркутской области впервые реализована интеграция данных о событийной активности и метеорологических факторов как экзогенных переменных ансамблевого прогноза. Среднеквадратичная ошибка ансамбля составила 3,85 п.п. для Иркутского района при лучшем одиночном результате 6,43 п.п. Предложен подход к информационному дизайну туристической аналитики, опирающийся на принципы визуальной иерархии и снижения когнитивной нагрузки. Разработана архитектура интеллектуального агента на базе графа состояний LangGraph с пятью инструментами для диалогового доступа к аналитике на естественном языке.

**Практическая значимость** работы определяется тем, что разработанная ИАС в автоматическом режиме собирает данные о заполняемости объектов размещения Иркутской области, формирует ансамблевые прогнозы на горизонте 3–90 дней и визуализирует результаты на восьми интерактивных страницах: панель мониторинга (дашборд) ключевых показателей эффективности, временные ряды заполняемости, тепловые карты, радарные диаграммы регионов, географическая карта отелей. Веб-интерфейс спроектирован по принципам UX-дизайна (User Experience, пользовательский опыт): информационная архитектура «от общего к частному», адаптивная вёрстка, тёмная и светлая темы, чат-интерфейс AI-агента с подсказками по модели conversational UI (диалоговый интерфейс). Система адресована управляющим компаниям гостиничной отрасли для оптимизации ценообразования и региональным органам управления туризмом для оперативного мониторинга.

<span id="_Toc225770893" class="anchor"></span>1 ИССЛЕДОВАНИЕ МЕТОДОВ МОНИТОРИНГА И ПРОГНОЗИРОВАНИЯ ЗАПОЛНЯЕМОСТИ СРЕДСТВ РАЗМЕЩЕНИЯ

<span id="_Toc225770894" class="anchor"></span>1.1 Мониторинг туристической активности: задачи и существующие решения

Мониторинг туристической активности представляет собой систематический процесс сбора, обработки и анализа данных о перемещениях и поведении туристов, состоянии инфраструктуры размещения и факторах, влияющих на спрос. Заполняемость (occupancy rate) – процент занятых номеров от общего номерного фонда – выступает центральным показателем гостиничного сектора. Этот индикатор определяет выручку объекта размещения и позволяет оценить спрос и туристическую привлекательность территории на его основе. Помимо заполняемости, задачи мониторинга охватывают отслеживание средней стоимости номера (ADR, Average Daily Rate), дохода на доступный номер (RevPAR, Revenue per Available Room), структуры спроса по каналам бронирования и сезонных колебаний.

Иркутская область – один из ведущих туристических регионов Сибири \[38\]. Территория охватывает 42 муниципальных района и городских округа, из которых 15 имеют выраженную туристическую специализацию: Иркутский, Ольхонский, Слюдянский, Листвянский (в составе Иркутского района), Байкальский и другие. Географическая неоднородность порождает различные модели спроса. Ольхонский район демонстрирует резкую сезонность с пиками в июле-августе и январе-марте (ледовый сезон Байкала) \[38\]. Иркутский район с деловым туризмом областного центра характеризуется более равномерной заполняемостью. Слюдянский район привлекает транзитных туристов на маршруте Кругобайкальской железной дороги (КБЖД) и горнолыжном курорте «Гора Соболиная» \[38\] преимущественно в тёплый сезон и зимний период соответственно.

Сезонные закономерности (паттерны) заполняемости осложняются влиянием экзогенных факторов. Государственные праздники и школьные каникулы формируют предсказуемые всплески: новогодние каникулы (31 декабря – 8 января), майские праздники, июньские выпускные. Культурные и спортивные события – фестиваль «Байкальская миля», «Зимниада», международный фестиваль «Звёзды на Байкале» \[38\] – создают локальные пики, ограниченные конкретными районами и датами. Погода оказывает нетривиальное воздействие: аномально тёплая зима сокращает период ледовых экскурсий, а затяжные дожди летом снижают поток в палаточные лагеря, перераспределяя спрос в пользу капитальных средств размещения. Совокупное влияние перечисленных факторов делает задачу мониторинга многомерной – учёт одного лишь календаря недостаточен для прогнозирования спроса.

Обзор существующих решений для мониторинга гостиничной заполняемости выявляет несколько категорий систем. Корпоративные платформы управления доходами (Revenue Management Systems, RMS) – IDeaS, Duetto, RateGain – ориентированы на крупные гостиничные сети. Они работают с внутренними данными PMS (Property Management System) конкретного объекта, используют алгоритмы динамического ценообразования и оптимизации доходности. Стоимость лицензии начинается от нескольких тысяч долларов в месяц \[4\]. Для малых средств размещения, составляющих основу гостиничного рынка Прибайкалья, такие затраты несопоставимы с годовой выручкой. Кроме того, RMS не работают с открытыми данными агрегаторов и не учитывают региональный событийный календарь.

Аналитические дашборды агрегаторов бронирования предоставляют ограниченную статистику партнёрам. Airbnb публикует AirDNA \[39\] – платформу с данными о заполняемости и ценах краткосрочной аренды, ориентированную на рынок P2P-аренды (Peer-to-Peer, одноранговая модель). Booking.com через Analytics Dashboard показывает конверсии и тренды спроса для зарегистрированных объектов. Инструменты охватывают исключительно собственную базу объявлений (листингов), не интегрируют внешние факторы и не предоставляют прогностических возможностей. Для региона с сотнями средств размещения на десятках платформ такая фрагментация означает неполноту картины.

Государственная система «Электронная путёвка» \[40\] (Единая информационная система электронных путёвок, ЕИСЭП) и ведомственные мониторинги Ростуризма (ныне – Министерства экономического развития) оперируют агрегированными квартальными данными. Оперативной информации о заполняемости в разрезе объектов или районов они не предоставляют. Для принятия решений о ценообразовании, которые требуются ежедневно, такая периодичность неприемлема.

Из аналитических платформ общего назначения применяются Yandex DataLens и Google Looker Studio. DataLens строит визуализации на основе произвольных источников данных и использовался на ранних этапах разработки описываемой системы. Зависимость от облачной инфраструктуры Yandex Cloud и ограниченные возможности кастомизации интерактивных элементов (всплывающие подсказки (тултипы), вложенные фильтры, адаптивность под мобильные устройства) потребовали перехода к встроенным визуализациям на базе React-библиотек \[5\]. Google Travel Insights предоставляет агрегированную статистику поисковых запросов по направлениям, но не содержит данных о фактической заполняемости и не покрывает российский сегмент в полном объёме после 2022 года.

Ограничения перечисленных решений сводятся к трём проблемам:

- ни одна из существующих платформ не агрегирует данные о заполняемости средств размещения в масштабе региона — каждая работает с собственной, неполной базой;

- прогнозные модули коммерческих RMS не учитывают специфику регионального событийного календаря и метеорологических условий Прибайкалья;

- стоимость корпоративных решений несопоставима с бюджетами малых гостиничных объектов, преобладающих в регионе.

Для оценки доступности данных нами проведён анализ программных интерфейсов российских агрегаторов методом обратной инженерии: перехват HTTP-запросов (HyperText Transfer Protocol, протокол передачи гипертекста) через инструменты разработчика браузера (F12-подход). Разрабатываемая система должна агрегировать разнородные источники, учитывать экзогенные факторы (погода, события, праздники) и предоставлять прогнозные оценки через веб-интерфейс, спроектированный с учётом принципов информационного дизайна и визуальной иерархии.

FastAPI выбран по совокупности факторов. Нативная асинхронность на базе стандарта ASGI (Asynchronous Server Gateway Interface) обрабатывает десятки одновременных запросов к внешним API парсеров и LLM-провайдерам без блокировки. Встроенная интеграция с Pydantic v2 гарантирует типизированную валидацию входных данных — критично для API с 59 endpoint-ами \[8\]. Автогенерация интерактивной документации API (Swagger UI) по аннотациям типов упрощает тестирование без дополнительных зависимостей. Django, обладая зрелой экосистемой, избыточен: встроенная ORM (Object-Relational Mapping), шаблонизатор и административная панель не используются, а шаблон MTV (Model-Template-View) привносит ограничения. Flask потребовал бы ручной настройки асинхронности, валидации и документации через сторонние расширения.

Система управления базами данных. Выбор СУБД определялся историей проекта. На начальном этапе использовалась YDB – распределённая СУБД Яндекса в Yandex Cloud. Миграция на PostgreSQL 16 выполнена в феврале 2026 года по трём причинам:

- локальное развёртывание без зависимости от облачного провайдера;

- асинхронный драйвер asyncpg с высокой пропускной способностью;

- необходимость полноценной ORM (SQLAlchemy 2.0).

YDB при всех достоинствах распределённой архитектуры оказалась избыточной для масштаба проекта (менее 40 тысяч записей) и создавала единую точку отказа в виде облачного сервиса.

SQLAlchemy 2.0 используется как ORM-слой с асинхронными сессиями. Модель данных включает пять таблиц: Hotel, HotelStatistic, Event, QueryHistory, Forecast. Связи обеспечены внешними ключами с каскадным удалением, ограничения CHECK контролируют допустимые диапазоны значений (occupancy 0–100%, rating 0–10).

Кэширование и rate limiting. Redis 7 применяется в двух ролях: кэширование ответов ресурсоёмких endpoint-ов и ограничение частоты запросов по алгоритму скользящего окна (sliding window). Прогнозные endpoint-ы кэшируются с TTL (Time to Live) 30 минут, аналитические – 15 минут. Rate limiting ограничивает обращения к AI-агенту десятью запросами в минуту на IP-адрес (Internet Protocol, межсетевой протокол). При недоступности Redis система переключается на резервный механизм (fallback) в оперативной памяти на базе словарей Python \[10\].

Инфраструктура развёрнута через Docker Compose: PostgreSQL 16, Redis 7 и контейнеры приложения. Обратный прокси-сервер nginx обслуживает статические файлы, проксирует API-запросы и обеспечивает заголовки безопасности \[11\]. Детальная конфигурация инфраструктуры приведена в приложении Б.

Планировщик задач. Для периодического сбора данных выбран APScheduler — встраиваемый в процесс планировщик, не требующий отдельного брокера сообщений. Альтернатива — Celery — предполагает запуск отдельного рабочего процесса и брокера (RabbitMQ или Redis), что избыточно для единственного сервера с четырьмя периодическими задачами. При росте нагрузки миграция на Celery возможна без изменения логики задач.

Безопасность API реализована на четырёх уровнях \[12\]:

- аутентификация через API-ключ для парсерных конечных точек;

- ограничение частоты запросов (rate limiting) через Redis с резервным механизмом в оперативной памяти;

- типизированная валидация входных данных через Pydantic;

- защита от SQL-инъекций: экранирование спецсимволов в LIKE-выражениях.

Детальное описание механизмов безопасности вынесено в приложение Б.

Перечисленные серверные технологии образуют инфраструктуру обработки данных — конвейер от сбора и хранения до прогнозирования и кэширования результатов. Не менее значима клиентская часть, отвечающая за визуализацию результатов и взаимодействие с пользователем.

React 18 выбран благодаря доминирующей экосистеме компонентов для визуализации данных \[13\]. Recharts и ECharts предоставляют полный набор типов диаграмм, необходимых для аналитического дашборда: AreaChart, BarChart, LineChart, RadarChart, Treemap, GeoMap. Vue 3 с vue-echarts покрывает часть потребностей, но отсутствует аналог Recharts с декларативным JSX-синтаксисом (JavaScript XML). Svelte 5, при элегантности реактивной модели, не располагает зрелой библиотекой для географических визуализаций, что критично для страницы «Регионы и карта».

Сборщик Vite 7 выбран вместо webpack по причине скорости: dev-сервер стартует за 300 мс благодаря нативной поддержке ES-модулей, горячая замена модулей (Hot Module Replacement, HMR) обновляет компонент за 50 мс \[14\]. Webpack в сопоставимой конфигурации требует 8–12 секунд на холодный старт и 1–2 секунды на HMR, что существенно замедляет итеративную разработку интерфейса. Итоговая сборка (production) Vite включает удаление неиспользуемого кода (tree-shaking), разделение на фрагменты по маршрутам (code splitting) и минификацию.

Tailwind CSS (Cascading Style Sheets, каскадные таблицы стилей) 4 — утилитарный CSS-фреймворк, генерирующий стили на основе используемых классов \[15\]. Утилитарный подход (utility-first) позволяет строить дизайн-систему на CSS-переменных, что гарантирует визуальную согласованность всех компонентов. Тёмная и светлая темы реализованы через переопределение переменных без дублирования стилей. Набор компонентов — Button (четыре варианта), Card, Badge, Input, Dropdown, ErrorState — образует атомарную дизайн-систему с единообразными радиусами скругления, тенями и отступами. Данная структура следует методологии Atomic Design, разработанной Б. Фростом \[16\]. Методология выстраивает иерархию компонентов по пяти уровням: атомы (минимальные элементы – кнопка, поле ввода), молекулы (функциональные группы атомов – например, строка поиска из кнопки и текстового поля), организмы (самостоятельные секции интерфейса – панель KPI, блок фильтров), шаблоны (скелеты страниц без данных) и страницы (конкретные реализации шаблонов с реальным контентом). При добавлении новой аналитической страницы элементы не создаются с нуля — достаточно комбинации существующих атомов и молекул.

Принято решение использовать две библиотеки совместно. Recharts применяется для 90% графиков (AreaChart, BarChart, LineChart, RadarChart, Treemap, ComposedChart) благодаря декларативному JSX-синтаксису и малому размеру \[17\]. ECharts подключён исключительно для GeoMap — пузырьковой карты отелей с GeoJSON-контуром Иркутской области на странице «Регионы и карта» \[18\]. Разделение обосновано: Recharts удобнее для типовых графиков, а ECharts – единственная из рассмотренных библиотек с полноценной поддержкой точечной географической диаграммы (scatter-geo) на произвольном формате географических данных GeoJSON без привлечения D3. Chart.js отклонён из-за отсутствия нативной поддержки географических карт и Treemap. D3.js потребовал бы ручной реализации каждого компонента – трудозатраты, не оправданные для прикладного проекта.

Методология проектирования архитектуры ИАС опирается на два взаимодополняющих принципа. Progressive disclosure (постепенное раскрытие) предполагает, что пользователь вначале получает упрощённое представление, а экспертные детали становятся доступны по запросу. Б. Шнейдерман формализовал этот подход в мантре визуальной аналитики: «сначала обзор, затем масштабирование и фильтрация, далее — детали по требованию» \[19\]. Восьмистраничная структура пользовательского интерфейса системы реализует оба принципа: «Главная» предоставляет обзорную сводку по району, «Аналитика» позволяет масштабировать и фильтровать данные через KPI и временные ряды, «Карточка отеля» раскрывает детали конкретного объекта размещения. Такая последовательность снижает когнитивную нагрузку – пользователь не сталкивается с полным объёмом данных на первом экране, а погружается в аналитику постепенно.

Управление серверным состоянием реализовано через TanStack React Query \[20\]. Библиотека берёт на себя кэширование ответов API, ревалидацию при возврате фокуса окна, повторные попытки при сетевых ошибках и дедупликацию параллельных запросов. Время жизни кэша дифференцировано: дольше для справочных данных (отели, события), короче для аналитических (прогнозы, KPI) и без кэширования для чат-запросов. Это устраняет типовые проблемы рассогласования данных между компонентами.

<span id="_Toc225770896" class="anchor"></span>1.3 Обоснование выбора методов прогнозирования и фреймворков реализации интеллектуального агента

Задача прогнозирования заполняемости средств размещения формулируется как предсказание процента занятых номеров на горизонте 3–90 дней с учётом календарных, погодных и событийных факторов. Ряд заполняемости характеризуется выраженной недельной сезонностью (пик в пятницу-субботу), годовой сезонностью (зима и лето), влиянием праздников и событий, а также потенциальными пропусками в наблюдениях. Объём накопленных данных – около года; детализация по числу записей приведена при описании базы данных. Это ограничивает применимость ряда методов.

Классические статистические методы. ARIMA и её сезонное расширение SARIMA моделируют ряд через авторегрессию, дифференцирование и скользящее среднее. Подбор порядков (p, d, q) и сезонных параметров (P, D, Q)s требует анализа автокорреляционной функции, что трудоёмко при масштабировании на 15 районов. Базовая формулировка не включает внешние регрессоры; расширение SARIMAX (SARIMA with eXogenous variables, сезонная модель с экзогенными переменными) допускает их, но при коротких рядах возрастает риск переобучения. Метод Хольта–Уинтерса поддерживает только одну сезонную частоту. На практике эти методы протестированы, но отвергнуты из-за невозможности штатной интеграции погоды, событий и праздников без построения отдельных конвейеров для каждого района.

Prophet. Модель Meta (Facebook) представляет ряд как аддитивную декомпозицию (1), где g(t) – тренд, s(t) – сезонные компоненты (ряды Фурье), h(t) – эффект праздников, ε(t) — шум \[21\]. Встроенная поддержка российских праздников (через библиотеку holidays) и внешних регрессоров (temperature, precipitation из Open-Meteo) делает модель пригодной для данного проекта без дополнительных инженерных усилий. Prophet устойчив к пропускам, не требует стационарности и автоматически определяет точки перелома тренда.

``` math
\begin{array}{r}
y(t) = \ g(t) + \ s(t) + \ h(t) + \ \varepsilon(t)\#(1)
\end{array}
```

NeuralProphet. Расширение Prophet на базе PyTorch, добавляющее нейросетевой компонент авторегрессии (AR Network) и лаговые регрессоры \[22\]. В отличие от Prophet, NeuralProphet принимает лаговые значения температуры через add_lagged_regressor, обучая индивидуальные веса для каждого лага. Модель улавливает задержку влияния погоды на спрос: прогноз хорошей погоды за 3–5 дней увеличивает число бронирований.

XGBoost и LightGBM. Градиентный бустинг решающих деревьев формирует прогноз как сумму слабых моделей (2) \[23\]. В системе модуль FeatureEngineeringService генерирует 38 признаков восьми категорий: календарные, праздничные, лаговые, скользящие статистики, погодные, событийные, трендовые и ценовые. Помимо стандартной модели, XGBoost обучается с квантильной регрессией для построения доверительных интервалов без параметрических предположений. LightGBM включён как альтернатива со стратегией построения по листьям (leaf-wise), вносящей разнообразие в прогнозы.

``` math
\begin{array}{r}
F(x) = \ \Sigma\ fₖ(x)\#(2)
\end{array}
```

Ансамблевый подход. Отдельные модели обладают различными сильными сторонами: Prophet точнее на гладких рядах с выраженной сезонностью, NeuralProphet – на рядах с автокорреляцией благодаря лаговым регрессорам, XGBoost – при информативных событийных и погодных признаках. Ансамбль объединяет прогнозы методом inverse-RMSE (3), что присваивает больший вес более точной модели. Теоретическое обоснование ансамблирования состоит в снижении дисперсии: объединение некоррелированных прогнозов уменьшает общую ошибку даже при отсутствии улучшения смещения. Экспериментальная оценка качества моделей на данных Иркутской области приведена в разделе 2.2.

``` math
\begin{array}{r}
w_{i} = \frac{\frac{1}{RMSE_{i}}}{\sum_{j}^{}\left( \frac{1}{RMSE_{j}} \right)}\#(3)
\end{array}
```

В системе проиндексировано свыше тысячи документов.

Выбор LLM-провайдера. Система поддерживает шесть провайдеров (Mistral, GigaChat, Groq, DeepSeek, OpenRouter, Gemini) с переключением через единственную переменную окружения LLM_PROVIDER. Groq и Gemini требуют VPN (виртуальную частную сеть) для доступа из РФ — при тестировании обнаружена блокировка Groq с российских IP через Cloudflare \[26\]. GigaChat используется для эмбеддингов русскоязычных текстов (GigaChatEmbeddings от Сбера) – модель оптимизирована для русского языка и показывает лучшее качество семантического поиска по описаниям отелей по сравнению с мультиязычными моделями.

Исследование предметной области мониторинга туристической активности выявило три проблемы: фрагментацию данных по десяткам агрегаторов без открытых API, отсутствие интеграции событийных и метеорологических факторов в существующих платформах, недоступность коммерческих RMS для малого гостиничного бизнеса Прибайкалья. Технологический стек сформирован на основе сравнительного анализа: FastAPI для асинхронной серверной части (бэкенда) с 59 endpoint-ами, PostgreSQL 16 с asyncpg для локального развёртывания, React 18 с TypeScript для клиентской части с аналитическими панелями. Recharts и ECharts обеспечивают визуализацию 90% графиков и географическую карту соответственно. Tailwind CSS 4 формирует атомарную дизайн-систему с поддержкой тёмной и светлой тем.

Обоснован ансамблевый подход, объединяющий Prophet, NeuralProphet и XGBoost с адаптивными весами inverse-RMSE для снижения дисперсии прогноза. Интеллектуальный агент на LangGraph с пятью инструментами и RAG-конвейером на ChromaDB с эмбеддингами GigaChat предоставляет аналитику на естественном языке. Mistral Large выбран основным LLM-провайдером благодаря лимиту в 1 миллиард токенов и качественной русскоязычной генерации.

<span id="_Toc225770899" class="anchor"></span>2.1 Архитектура системы и подсистема сбора данных

Проектируемая информационно-аналитическая система (ИАС) мониторинга туристической активности Иркутской области построена по клиент-серверной архитектуре с модульным серверным ядром. Выбор монолитной модульной архитектуры, а не микросервисной, обусловлен масштабом проекта: система обслуживает один регион с прогнозируемой нагрузкой до нескольких тысяч запросов в сутки, и накладные расходы на оркестрацию контейнеров, сервисную шину и распределённые транзакции не оправданы. Модульность достигается разделением серверной части на изолированные слои: маршрутизаторы запросов (роутеры), бизнес-логика (services), доступ к данным (db), модели данных (models), парсеры (parsers), промежуточное ПО (middleware) и зависимости (dependencies). Три основных слоя архитектуры – клиентское SPA-приложение, модульное серверное ядро и инфраструктурные сервисы (PostgreSQL, Redis, ChromaDB) – показаны на рисунке 1.

Рисунок 1 – Общая архитектура информационно-аналитической системы

Исторически на этапе курсовой работы использовалась Yandex YDB Serverless – облачная документо-ориентированная СУБД. В ходе производственной практики принято решение о миграции на PostgreSQL 16 для обеспечения возможности локальной разработки, внедрения полноценного ORM и достижения независимости от облачного провайдера. Миграция выполнена в феврале 2026 года: переписаны ORM-модели на SQLAlchemy 2.0, заменён драйвер с YDB SDK на asyncpg, схема данных приведена к реляционной модели с внешними ключами и CHECK-ограничениями. Время отклика на типовых запросах сократилось примерно втрое по сравнению с облачной YDB, а локальное развёртывание через Docker Compose устранило зависимость от внешнего облачного провайдера.

Серверная часть реализована на FastAPI — асинхронном Python-фреймворке, обоснование выбора которого приведено в разделе 1.2. Фреймворк нативно поддерживает async/await, что критично для системы с интенсивным вводом-выводом: одновременные HTTP-запросы к внешним API, обращения к базе данных и вызовы LLM-провайдеров. Серверная часть содержит 7 роутеров, объединяющих 59 конечных точек API:

- hotels (3) — список, детали и статистика отелей;

- events (6) — каталог и управление событиями;

- query (5) — AI-агент и потоковая передача;

- forecast (9) — ансамблевый и покомпонентный прогнозы;

- documents (5) — управление документами RAG-конвейера;

- parser (12) — запуск и мониторинг парсеров;

- analytics (17) — KPI, корреляции, тепловая карта, данные для визуализаций;

- 2 корневых (health, root).

Роутер analytics предоставляет endpoint для дашборда ключевых показателей эффективности (KPI, Key Performance Indicators), тепловой карты заполняемости, корреляционного анализа, агрегированных данных по отелям и районам (в том числе для картографической визуализации на странице «Регионы и карта») и сравнения районов.

Клиентская часть – одностраничное приложение (SPA) на React 18 с TypeScript, взаимодействующее с сервером через REST API и Server-Sent Events (SSE) для потоковых ответов интеллектуального агента \[27\]. Обратный прокси-сервер nginx выполняет маршрутизацию запросов, сжатие статических ресурсов и поддержку SSE-соединений. Политика общего происхождения ресурсов (CORS, Cross-Origin Resource Sharing) ограничивает источники запросов доменом клиентской части (фронтенда).

Инфраструктурный слой включает три компонента:

- PostgreSQL 16 — основная СУБД для хранения отелей, статистики и событий;

- Redis 7 — кэширование ответов и ограничение частоты запросов;

- ChromaDB — хранение векторных представлений документов для RAG-конвейера.

Все инфраструктурные компоненты развёрнуты в Docker-контейнерах через Docker Compose \[28\]. Конфигурация предусматривает два режима: по умолчанию запускаются только PostgreSQL и Redis (для локальной разработки серверной и клиентской частей); профиль full добавляет контейнеры серверной и клиентской частей для развёртывания в рабочем окружении. Контейнеры оснащены проверками работоспособности (healthcheck), секреты передаются через переменные окружения, процессы запускаются от непривилегированного пользователя (non-root) для снижения поверхности атаки.

Схема базы данных спроектирована на основе реляционной модели и реализована средствами SQLAlchemy 2.0 ORM с асинхронным драйвером asyncpg \[29, 30\]. Асинхронный драйвер обрабатывает несколько запросов к БД параллельно, не блокируя цикл обработки событий FastAPI. База содержит пять таблиц с чётко определёнными связями и ограничениями целостности. Первичный ключ формируется хешированием заголовка, даты начала и идентификатора источника, что гарантирует идемпотентность: одно и то же событие из разных порталов не создаст дубликат. Результаты прогнозирования хранятся в Forecast: район, дата, предсказанная заполняемость, имя модели и границы доверительного интервала. Хранение прогнозов позволяет ретроспективно сравнивать качество моделей и отдавать кэшированные результаты без повторных вычислений.

Подсистема сбора данных решает три задачи: извлечение информации о мероприятиях из восьми источников, получение статистики средств размещения с агрегатора 101Hotels и загрузка метеорологических данных из Open-Meteo. Все парсеры наследуют базовый класс BaseParser, определяющий единый интерфейс и общую логику \[31\].

BaseParser реализует единый интерфейс для всех парсеров: управление HTTP-сессиями, автоматические повторные попытки с экспоненциальной задержкой при ошибках сервера, ротацию заголовка User-Agent для противодействия блокировке (anti-detection). Конфигурация парсеров (таймауты, число попыток, задержки) вынесена в отдельный объект настроек.

Восемь парсеров событий покрывают основные информационные источники: irk.ru (городской портал Иркутска, HTML-парсинг через BeautifulSoup), culture38 (сайт министерства культуры Иркутской области), zeroevent (афиша мероприятий), yandex (Яндекс.Афиша), kassir (билетный сервис), culture_rf (федеральный портал «Культура.РФ»), telegram (каналы через Telethon API) и major (крупные площадки). Каждый возвращает унифицированный список событий с обязательной валидацией: название, дата начала и тип мероприятия проверяются при парсинге. Telegram-парсер представляет особый случай: сообщения из каналов содержат не только анонсы мероприятий, но и поздравления, рекламу, новости. Реализована LLM-классификация сообщений, отсеивающая нерелевантный контент (поздравления, реклама) на этапе парсинга.

Парсер средств размещения работает с JSON API агрегатора 101Hotels.com \[32\]. Конечная точка ssg.101hotels.com/hotel/available/city/russia/{slug} принимает символьный идентификатор города (slug) и возвращает JSON с информацией о доступности номеров для конкретного населённого пункта. 101Hotels выбран по итогам анализа агрегаторов, описанного в разделе 1.1. Парсер последовательно обходит 15 районов Иркутской области: Иркутский, Ольхонский, Слюдянский, Ангарский, Листвянка (Иркутский район), Байкальск (Слюдянский район) и другие. Для перекрёстной верификации данных реализован дополнительный парсер Xotelo, получающий рейтинги и количество отзывов TripAdvisor путём перекрёстной сверки (cross-reference) по названию и координатам отеля.

Метеорологические данные поступают из Open-Meteo API, описанного в разделе 1.1. Сервис предоставляет бесплатный доступ без ключа авторизации с лимитом 10 000 запросов в день (условия зафиксированы в проектной документации на дату обращения 22.03.2026). Запрашиваются суточные параметры: максимальная и минимальная температура воздуха, осадки, скорость ветра и код погоды по классификации WMO (World Meteorological Organization). Координаты запросов соответствуют центрам 15 районов. Горизонт прогноза погоды – 14 дней.

Автоматизация сбора реализована через APScheduler с асинхронным планировщиком AsyncIOScheduler \[33\]. Четыре периодические задачи запускаются по расписанию:

- средства размещения — каждые 2 часа;

- события из восьми источников — каждые 6 часов;

- метеорологические данные — каждые 3 часа;

- Telegram-каналы — каждый час.

Периодичность определена экспериментально: интервал в 2 часа для отелей достаточен для фиксации внутридневных колебаний доступности без превышения лимитов API; 6-часовой интервал для событий достаточен, поскольку культурные мероприятия обновляются не чаще раза в сутки. При запуске планировщик выполняет начальный сбор всех типов данных, затем работает по расписанию.

Нормализация данных выполняется на этапе парсинга. Названия районов приводятся к каноническому виду (например, «Иркутский район» в «Иркутский»). Дедупликация событий осуществляется по первичному ключу event_id, формируемому из хеша заголовка, даты и источника, – повторная вставка приводит к обновлению существующей записи, то есть выполняется операция «вставка или обновление» (upsert). Для отелей применяется аналогичная стратегия через ON CONFLICT DO UPDATE в PostgreSQL. Пакетная вставка (batch insert) через ORM загружает до нескольких тысяч записей за одну транзакцию с автоматическим разрешением конфликтов (upsert).

Мониторинг парсеров отслеживает время последнего успешного запуска, количество собранных записей и процент ошибок. При деградации источника (изменение структуры страницы, блокировка) оператор получает уведомление через API статистики.

Доступ к данным централизован через сервисный слой, абстрагирующий операции чтения и записи для всех таблиц. Роутеры не содержат прямых SQL-запросов, что упрощает замену СУБД или добавление кэширующего слоя.

<span id="_Toc225770900" class="anchor"></span>2.2 Модуль прогнозирования и интеллектуальный агент

Прогнозирование заполняемости средств размещения основано на ансамблевом подходе, объединяющем три модели: Prophet, NeuralProphet и XGBoost (LightGBM включён в XGBoost-сервис). Каждая модель обладает собственными достоинствами в отношении типов зависимостей, которые она способна моделировать. Объединение их прогнозов снижает дисперсию и повышает устойчивость результата. Перед подачей данных в модели выполняется инженерия признаков (feature engineering) – процесс преобразования исходных временных рядов в набор числовых характеристик.

Для повышения наглядности конвейер ансамблевого прогнозирования (параллельный запуск моделей, объединение и построение доверительного интервала) представлен на рисунке 10.

Модуль FeatureEngineering генерирует 38 признаков, разделённых на восемь групп:

1)  календарные (8 шт.) — день недели, месяц, квартал, номер недели, признаки выходных и границ месяца. Заполняемость в пятницу и субботу в среднем на 12–18 п.п. выше, чем в середине рабочей недели;

2)  праздничные (5 шт.) — факт праздника, расстояние до ближайшего и от последнего праздника, принадлежность к длинным выходным, сезон;

Под длинными выходными в работе понимаются периоды из трёх и более подряд идущих нерабочих дней, возникающие за счёт официальных праздничных дней и переноса выходных (например, новогодние и майские праздники).

3)  лаговые (7 шт.) — автокорреляция ряда заполняемости на горизонтах от одного дня до трёх месяцев;

4)  скользящие статистики (5 шт.) — средние, стандартное отклонение, минимум и максимум в окнах 7 и 30 дней;

5)  погодные (4 шт.) — температура, осадки, скорость ветра, код погоды из Open-Meteo. Корреляция между температурой и заполняемостью в Ольхонском районе летом достигает 0,42;

6)  событийные (3 шт.) — количество мероприятий за день и неделю, наличие крупного события;

7)  трендовые (2 шт.) — долгосрочная динамика рынка;

8)  ценовые (4 шт.) — текущая стоимость и её недельное изменение.

Полный перечень признаков (группа, признак, тип данных, описание/возможные значения) приведён в Приложении Г (таблица Г.1). Таблица вынесена в приложение, поскольку используется для воспроизведения модели и удобнее воспринимается в виде структурированного перечня.

При отсутствии данных за конкретную дату применяется подстановка среднемесячных значений, рассчитанных по имеющимся историческим наблюдениям.

Реализация Prophet (модель описана в разделе 1.3) включает годовую и недельную сезонность с рядами Фурье. Российские праздники задаются явным списком с окном влияния в несколько дней до и после даты: система учитывает период, когда спрос начинает расти заранее. Температура и осадки подключены как внешние регрессоры через метод add_regressor. Обучение занимает 2–5 секунд на данных одного района.

В реализации NeuralProphet (раздел 1.3) параметр n_lags установлен в 14 — двухнедельное окно авторегрессии, подобранное экспериментально перебором значений от одной до четырёх недель. Погода и события подключены как лаговые регрессоры через add_lagged_regressor, а не как обычные: нейросеть обучает индивидуальные веса для каждого лага. Активирована ранняя остановка (early_stopping) для предотвращения переобучения. Время обучения — 10–15 секунд.

XGBoost и LightGBM (описание в разделе 1.3) реализованы как модели на основе метода градиентного бустинга для табличных данных, обучаемые на 38 признаках модуля FeatureEngineering. Для построения доверительных интервалов обучаются три модели: стандартная (squared error) для точечного прогноза и две квантильные (reg:quantileerror, квантили 0,1 и 0,9) для нижней и верхней границ 80-процентного интервала. LightGBM обучается параллельно внутри того же сервиса как альтернативная реализация градиентного бустинга.

Реализована квантильная регрессия (quantile regression) для построения доверительных интервалов: помимо стандартной модели XGBoost (squared error), обучается квантильная модель с функцией потерь reg:quantileerror для квантилей 0.1 и 0.9. Стандартная модель даёт точечный прогноз, квантили 0.1 и 0.9 – нижнюю и верхнюю границы 80-процентного доверительного интервала. LightGBM реализован внутри XGBoost-сервиса как альтернативная реализация градиентного бустинга: стратегия построения по листьям (leaf-wise — выбор листа с максимальным снижением ошибки) отличается от построения по уровням (level-wise) у XGBoost (равномерное углубление дерева), что вносит разнообразие в прогнозы и повышает устойчивость ансамбля.

Ансамблевый сервис (EnsembleService) координирует запуск моделей и объединение результатов. Параллельное выполнение сокращает общее время прогноза до ~2 секунд вместо 15–20 при последовательном запуске: три модели запускаются одновременно в отдельных потоках. При ошибке одной модели остальные продолжают работу по принципу мягкой деградации (graceful degradation): если Prophet вернул пустой результат из-за нехватки данных, ансамбль формируется из оставшихся моделей с перераспределением весов.

Веса моделей в ансамбле рассчитываются по формуле inverse-RMSE, приведённой в разделе 1.3. Автокалибровка выполняется не чаще раза в час: сервис сравнивает модели на валидационных данных по метрикам RMSE, MAE и R², затем пересчитывает веса. Помимо взвешенного среднего (weighted_average) доступны простое среднее (simple_average) и выбор лучшей модели (best_model). Кэширование в Redis со временем жизни 30 минут исключает повторные вычисления при частых запросах.

Оценка вклада признаков в модели градиентного бустинга подтверждается визуализацией значимости признаков (feature importance) в экспертном режиме страницы «Прогнозы» (см. рисунок 11).

Пять инструментов покрывают основные аналитические потребности:

1)  search_hotels — семантический поиск по ChromaDB, возвращает наиболее релевантные средства размещения с ценами, рейтингами и координатами;

2)  search_events — поиск предстоящих мероприятий с фильтрацией по дате начала;

3)  get_weather — обращение к Open-Meteo API за текущей и прогнозной погодой по координатам населённых пунктов области;

4)  forecast_occupancy — делегирование отдельному агенту прогнозов, который собирает историю, запускает ансамбль и формирует объяснение на естественном языке;

5)  get_statistics — агрегированные KPI из PostgreSQL: количество отелей, событий, средний рейтинг, заполняемость по районам.

RAG-конвейер (Retrieval-Augmented Generation) расширяет возможности агента контекстом из базы знаний \[34\]. Документы – описания отелей, события, статистические сводки – индексируются в ChromaDB с эмбеддингами GigaChat Embeddings (модель Embeddings API Сбера). При поступлении запроса текст преобразуется в вектор, выполняется поиск ближайших соседей (top-5), найденные фрагменты конкатенируются и добавляются в системную инструкцию (промпт, prompt). Метаданные документов (тип, район, дата актуальности) позволяют сужать поиск до релевантного района и временного периода.

Основной LLM-провайдер – Mistral Large, доступный из РФ без виртуальной частной сети (VPN), с квотой 1 млрд токенов в месяц. Для выбора инструментов настроены минимальные параметры стохастичности, обеспечивающие стабильность ответов. Мультипровайдерная архитектура поддерживает переключение между провайдерами (GigaChat, Groq, DeepSeek, OpenRouter) через единственную переменную окружения; абстракция LangChain скрывает различия API провайдеров.

Потоковая передача через SSE реализована в endpoint POST /api/query/stream, возвращающий StreamingResponse с типом text/event-stream. Каждый токен LLM-ответа передаётся клиенту отдельным SSE-событием. Пользователь видит начало ответа менее чем через секунду, не дожидаясь полной генерации. Контекст разговора сохраняется в памяти агента: при следующем сообщении агент «помнит» предыдущие реплики, что позволяет вести связный диалог. При ошибке LLM-провайдера SSE-канал отправляет событие error и закрывает соединение.

<span id="_Toc225770901" class="anchor"></span>2.3 Проектирование пользовательского интерфейса и обеспечение качества

Клиентская часть системы реализована на связке React 18 + TypeScript + Vite 7, обоснованной в разделе 1.2. TypeScript работает в строгом режиме, что исключает категорию ошибок, связанных с неявными типами. Маршрутизация выполнена через React Router 7 с ленивой загрузкой страниц, не требующихся при начальном отображении..

Информационная архитектура пользовательского интерфейса. Структура навигации веб-приложения построена по задачному принципу: каждая из восьми страниц соответствует конкретному пользовательскому сценарию. Задачный подход к навигации означает, что каждая страница отвечает на один ключевой вопрос: «Куда поехать?» («Главная»), «Что происходит в районе?» («Аналитика»), «Какие события запланированы?» («События»), «Как сравнить районы?» («Регионы и карта»). В ходе разработки навигация была реструктурирована: первоначальный вариант группировал страницы по типу данных (отели, события, погода), итоговый – по пользовательским ролям, разделяя туристические страницы с упрощённой подачей и аналитические с экспертным инструментарием. Подход основан на методологии Л. Розенфельда и П. Морвилля, определяющей информационную архитектуру как проектирование систем организации, навигации и поиска контента, оптимизированных под ментальные модели целевой аудитории \[35\].

Назначение каждой страницы:

1)  «Главная» — планирование поездки на Байкал (выбор района, периода, быстрые вопросы к AI-ассистенту);

2)  «Аналитика» — аналитический обзор района с KPI, историей цен, рекомендациями и прогнозом на 14 дней;

3)  «События» — каталог мероприятий с фильтрацией по типу, источнику и дате;

4)  «Регионы и карта» — географическое сопоставление районов (карточки, тепловая карта, радарное сравнение);

5)  «Прогнозы» — экспертное прогнозирование с переключением между простым и развёрнутым режимами;

6)  «AI-помощник» — полноэкранный диалог с интеллектуальным агентом через потоковую передачу;

7)  «Карточка отеля» — детальная страница отеля, доступная по прямой ссылке /hotels/:id;

8)  «О системе» — презентация системы для защиты ВКР.

Основным элементом навигации пользовательского интерфейса является боковая панель, расположенная в левой части экрана. Панель содержит семь пунктов меню, каждый из которых включает графическую иконку, текстовое название раздела и краткое описание, поясняющее назначение страницы. Пункты «Прогнозы» и «AI-помощник» дополнены визуальными метками «ML» и «AI» соответственно, сигнализирующими об использовании методов машинного обучения и интеллектуальной обработки данных, что повышает прозрачность системы для конечного пользователя. Помимо семи разделов меню, в системе присутствует восьмая страница — карточка отеля, которая не вынесена в навигацию, поскольку представляет собой детализированное описание конкретного объекта размещения. Типичный сценарий взаимодействия туриста выстроен по принципу «от общего к частному». Неподготовленный посетитель видит лишь итоговый график, аналитик — полный инструментарий.

CSS-класс для скелетонов создаёт мерцающую анимацию (shimmer) на основе цветовых токенов темы. Скелетоны воспроизводят структуру целевого контента: на странице «Аналитика» – прямоугольники вместо KPI-карточек и графиков, на «Прогнозах» – полоса вместо диаграммы с областями, на «Событиях» – ряды карточек, на «Регионах и карте» – область карты. Тестирование и безопасность. Тестирование охватывает два уровня. Модульные тесты (93 шт.) разделены на шесть файлов: ансамблевый сервис, вспомогательные функции прогнозирования, безопасность (rate limiting, аутентификация, валидация), роутеры API, схемы данных и инструменты агента. Тестовые заготовки (фикстуры) изолируют тесты: имитационные данные (мок-данные) истории заполняемости, тестовый Redis-клиент, пустая коллекция векторной базы. Тесты роутеров проверяют HTTP-контракты без запущенного сервера через встроенный асинхронный клиент. Сквозные (E2E) тесты включают 9 сценариев: health-endpoint, KPI, список отелей, события, прогноз Prophet, ансамблевый прогноз, погода, запрос к AI-агенту, статус планировщика. Тесты выполняются против запущенного сервера и реальной БД, проверяя цепочку от HTTP-запроса до JSON-ответа.

Четыре уровня безопасности API, описанные в разделе 1.2, реализованы в виде промежуточного ПО (middleware). Конкретные пороговые значения rate limiting, параметры валидации Pydantic и конфигурация заголовков CSP/HSTS вынесены в приложение Б.

Собранные данные содержат ограничение: летний период 2025 года (июль–сентябрь) не покрыт наблюдениями, поскольку система находилась на этапе проектирования. Пробел влияет на точность долгосрочных прогнозов – при горизонте 30+ дней R² может принимать отрицательные значения. Для демонстрации рекомендованы краткосрочные горизонты (3–14 дней). Архитектурно система полностью готова к работе с полными данными: при накоплении летних наблюдений в 2026 году модели обучатся на годовом цикле без изменений кода.

В ходе производственной практики разработана интеллектуальная аналитическая система (ИАС) мониторинга и прогнозирования туристической активности Иркутской области. Поставленная цель достигнута путём последовательного выполнения всех поставленных задач:

Проведён поиск и анализ доступных источников экзогенных данных (8 платформ региональных событий, метео-сервис Open-Meteo). Обоснован выбор моделей градиентного бустинга и фреймворка LangGraph для построения интеллектуального агента.
2. **Обоснован технологический стек системы и выполнена миграция БД:** осуществлён полный переход от устаревшей облачной инфраструктуры (YDB) на локальную PostgreSQL 16 с асинхронным драйвером asyncpg. Для клиентской части внедрены библиотеки высокопроизводительной визуализации Recharts и ECharts.
3. **Спроектирована и реализована подсистема автоматизированного сбора данных**, стабильно агрегирующая информацию из 11 внешних источников (парсер агрегатора, 8 порталов событий, метеоданные Open-Meteo). База данных включает 1 366 объектов размещения и 376 событий по 15 районам.
4. **Разработан ансамблевый метод прогнозирования заполняемости средств размещения и реализующий его модуль.** Метод комбинирует модели Prophet, NeuralProphet и XGBoost с весами inverse-RMSE, что позволило снизить ошибку прогноза (RMSE) до 3,85 п.п. Успешно реализованы инструменты визуальной аналитики моделей.

**Техническая конфигурация инфраструктуры**

Контейнеризация реализована через Docker Compose с двумя режимами: по умолчанию запускаются PostgreSQL 16 и Redis 7 для локальной разработки; профиль full добавляет контейнеры серверной и клиентской частей для развёртывания. Секреты передаются через переменные окружения. Контейнеры работают от непривилегированного пользователя (non-root) для снижения поверхности атаки. Проверки работоспособности (healthcheck: pg_isready, redis-cli ping) обеспечивают мониторинг состояния.

Nginx конфигурация включает: проксирование /api/\* на серверную часть (proxy_pass http://backend:8000), сжатие данных (gzip) статических ресурсов, поддержку SSE-соединений (proxy_buffering off, proxy_read_timeout 300s), заголовки безопасности Content-Security-Policy, Strict-Transport-Security (max-age=31536000), X-Content-Type-Options (nosniff).

Безопасность API:

- Ограничение частоты запросов: упорядоченное множество Redis (sorted set), алгоритм скользящего окна – 60 запросов/мин для общих конечных точек, 10 для /api/query, 5 для /api/parser; при превышении – HTTP 429 с заголовком повторной попытки (Retry-After); при недоступности Redis – резервный механизм в оперативной памяти.

<!-- -->

- API-ключ: заголовок X-API-Key защищает 12 парсерных маршрутов.

<!-- -->

- Валидация: Pydantic Field(ge=0, le=100) для процентов, Field(min_length=1) для строк; параметр days_ahead принимает значения от 1 до 90; символы % и \_ в LIKE-выражениях экранируются для предотвращения SQL-инъекций.

<!-- -->

- CORS: ограничение источников запросов, методы GET, POST, PUT, OPTIONS, заголовки Content-Type, Authorization, X-API-Key.
