# Выбор системы кеширования: сравнительный анализ

## Задачи кеширования в системе

В интеллектуальной аналитической системе мониторинга туристической активности кеширование выполняет несколько функционально различных ролей, что накладывает требования на тип хранилища, модель согласованности и доступные примитивы данных.

**Результаты ансамблевого прогноза (Ensemble).** Сочетание моделей Prophet, NeuralProphet, XGBoost и LightGBM с дорогостоящим feature engineering требует избежания повторных вычислений при идентичных входных параметрах (район, горизонт прогноза, набор признаков). Кеш должен поддерживать явное время жизни записей (TTL) и инвалидацию при обновлении исходных данных.

**Ограничение частоты запросов (rate limiting).** Для защиты дорогих конечных точек (запросы к LLM, парсинг, тяжёлая аналитика) применяется алгоритм скользящего окна. Его корректная реализация в распределённой среде опирается на атомарные операции и структуры, позволяющие хранить временные метки или счётчики с привязкой к окну (например, отсортированные множества или списки с истечением срока).

**Кеширование ответов API.** Часто запрашиваемые агрегаты (KPI, корреляции, справочники районов) целесообразно отдавать из кеша с умеренным TTL, снижая нагрузку на PostgreSQL и сокращая время отклика для интерактивных дашбордов.

**Управление сессиями и потоками ИИ-агента.** В архитектуре на LangGraph персистентность состояния диалога (например, через `MemorySaver` или внешнее хранилище чекпоинтов) может требовать быстрого key-value доступа с TTL или политикой вытеснения; при масштабировании на несколько воркеров предпочтительна общая память процессов, а не локальный словарь.

## Рассматриваемые альтернативы

В сравнительный анализ включены следующие классы решений: **Redis** (in-memory СУБД с богатой моделью данных), **Memcached** (классический распределённый key-value кеш), **in-memory** внутри процесса приложения (`dict`, `functools.lru_cache`, локальные структуры), **Apache Ignite** (распределённая in-memory платформа с SQL и персистентностью), **KeyDB** (мультипоточный форк Redis с совместимостью по протоколу).

## Сравнительная таблица

| Критерий | Redis | Memcached | In-memory (процесс) | Apache Ignite | KeyDB |
|----------|-------|-----------|---------------------|---------------|-------|
| Персистентность | Опционально (RDB, AOF) | Нет | Нет (потеря при рестарте) | Да (диск + репликация) | Как у Redis (форк) |
| Структуры данных | Строки, списки, хеши, ZSET, bitmap и др. | Только строки/blob | Произвольные объекты Python | Кэш-таблицы, SQL, очереди | Совместимо с Redis |
| Pub/Sub | Да | Нет | Нет | Да | Да |
| TTL | Нативно по ключу | Да | Ручная реализация | Политики истечения | Нативно |
| Кластеризация | Redis Cluster, Sentinel | Клиентская шардирование | Нет | Встроенная топология | Аналогично Redis |
| Простота развёртывания | Высокая (официальный образ Docker) | Высокая | Тривиальная (в коде) | Ниже (JVM, конфигурация) | Высокая (совместимость с Redis) |
| Асинхронные драйверы Python | `redis.asyncio` (redis-py) | `aiomcache`, обёртки | Нативно (без I/O) | `pyignite` (ограниченно async) | Тот же стек, что для Redis |

## Детальный анализ

**Redis** сочетает низкую задержку доступа с развитой семантикой данных: отсортированные множества удобны для скользящего окна и ранжирования, хеши — для структурированных фрагментов ответа API, строки с TTL — для сериализованных JSON-результатов прогнозов. Поддержка pub/sub расширяет сценарии (инвалидация кеша по событиям, координация воркеров). Персистентность по желанию позволяет балансировать между чистым кешем и допустимой устойчивостью к перезапуску. Для FastAPI-стека естественен асинхронный клиент `redis.asyncio`.

**Memcached** остаётся эталоном простоты для «плоского» key-value кеширования страниц или бинарных объектов, однако отсутствие встроенных сложных типов усложняет атомарные сценарии rate limiting без дополнительной логики на стороне приложения; отсутствие персистентности и pub/sub сужает применимость для сквозных задач одной платформой.

**In-memory** внутри процесса даёт минимальную латентность и отсутствие сетевых сбоев, но кеш не разделяется между несколькими экземплярами Uvicorn/Gunicorn и полностью теряется при перезапуске. Для rate limiting в мультипроцессной конфигурации это приводит к расхождению лимитов между воркерами. Паттерн допустим как резерв при недоступности внешнего хранилища (graceful degradation).

**Apache Ignite** ориентирован на крупные распределённые кластеры, SQL и интеграцию с экосистемой JVM; для типичного сервиса на Python с основной БД PostgreSQL такой уровень сложности избыточен, а операционные издержки выше, чем у специализированного in-memory key-value.

**KeyDB** использует совместимость с протоколом Redis и многопоточную модель, что может дать выигрыш в CPU-bound нагрузках на одном узле. Экосистема инструментов, примеров и хостинг-практик по-прежнему смещена в сторону Redis; миграция возможна, но выгода для текущего масштаба проекта не детерминирующая.

## Обоснование выбора Redis для данного проекта

Для рассматриваемой системы туристической аналитики **Redis** выступает компромиссом между функциональностью и операционной простотой. Алгоритм скользящего окна в middleware ограничения частоты запросов опирается на централизованное хранилище с атомарными операциями; отсортированные множества и комбинации ключей с TTL хорошо согласуются с этой задачей. Кеширование результатов Ensemble и тяжёлых аналитических эндпоинтов требует гибкой политики TTL и сериализации структурированных ответов — достаточно строкового слоя с JSON, что нативно поддерживается Redis.

Развёртывание через **Docker** (официальный образ, healthcheck, соседство с PostgreSQL в `docker-compose`) снижает порог внедрения для дипломного стенда и промышленного прототипа. В кодовой базе реализован **fallback на in-memory** при недоступности Redis: приложение продолжает обслуживать запросы без распределённого кеша и с локальным ограничителем, что соответствует принципу устойчивости к отказу зависимости второго уровня.

Альтернативы либо не закрывают совокупность сценариев без дополнительных компонентов (Memcached, чистый in-memory), либо избыточны по сложности эксплуатации для данного контура (Apache Ignite). KeyDB остаётся резервом на этапе масштабирования при узком профиле нагрузки, не меняя прикладной код благодаря совместимости протокола.
