# Инфраструктура развёртывания: сравнительный анализ

## Критерии выбора

При выборе инфраструктуры развёртывания ИАС учитывались: простота воспроизведения среды (демонстрация на защите ВКР), изоляция сервисов (PostgreSQL, Redis, backend, frontend), поддержка SSE-потоков и WebSocket, возможность настройки безопасности (CSP, HSTS, rate limiting), а также минимальные требования к вычислительным ресурсам.

## Рассматриваемые альтернативы

### Оркестрация контейнеров

| Критерий | Docker Compose | Kubernetes | Bare metal |
|----------|---------------|------------|------------|
| Сложность настройки | Один YAML-файл | Высокая (манифесты, Helm) | Ручная установка каждого сервиса |
| Воспроизводимость | Полная (docker-compose.yml) | Полная (декларативная) | Низкая (зависит от ОС) |
| Масштабирование | Вертикальное (replicas) | Горизонтальное (pods, HPA) | Ручное |
| Мониторинг healthcheck | Встроенный (healthcheck) | Liveness/readiness probes | Ручной (systemd) |
| Управление секретами | .env файл | Secrets/ConfigMaps | Env vars / .env |
| Требования к ресурсам | ~512 МБ RAM | ≥4 ГБ RAM (control plane) | Зависит от сервисов |

**Docker Compose** выбран как оптимальное решение для учебного проекта: единый `docker-compose.yml` описывает PostgreSQL 16, Redis 7, backend и frontend, обеспечивая полную воспроизводимость среды. Kubernetes избыточен — горизонтальное масштабирование не требуется для демонстрационной системы с одним пользователем. Bare metal отвергнут из-за низкой воспроизводимости и сложности настройки зависимостей на разных ОС.

Конфигурация Docker включает: non-root контейнеры, healthcheck-проверки для PostgreSQL и Redis, ограничение портов (только 80/443 наружу), передача секретов через переменные окружения, поддержка профилей (`--profile full` для полного стека).

### Обратный прокси-сервер

| Критерий | nginx | Caddy | Traefik |
|----------|-------|-------|---------|
| Производительность | Высокая (event-driven) | Средняя | Средняя |
| SSL/TLS | Ручная настройка (Let's Encrypt) | Автоматический ACME | Автоматический ACME |
| SSE-поддержка | Настраиваемая (proxy_buffering off) | Встроенная | Встроенная |
| Security headers | Ручная настройка (гибкая) | Ограниченная | Middleware |
| Конфигурация | Файловая (nginx.conf) | Caddyfile (простая) | Labels / TOML |
| Документация | Обширная | Средняя | Средняя |

**nginx** выбран за высокую производительность, гибкую настройку security headers (CSP, HSTS, X-Frame-Options, X-Content-Type-Options) и управляемую поддержку SSE через отключение буферизации (`proxy_buffering off`). Caddy проще в настройке SSL, но уступает в гибкости конфигурации заголовков безопасности. Traefik ориентирован на динамическое обнаружение сервисов в Kubernetes, что избыточно для данного проекта.

Конфигурация nginx включает: проксирование API-запросов на FastAPI (`/api/ → localhost:8000`), раздачу статики фронтенда, настройку SSE (`proxy_read_timeout 300s`, `proxy_buffering off`), заголовки безопасности (CSP с ограничением источников скриптов и стилей, HSTS с `max-age=31536000`), сжатие gzip для текстовых ресурсов.

### Планировщик задач

| Критерий | APScheduler | Celery | cron (системный) |
|----------|-------------|--------|-------------------|
| Интеграция с Python | In-process | Отдельный воркер | Внешний процесс |
| Брокер сообщений | Не требуется | Redis/RabbitMQ (обязательно) | Не применимо |
| Персистентность задач | JobStore (SQLAlchemy) | Result backend | Нет |
| Async-совместимость | AsyncIOScheduler | Ограниченная | Нет |
| Мониторинг | Программный (logging) | Flower (веб-интерфейс) | Логи |
| Сложность | Низкая | Высокая | Минимальная |

**APScheduler** с `AsyncIOScheduler` выбран за внутрипроцессную работу без необходимости отдельного брокера сообщений. Планировщик запускает периодические задачи: обновление событий, отелей, погоды, Telegram-каналов (интервалы по конфигурации). Отдельной задачи «очистка устаревшего кэша по расписанию» в планировщике нет — при необходимости TTL обеспечивается на стороне Redis/логикой кэша. Celery отвергнут как избыточное решение, требующее отдельного воркера и брокера для нескольких периодических задач. Системный cron не обеспечивает интеграцию с async-кодом и персистентность состояния задач.

## Обоснование выбора

Итоговая инфраструктура (Docker Compose + nginx + APScheduler) обеспечивает: полную воспроизводимость среды через один файл конфигурации, безопасность на уровне транспорта и HTTP-заголовков, поддержку SSE-потоков для AI-чата, периодическое обновление данных без внешних зависимостей. Архитектура допускает миграцию на Kubernetes при промышленном внедрении без изменения кода приложения — потребуется только создание Helm-чартов на основе существующего `docker-compose.yml`.
