# Выбор фреймворка бэкенда: сравнительный анализ

Настоящий документ обосновывает выбор технологии серверной части для интеллектуальной аналитической системы мониторинга и прогнозирования туристической активности (ВКР). Предметная область характеризуется одновременным наличием: интенсивного ввода-вывода (парсинг внешних источников, обращения к PostgreSQL, Redis, внешним API погоды и агрегаторов), вычислительно тяжёлых синхронных операций (модели Prophet, NeuralProphet, XGBoost, LightGBM, ансамблевое прогнозирование), потоковой отдачи ответов ИИ-агента (SSE) и строгих требований к контракту REST API для фронтенда на React.

## Критерии выбора

Для системы туристической аналитики с ML, обновляемыми во времени данными и асинхронными конвейерами сбора информации целесообразно выделить следующие критерии:

1. **Нативная поддержка асинхронного ввода-вывода (async/await, ASGI)** — возможность параллельно обслуживать запросы к БД, HTTP-клиентам и LLM без блокировки цикла событий при корректном вынесении CPU-bound задач в пул потоков или отдельные процессы.

2. **Совместимость с блокирующим ML- и научным стеком** — предсказуемая интеграция библиотек вроде Prophet, scikit-learn, XGBoost через `asyncio.to_thread`, фоновые задачи или очереди без нарушения отзывчивости API.

3. **Валидация и сериализация данных на границе API** — декларативное описание схем запросов и ответов, единый источник истины для контракта с клиентом и для генерации документации.

4. **Автоматическое построение спецификации OpenAPI и интерактивная документация** — ускорение разработки десятков эндпоинтов, снижение расхождений между реализацией и документацией, удобство приёмочного тестирования.

5. **Производительность и масштабируемость при I/O-нагрузке** — устойчивое поведение при множестве одновременных обращений к прогнозам, аналитике и агенту; сопоставимость с эталонными бенчмарками в классе Python-фреймворков.

6. **Поддержка потоковой передачи (SSE, streaming)** — для сценариев чата с пошаговой отдачей токенов или фрагментов ответа без буферизации всего сообщения в памяти.

7. **Гибкость middleware и политик безопасности** — ограничение частоты запросов, проверка API-ключей, CORS, заголовки безопасности при развёртывании за обратным прокси.

8. **Соответствие архитектуре «API-first» без избыточного монолита** — проект ориентирован на REST/SSE и отдельный SPA-фронтенд; отсутствие обязательной привязки к серверному рендерингу страниц и к «батарейкам», не используемым в данной постановке (например, встроенная админ-панель как обязательный компонент).

## Рассматриваемые альтернативы

В сравнение включены пять решений, представляющих различные архитектурные подходы в экосистеме Python:

- **FastAPI** — ASGI-фреймворк высокого уровня на базе Starlette и Pydantic, ориентированный на типизированные API и автоматический OpenAPI.

- **Django** — полнофункциональный MVC/MTV-фреймворк с мощной ORM, системой приложений и зрелой экосистемой; в современных версиях поддерживает асинхронные представления, однако исторически ориентирован на синхронную модель и широкий набор встроенных подсистем.

- **Flask** — минималистичный WSGI-фреймворк; гибкий, но без встроенной async-модели на уровне ядра и без автоматической генерации OpenAPI.

- **Starlette** — лёгкий ASGI-фреймворк низкого уровня; высокая производительность и гибкость за счёт меньшего числа соглашений «из коробки».

- **Litestar** — современный ASGI-фреймворк с акцентом на типизацию, валидацию и производительность; конкурирует с FastAPI в нише типобезопасных API.

Условная шкала: **5** — оптимально для заданного критерия в контексте описанного проекта; **4** — хорошо с дополнительными библиотеками или оговорками; **3** — приемлемо; **2** — существенные компромиссы; **1** — несоответствие или высокая стоимость доработки. В скобках — краткий комментарий.

| Критерий | FastAPI | Django | Flask | Starlette | Litestar |
|----------|---------|--------|-------|-----------|----------|
| Async I/O (ASGI) | **5** (нативно, весь стек async-совместим) | **3** (async views есть; часть ORM/интеграций остаётся sync-ориентированной) | **2** (WSGI; async через расширения/обходные пути) | **5** (чистый ASGI) | **5** (ASGI) |
| ML / блокирующие вычисления | **4** (паттерн `asyncio.to_thread`, фоновые задачи; не встроено, но документировано в экосистеме) | **4** (Celery, threads; проверенные паттерны, но тяжелее каркас) | **4** (то же, вручную) | **3** (ниже уровень абстракции — больше кода обвязки) | **4** (аналогично FastAPI) |
| Валидация и схемы API | **5** (Pydantic v2, интеграция с OpenAPI) | **4** (Django REST framework + serializers; не в ядре) | **2** (Marshmallow/Pydantic вручную) | **3** (часто Pydantic отдельно) | **5** (встроенная валидация, DTO) |
| OpenAPI / интерактивные docs | **5** (`/docs`, `/redoc`, схема из типов) | **4** (через DRF Spectacular и аналоги) | **2** (Flask-Smorest и др.) | **3** (ручная или сторонние обвязки) | **5** (автогенерация, OpenAPI) |

| SSE / streaming | **5** (`StreamingResponse`, `text/event-stream`) | **4** (реализуемо, больше шаблонного кода) | **3** (возможно, не идиоматично) | **5** (нативно на ASGI) | **5** (поддержка streaming) |
| Middleware, security hooks | **4** (Starlette middleware) | **5** (зрелая цепочка, CSRF и пр. — избыточно не всегда нужно) | **3** (ручная сборка) | **5** (гибко) | **4** |

Сводка: для **данного** проекта (десятки эндпоинтов, async PostgreSQL, Redis, парсеры, ML-ансамбль, SSE для агента) лидируют **FastAPI**, **Litestar** и **Starlette**. Django и Flask уступают по сочетанию нативного async, автоматического OpenAPI и лаконичности API-only архитектуры.

## Детальный анализ

### FastAPI

**Сильные стороны для рассматриваемого проекта.** Фреймворк изначально спроектирован под **async/await** и ASGI-серверы (Uvicorn, Hypercorn и др.), что согласуется с асинхронным доступом к PostgreSQL (asyncpg, SQLAlchemy 2.0 async), неблокирующими HTTP-клиентами (aiohttp, httpx) и параллельным опросом внешних источников данных о туризме и событиях.

Встроенная связка с **Pydantic** обеспечивает валидацию входных параметров и тел запросов, сериализацию ответов и формирование **схемы OpenAPI** без дублирования описаний. Интерактивная документация (Swagger UI по умолчанию на `/docs`, ReDoc) снижает трудозатраты на сопровождение большого числа маршрутов и упрощает взаимодействие с фронтенд-командой; настройка URL документации описана в официальном руководстве [Metadata and Docs URLs](https://fastapi.tiangolo.com/tutorial/metadata/#docs-urls).

**Интеграция с ML-библиотеками.** Модели Prophet, NeuralProphet, XGBoost выполняют преимущественно синхронные CPU-bound расчёты. Рекомендуемый в экосистеме asyncio паттерн — вынесение таких вызовов в **`asyncio.to_thread()`** (или эквивалентный пул потоков), чтобы не блокировать event loop. FastAPI не мешает этому: асинхронные обработчики остаются отзывчивыми для других запросов, пока прогноз считается в отдельном потоке. Ансамблевое объединение прогнозов и кэширование в Redis логично размещаются в сервисном слое поверх того же подхода.

**SSE и потоковая отдача.** Для сценария ИИ-агента с пошаговой передачей данных клиенту применим класс **`StreamingResponse`** с `media_type="text/event-stream"` и асинхронным генератором контента; в справочнике FastAPI описана поддержка sync и async итераторов и фоновых задач после начала ответа [StreamingResponse](https://fastapi.tiangolo.com/reference/responses/#streamingresponse-class).

**Производительность.** FastAPI входит в набор **TechEmpower Framework Benchmarks** (конфигурации с различными ASGI-серверами и прокси). В **Round 23** (март 2025 г.) отмечено обновление инфраструктуры тестов и масштаб сравнения сотен фреймворков; абсолютные цифры зависят от типа теста (JSON, запросы к БД, шаблоны), однако **ASGI-стек Starlette/FastAPI** стабильно относится к быстрым представителям экосистемы Python в синтетических нагрузочных тестах. Для ВКР важно интерпретировать бенчмарки как ориентир при **I/O-ограниченной** нагрузке, а не как гарантию скорости конкретного ML-инференса, который ограничен CPU и памятью.

### Django

Django обеспечивает **зрелую ORM**, встроенную админ-панель, систему миграций и богатую экосистему пакетов. Для крупного продукта с серверным рендерингом, сложной моделью прав доступа и администрированием контента это существенные преимущества.

**Ограничения для данного проекта.** Архитектура ВКР — **отдельный SPA и REST/SSE API** без использования Django Templates как основного UI. Типичный «полный» стек Django создаёт **избыточную массу** зависимостей и соглашений относительно узкой задачи публичного API. Асинхронность в Django развивается, однако многие прикладные паттерны и сторонние пакеты по-прежнему ориентированы на **синхронное** выполнение; смешение async/sync требует дисциплины. Для **тяжёлых ML-задач** сам по себе Django не ускоряет вычисления; преимущество — в инфраструктуре фоновых очередей (например, Celery), что возможно и вне Django.

### Flask

Flask остаётся **лёгким и гибким** выбором для небольших сервисов. Для проекта с **множеством асинхронных парсеров**, async ORM и потоковым чатом недостатки проявляются в том, что ядро ориентировано на **WSGI**: нативная модель async отсутствует, OpenAPI и строгая валидация **не встроены** (подключаются отдельными расширениями). Итог — больший объём инфраструктурного кода и риск расхождения схем с реализацией по сравнению с FastAPI/Litestar.

### Starlette

Starlette — **фундамент** для FastAPI: маршрутизация, middleware, Request/Response, поддержка WebSocket и streaming на уровне ASGI. Для команды, готовой вручную собирать валидацию, OpenAPI и соглашения о структуре проекта, Starlette даёт **минимальные накладные расходы** и максимальный контроль. В контексте ВКР с фиксированными сроками и необходимостью **автоматической документации и Pydantic-схем** целесообразнее использовать FastAPI как надстройку, не отказываясь от преимуществ нижележащего Starlette.

### Litestar

Litestar — конкурентоспособный ASGI-фреймворк с упором на **типизацию, валидацию и высокую производительность**; поддерживает OpenAPI и сценарии вроде streaming. Для описанного проекта он является **сильной альтернативой** FastAPI. Выбор между FastAPI и Litestar во многом определяется зрелостью экосистемы, объёмом учебных материалов и совместимостью с уже принятыми в проекте библиотеками (LangGraph, интеграции LLM). На момент подготовки системы для ВКР **FastAPI** обладает более широким распространением в индустрии и документации, что облегчает сопровождение и защиту работы.

## Обоснование выбора FastAPI

Для интеллектуальной системы туристической аналитики с **асинхронными парсерами**, **PostgreSQL и Redis**, **ансамблевым прогнозированием** (Prophet, NeuralProphet, градиентный бустинг) и **ИИ-агентом** с **SSE-потоком** оптимальным компромиссом признаётся **FastAPI** по следующим причинам:

1. **Единая модель async** для сетевого I/O и БД при документированном способе вынесения ML в потоки — соответствует реальной смеси I/O-bound и CPU-bound нагрузок.

2. **Pydantic и автоматический OpenAPI** сокращают трудозатраты на поддержку десятков эндпоинтов и искажения контракта между React-клиентом и сервером.

3. **StreamingResponse** и экосистема Starlette закрывают требование **потоковой отдачи** ответов агента без смены стека.

4. **Участие в независимых бенчмарках** (TechEmpower, в т.ч. Round 23, 2025) подтверждает конкурентоспособность стека в классе Python при корректном развёртывании.

5. **Litestar** рассматривается как близкая по возможностям альтернатива; **Django** и **Flask** в данной постановке уступают по сочетанию нативного async, автогенерации API и минимализма каркаса для API-only сервиса.

Практическая реализация бэкенда ВКР (роутеры прогнозов, аналитики, событий, парсеров, query/stream для агента) опирается на указанные свойства FastAPI и согласуется с архитектурой, описанной в проектной документации.

## HTTP-клиенты: aiohttp и httpx

Для исходящих запросов к внешним сайтам и API в парсерах используется **aiohttp**: полностью асинхронный клиент с сессиями и естественной связкой с `asyncio.gather` для параллельного опроса источников без блокировки event loop. **httpx** применяется в тестах: у него есть ASGI transport, что позволяет вызывать приложение FastAPI напрямую в pytest без поднятого TCP-сервера и стабильно проверять контракты эндпойнтов. Такое разделение — продакшен I/O на aiohttp, изолированные проверки API на httpx — уменьшает смешение ответственности и упрощает сопровождение.
