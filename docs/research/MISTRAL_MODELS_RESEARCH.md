```
│  │ Параметры:                │    │ Параметры (из тестов):    │    │
│  │ • temp=0.1 (Mistral Best  │    │ • extraction: temp=0.0    │    │
│  │   Practices для tools)    │    │ • classification: temp=0.0│    │
│  │ • top_p=0.9               │    │ • recommendation: temp=0.4│    │

│  └───────────────────────────┘    └───────────────────────────┘    │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

### Где используются результаты тестов

| Тест | Результат | Где применяется |
|------|-----------|-----------------|
| **Модели (Large/Small/8B)** | Large лучше для сложных | Agent: Large, Direct: по задаче |
| **temperature 0.0** | 100% консистентность | `extract_structured()`, classification |
| **temperature 0.4** | Баланс креатив/точность | `explain_forecast()`, recommendations |
| **temperature 0.1** | Mistral рекомендует для tools | LangGraph Agent |
| **json_schema** | Гарантированный JSON | `extract_structured()` |
| **top_p=1 при temp=0** | Фикс ошибки API | Все вызовы с temp=0 |
| **Русский в system prompt** | Язык ответов | Оба компонента |
| **RAG точность 100%** | Качество ответов | `generate_response()` |
| **Реальные данные** | Валидация на проекте | Подтверждено качество |

### Почему разные температуры

**LangGraph Agent (temp=0.1):**
- Mistral официально рекомендует для function calling
- Источник: docs.mistral.ai/capabilities/function_calling
- Цель: стабильный выбор правильного tool

**Direct LLM Calls (temp=0.0-0.4):**
- Из наших тестов на реальных данных
- extraction: 0.0 (детерминизм)
- recommendation: 0.4 (креативность)

## Архитектурное решение: Adaptive Model Routing

### Теоретическое обоснование

Реализованная архитектура основана на современном паттерне **Model Routing** — динамической маршрутизации запросов между моделями разного класса в зависимости от типа задачи.

**Источники:**
- LLMRouterBench (arXiv:2601.07206, 2026) — benchmark для систем маршрутизации
- RouteLLM (ICML 2025) — framework для cost-aware routing
- Cascade Routing (arXiv:2410.10347) — unified approach to routing and cascading
- ASDLC.io Model Routing Patterns — индустриальные паттерны

### Ключевые концепции

**"Iron Triangle" LLM систем:**
```
        Latency
           △
          /|\
         / | \
        /  |  \
       /   |   \
      ▽────┴────▽
   Cost        Quality
```

Невозможно оптимизировать все три параметра одновременно. Model Routing позволяет достичь **frontier-class quality** при **efficient-class costs** путем маршрутизации 80-90% простых запросов на легкие модели.

### Реализованный подход

```
┌─────────────────────────────────────────────────────────────┐
│                    Adaptive Model Routing                    │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  Входящий запрос                                            │
│        │                                                     │
│        ▼                                                     │
│  ┌──────────────┐                                           │
│  │ Task Router  │ ← _get_mistral_config(task_type)          │
│  └──────────────┘                                           │
│        │                                                     │
│   ┌────┴────┐                                               │
│   ▼         ▼                                               │
│ ┌─────┐  ┌─────┐                                            │
│ │Small│  │Large│                                            │
│ │0.52s│  │6.32s│                                            │
│ └──┬──┘  └──┬──┘                                            │
│    │        │                                               │
│    ▼        ▼                                               │
│  JSON    Dialog                                             │
│  Extract Recommend                                          │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### Научное обоснование выбора

| Критерий | mistral-small | mistral-large | Решение |
|----------|---------------|---------------|---------|
| Latency | 0.52s | 6.32s | Small для UX-критичных |
| JSON accuracy | 100% | 100% | Равны → выбор по скорости |
| Dialog quality | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | Large для качества |
| Консистентность | 100% | 100% | Равны |
| Cost efficiency | 10x дешевле | Базовая | Small для массовых операций |

**Вывод:** Для задач extraction/classification оптимальна Small модель (равное качество при 3x скорости). Для dialog/planning необходима Large (превосходящее качество ответов).

## Исследование температуры

### Теория (по исследованиям 2025-2026)

| Temperature | Характеристика | Применение |
|-------------|----------------|------------|
| 0.0 | Детерминированный, повторяемый | Извлечение фактов, JSON |
| 0.1-0.3 | Минимальная вариация | RAG, структурированные данные |
| 0.3-0.5 | Баланс точности и гибкости | Рекомендации, Q&A |
| 0.5-0.7 | Креативность с контролем | Персональные советы |
| 0.7-1.0 | Максимальная креативность | Генерация контента |

### Практический тест (mistral-large)

```
Вопрос: "Когда лучше всего посещать Байкал для подводного плавания?"

temp=0.0: "с июня по сентябрь, вода +10…+14°C, прозрачность до 40м"
temp=0.3: "с июня по сентябрь, вода +10°C до +16°C" 
temp=0.5: "с июня по сентябрь, прозрачность 20-40 метров"
temp=0.7: "с июня по сентябрь, +4…+10°C в начале"
temp=1.0: "+8…+12°C, нужна гидрокостюм 7-9 мм"
```

**Наблюдения:**
- 0.0-0.3: Стабильные, точные ответы
- 0.5-0.7: Небольшие вариации в деталях
- 1.0: Добавляет новые детали (гидрокостюм), но может галлюцинировать

### Рекомендации для проекта

| Компонент | Temperature | Обоснование |
|-----------|-------------|-------------|
| RAG: извлечение событий | **0.0** | Максимальная точность JSON |
| RAG: классификация | **0.0** | Детерминированный результат |
| Агент: рекомендации | **0.3-0.4** | Баланс точности и гибкости |
| Агент: планирование | **0.4** | Структурированный, но гибкий |
| Агент: диалог | **0.5** | Естественность общения |

## Параметры top_p и max_tokens

### top_p (nucleus sampling)

| top_p | Эффект | Рекомендация |
|-------|--------|--------------|
| 0.1 | Только топ-10% вероятных токенов | Извлечение фактов |
| 0.5 | Средняя выборка | Структурированные задачи |
| 0.9 | Широкая выборка | Креативные задачи |
| 1.0 | Все токены (по умолчанию) | Общее использование |

**Рекомендация для проекта:** top_p = 0.9 (по умолчанию достаточно)

### max_tokens

| Задача | max_tokens | Обоснование |
|--------|------------|-------------|
| Классификация | 50 | Одно слово |
| Извлечение JSON | 200 | Компактный JSON |
| Короткий ответ | 500 | 2-3 абзаца |
| Детальный ответ | 1000 | Полное описание |
| Планирование | 2000 | Развернутый маршрут |

## Лимиты бесплатного тарифа Mistral

| Параметр | Лимит |
|----------|-------|
| Токены в месяц | **1 000 000 000** (1B) |
| Запросы в секунду | 1 |
| Токены в минуту | 500 000 |

**Расчет для проекта:**
- Средний запрос: ~500 токенов
- 1B токенов / 500 = **2 000 000 запросов/месяц**
- Это ~66 000 запросов в день

**Вывод:** Лимитов хватит с огромным запасом для любого масштаба.

## Best Practices из официальной документации (Context7)

### 1. Structured Output (JSON Mode)

Для гарантированного JSON используй `response_format`:

```python
# Простой JSON mode
chat_response = client.chat.complete(
    model="mistral-large-latest",
    messages=[...],
    response_format={"type": "json_object"},
    temperature=0
)

# Строгая JSON Schema (лучше для извлечения)
response_format = {
    "type": "json_schema",
    "json_schema": {
        "schema": {
            "properties": {
                "event": {"type": "string"},
                "date": {"type": "string"},
                "location": {"type": "string"}
            },
            "required": ["event", "date", "location"],
            "additionalProperties": False
        },
        "name": "event_extraction",
        "strict": True
    }
}
```

### 2. Детерминированные ответы

Для воспроизводимых результатов используй `random_seed`:

```python
chat_response = client.chat.complete(
    model=model,
    messages=[...],
    temperature=0,
    random_seed=42  # Фиксированный seed
)
```

### 3. Retry Configuration

Встроенная поддержка ретраев:

```python
from mistralai.utils import RetryConfig

retries = RetryConfig(
    max_retries=3,
    timeout=10.0
)

chat_response = client.chat.complete(
    model=model,
    messages=[...],
    retries=retries
)
```

### 4. Safe Prompt

Для безопасности можно включить:

```python
chat_response = client.chat.complete(
    model=model,
    messages=[...],
    safe_prompt=True  # Инжектит safety prompt
)
```

### 5. Batch API (экономия 50%)

Для массовых операций:
- 50% скидка на токены
- До 1M pending requests
- Не влияет на rate limits

### Финальный выбор моделей

| Задача | Модель | Temperature | Обоснование |
|--------|--------|-------------|-------------|
| RAG: Extraction | **mistral-small** | 0.0 | Быстрее, точнее для JSON |
| RAG: Classification | **mistral-small** | 0.0 | 0.33s, 100% точность |
| Agent: Recommendations | **mistral-large** | 0.4 | Развернутые ответы |
| Agent: Planning | **mistral-large** | 0.4 | Детализация важна |
| Agent: Dialog | **mistral-large** | 0.5 | Естественность |

### Оптимальные параметры (финальные)

```python
# Для RAG / Extraction
EXTRACTION_CONFIG = {
    "model": "mistral-small-latest",
    "temperature": 0.0,
    "max_tokens": 200,
    "response_format": {
        "type": "json_schema",
        "json_schema": {..., "strict": True}
    }
}

# Для Agent / Recommendations
AGENT_CONFIG = {
    "model": "mistral-large-latest",
    "temperature": 0.4,
    "max_tokens": 1000,
    "top_p": 0.9,
}
```

### Стратегия экономии токенов

**80% операций** (classification, extraction) → **mistral-small** = **~3x быстрее**
**20% операций** (recommendations, planning) → **mistral-large** = **качество**

### Важные best practices

1. **JSON extraction:** Используй `json_schema` с `strict: true`
2. **Консистентность:** temp=0.0 для детерминированных ответов
3. **Галлюцинации:** Строгий system prompt для RAG
4. **Производительность:** Small для рутины, Large для качества
5. **ВАЖНО:** При `temperature=0` обязательно `top_p=1` (greedy sampling)
6. **System prompt:** ОБЯЗАТЕЛЬНО указывать "Отвечай на русском" (иначе китайский)
7. **Edge cases:** Пустой ввод возвращает 400, остальное обрабатывается

## Научные выводы и рекомендации

### Валидация архитектурного решения

Проведенное экспериментальное исследование подтверждает эффективность подхода Adaptive Model Routing:

1. **Гипотеза:** Разделение моделей по типам задач улучшает соотношение latency/quality
   - **Результат:** ✅ Подтверждено. Small модель показывает идентичное качество для extraction при 3x меньшей latency

2. **Гипотеза:** Temperature=0.0 оптимален для структурированного извлечения
   - **Результат:** ✅ Подтверждено. 100% консистентность, детерминированный вывод

3. **Гипотеза:** Large модель необходима для диалоговых задач
   - **Результат:** ✅ Подтверждено. Качество ответов значительно выше (экспертная оценка)

### Соответствие индустриальным стандартам

| Паттерн | Источник | Реализация в проекте |
|---------|----------|---------------------|
| Model Routing | ASDLC.io, RouteLLM | `_get_mistral_config()` |
| Task-based Selection | LLMRouterBench | extraction → Small, dialog → Large |
| Deterministic Extraction | Best Practices | temp=0.0 + json_schema |
| Greedy Sampling Fix | Mistral Docs | top_p=1.0 при temp=0 |

### Вклад в научную новизну ВКР

1. **Экспериментальная валидация** Model Routing на реальных туристических данных
2. **Оптимизация параметров** для русскоязычного RAG (temperature, system prompt)
3. **Интеграция json_schema** для гарантированного структурированного вывода
4. **Документирование edge cases** (китайский язык без system prompt, greedy sampling)

### Ограничения исследования

- Тестирование проведено на одном провайдере (Mistral AI)
