# Выбор векторной базы данных для RAG: сравнительный анализ

## Задача

В интеллектуальной аналитической системе мониторинга туристической активности требуется организовать хранение векторных представлений (эмбеддингов) текстовых данных и обеспечить семантический поиск для модуля Retrieval-Augmented Generation (RAG). Предметная область предполагает индексацию описаний средств размещения, анонсов и описаний событий, а также нормативно-справочной и аналитической документации по туризму региона.

Контекст использования: вспомогательный поиск релевантных фрагментов для AI-агента на базе LangGraph, который формирует ответы пользователю на естественном языке. Ориентировочный объём корпуса на этапе дипломного проекта — порядка 1000 документов с перспективой роста за счёт периодического пополнения событий и данных об отелях. Векторизация текста выполняется через API эмбеддингов GigaChat (Сбер), что накладывает требования к размерности векторов и совместимости клиентских библиотек с выбранным хранилищем.

Критерии выбора решения: возможность локального развёртывания (в т.ч. для демонстрации и защиты ВКР), устойчивое хранение индекса между перезапусками, простота интеграции с экосистемой LangChain, адекватная производительность при заданном масштабе данных и приемлемая совокупная стоимость владения.

## Рассматриваемые альтернативы

В сравнительном обзоре участвуют следующие варианты: **ChromaDB**, **FAISS**, **Pinecone**, **Weaviate**, **Milvus**, расширение **pgvector** для СУБД PostgreSQL, **Qdrant**. Данный набор охватывает встроенные и облачные SaaS-решения, специализированные векторные СУБД и гибридный подход «реляционная БД + векторный поиск».

## Детальный анализ

**ChromaDB** позиционируется как ориентированная на разработчиков встраиваемая векторная база с упором на сценарии RAG и прототипирование. Для небольших и средних корпусов она обеспечивает персистентное хранение коллекций, запросы по сходству и фильтрацию по метаданным, а также прямую поддержку в LangChain. Преимущества — минимальный порог входа и отсутствие обязательной оплаты при локальном использовании. Ограничения связаны с тем, что для крупномасштабных распределённых нагрузок часто выбирают специализированные кластерные решения.

**FAISS** (Facebook AI Similarity Search) — высокопроизводительная библиотека индексации и поиска ближайших соседей. Она обеспечивает исключительную скорость на CPU/GPU, но не является полноценной «базой данных» в классическом смысле: персистентность, транзакции, обновление коллекций и метаданные обычно реализуются на уровне приложения. Интеграция с LangChain возможна, однако требует большего объёма кода и соглашений о сериализации индекса.

**Pinecone** — управляемый облачный сервис с сильной экосистемой и предсказуемой моделью масштабирования. Для учебного и дипломного проекта с требованием автономной демонстрации и работы без стабильного внешнего канала зависимость от интернета и платёжной модели снижает привлекательность, несмотря на удобство эксплуатации в продакшене.

**Weaviate** — многофункциональная векторно-семантическая СУБД с модульностью, GraphQL API и развитыми возможностями фильтрации. Развёртывание и сопровождение для корпуса ~1000 документов может оказаться избыточным с точки зрения операционных затрат и сложности инфраструктуры по сравнению с встраиваемым решением.

**Milvus** ориентирован на высоконагруженные и распределённые сценарии с большими объёмами векторов. Архитектурная тяжесть и типичный сценарий развёртывания (отдельные компоненты, оркестрация) для задач дипломного прототипа с умеренным объёмом данных не дают существенного выигрыша при пропорциональном росте сложности.

**pgvector** позволяет хранить векторы в уже используемой PostgreSQL, унифицируя транзакционные данные и эмбеддинги в одной СУБД. Это упрощает резервное копирование и согласованность, однако набор векторных операций и оптимизаций может быть менее богатым, чем у специализированных движков; производительность при росте размерности и QPS зависит от конфигурации PostgreSQL и выбора индексов (например, IVFFlat, HNSW — в зависимости от версии и настроек).

**Qdrant** демонстрирует хорошие показатели по скорости и фильтрации, имеет зрелый API и поддержку LangChain. При этом для проекта, уже использующего Docker с PostgreSQL и Redis, добавление отдельного сервиса векторного поиска увеличивает число компонентов контура развёртывания по сравнению с вариантом встраивания ChromaDB в приложение.

## Обоснование выбора ChromaDB

Для настоящего проекта (ИАС туристической аналитики с корпусом порядка 1000 документов, локальным развёртыванием для дипломной работы, эмбеддингами GigaChat и агентом на LangGraph) **ChromaDB** представляется рациональным компромиссом между функциональностью, простотой внедрения и стоимостью.

Во-первых, масштаб данных находится в зоне, где специализированные распределённые СУБД не дают обязательного выигрыша, тогда как лёгкость настройки и сопровождения критична для учебного контура.

Во-вторых, требование **бесплатного** локального запуска исключает облач-only сервисы как основной вариант для базовой конфигурации ВКР.

В-третьих, **персистентность** и воспроизводимость демонстрации (сохранение коллекции между перезапусками backend) соответствуют ожиданиям к инженерной зрелости прототипа.

В-четвёртых, **прямая интеграция с LangChain** снижает объём шаблонного кода и риск ошибок при связывании RAG-цепочки с хранилищем.

Наконец, **простой Python API** согласуется со стеком проекта (FastAPI, асинхронные сервисы) и ускоряет итерации при доработке агента и состава индексируемых документов.

Альтернативы (pgvector в существующей PostgreSQL, Qdrant, Weaviate) остаются обоснованными для этапа промышленной эксплуатации или роста нагрузки; фиксация выбора ChromaDB в рамках ВКР отражает приоритет **доказуемой работоспособности RAG-контура** при ограниченном объёме данных и ресурсах на сопровождение инфраструктуры.
